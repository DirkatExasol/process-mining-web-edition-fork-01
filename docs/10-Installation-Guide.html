Installing the Process Mining Suite

One code base, five surfaces, two ways to run it: natively with ./run.sh or as a container with Docker Compose. This guide takes a fresh machine to a running, signed-in suite — and tells you where your data lives.

Both variants run the same services and keep their state in the same data directory — the choice is purely operational. Native gives you direct control and hot-reload development; Docker gives you an isolated, restartable deployment where host ports default to +10000 (app on 18080 instead of 8080) — and any free host port can be mapped instead.
1

What you are installing

The suite is one code base with five surfaces, each on its own port. A single start command brings them all up — whichever variant you choose:

SurfaceWhoNative (run.sh)Docker host port
Main applicationall users8080 / 844318080 / 18443
Admin interfaceadministrators8090 / 845318090 / 18453
Integration consolepower / dev / admin8100 / 846318100 / 18463
Actions surfacedev / admin8110 / 847318110 / 18473
Compute backendinternal only8000 (loopback, TLS)inside the container

Second port of each pair = HTTPS, active once TLS is enabled in the admin. The Docker column shows the defaults — host ports mapped at +10000 so they don't clash with local services; any free host port can be mapped instead (see Variant B). The compute backend is never exposed to the browser — the GUI server proxies to it.

Which variant? run.sh for development or a machine you manage directly; Docker Compose for a self-contained, restartable deployment with one folder of persistent state.

3

Variant A — native, with run.sh

Three commands from a fresh checkout: create the Python environment, build the frontend once, start everything.

# 1. Python environment + backend dependencies (python3.14 works too)
python3.13 -m venv .venv
.venv/bin/pip install -r requirements.txt

# 2. Build the frontend SPA (installs npm dependencies on first run)
./run.sh --build

# 3. Start the suite — backend, GUI, admin, integration, actions
./run.sh

run.sh starts all five services and stops them together on Ctrl-C. On the next start the SPA is only rebuilt if missing.

  • App → http://127.0.0.1:8080 · Admin → http://127.0.0.1:8090 · Integration → http://127.0.0.1:8100
  • Frontend development with hot reload: ./run.sh --dev (backend + admin + Vite dev server on :5173).
  • Optional test dependencies: .venv/bin/pip install -r requirements-dev.txt.
Custom ports. Override with environment variables before starting: PMW_FRONTEND_PORT, PMW_ADMIN_PORT, PMW_BACKEND_PORT, PMW_INTEGRATION_PORT, PMW_ACTIONS_PORT (and the matching …_HTTPS_PORT variants).
4

Variant B — Docker Compose

One command builds the image (SPA in a Node stage, Python services in a slim runtime) and starts the container with all surfaces:

# optional but recommended BEFORE the first start:
#   edit docker-compose.yml and set the bootstrap admin password
#   PMW_DEFAULT_ADMIN_PASSWORD: "your-strong-password"

docker compose up -d --build

App → http://localhost:18080 · Admin → http://localhost:18090 · Integration → http://localhost:18100 · Actions → http://localhost:18110 (host ports are the container ports +10000).

  • The container runs the same run.sh under tini and restarts automatically (restart: unless-stopped).
  • The bootstrap password env applies only while the security database is empty — set it before the very first up.
  • Auto-rebuild during development: docker compose watch (or up --watch) rebuilds the image when sources change; Docker's layer cache keeps unchanged parts free.
Pick your own ports. The +10000 mapping is only the default. Map any free host port to the container ports by editing the ports: entries in docker-compose.yml — the left-hand side is the host port, e.g. "80:8080" serves the app on plain port 80. The container ports on the right stay as they are. One caveat: never map to host port 10080 — browsers block it as a restricted port.
5

First sign-in

Open the admin interface first. A fresh installation bootstraps one administrator account:

username:  Administrator
password:  Administrator          (unless overridden via
                                   PMW_DEFAULT_ADMIN_USER / _PASSWORD)

Change this password immediately — admin → Users. Then create your users, define database connections (admin → Connections) and assign them; users sign in to the main app with their own accounts.

  • A Demo Mode banner on the sign-in panel means no license is installed yet — the suite runs with the demo allowance until a license file is uploaded in the admin's App Control section.
  • The Integration console and Actions surface are role-gated (and Actions stays disabled until an admin switches it on in the Actions tab).
6

Where your data lives

Everything the suite must keep is written to one directory — the same layout in both variants:

native:  ./data                (override with PMW_DATA_DIR)
docker:  ./data  ⇄  /app/data  (bind mount in docker-compose.yml)

data/
  settings.sqlite3    per-user app settings
  security.sqlite3    users, roles, connections, norms, licenses
  logs.sqlite3        backend / admin logs
  secret.key          encryption key for stored secrets
  certs/              TLS certificates managed in the admin

Back up the data directory and you have backed up the installation — users, connections, certificates and settings. (Scheduled backups can also be configured in the admin.)

Keep secret.key with its databases. Stored secrets (connection passwords, LLM keys) are encrypted with it — a database restored without its matching key cannot decrypt them.
7

Enabling HTTPS

Both variants start on plain HTTP. TLS is switched on centrally in the admin interface (TLS tab): upload or generate a certificate, choose the TLS mode, and every surface follows the same plan — the HTTPS ports (8443/8453/8463/8473, or their +2000 Docker mappings) become active, no restart of individual services needed.

  • The internal GUI → backend hop is always TLS-encrypted with an internal self-signed certificate, independent of the public-facing mode.
  • The admin, integration and actions surfaces follow the same TLS mode and active certificate as the main app.
8

Updating

Updates are the install commands again — state in data/ is untouched:

# native
git pull
.venv/bin/pip install -r requirements.txt   # in case dependencies changed
./run.sh --build                            # rebuild the SPA
./run.sh

# docker
git pull
docker compose up -d --build                # rebuilds only changed layers

Good to know

  • The browser only ever talks to the GUI server — the compute backend can even run on a separate host close to the database (PMW_BACKEND_URL).
  • Useful env vars: PMW_DATA_DIR, PMW_QUERY_TIMEOUT, PMW_DEFAULT_ADMIN_USER / PMW_DEFAULT_ADMIN_PASSWORD, and the port overrides listed in Variant A.
  • Uninstalling is deleting the checkout (and the container/image for Docker) — all state is in data/, nothing is installed system-wide.

Rule of thumb: if you can type docker compose up -d --build, the Docker variant is the fastest path from zero to a running suite.
