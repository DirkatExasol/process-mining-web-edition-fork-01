The Integration Console

Bring event data into a connection: a pluggable extractor reads a file, applies a parsing recipe you define once, and writes process-mining rows straight into the database. This is the overview — the three format how-tos follow (31 / 32 / 33).

The Integration Console is a separate, role-gated surface for loading logs into a connection's schema. You define a source type (how to parse a file) and a source (which file), then run an import — the extractor normalises the timestamp, hashes the case id and writes one JOURNEYS row per event.
1

A separate surface for loading data

The Integration Console is where you bring event data in. It runs on its own port (the admin port + 10 — 8100 HTTP, 8463 HTTPS) and reuses the app's sign-in and TLS. It is for developers and administrators only; an admin can disable it entirely under Admin → Integration.

🧩 Integration Console · :8100 / :8463 — developers & admins · same sign-in & TLS as the app
2

The abstraction layer

At its heart is a pluggable extractor: it reads a source (today, a file), applies your parsing recipe, and writes the parsed events straight into the schema of a connection — creating the process-mining tables as needed.

📄 Source file→ Extractor→ Connection schema · JOURNEYS

One hub in the middle; supporting a new kind of source is a matter of adding an extractor behind it.

3

Two things you define

Before importing you set up two reusable pieces — both live in the left panel alongside Connections:

Source type
A parsing recipe for one file format: an example record plus the selectors that pull out the timestamp, case id, step and up to three metas — regular expressions for Text, or JSON / XML paths for semi-structured files.
Source
A concrete thing to import — a File (a path + encoding) linked to a source type.
  • The left panel mirrors the app: Connections, Sources and Source types, plus the theme selector and your account.
  • Connections can be created and edited here (＋ / ✎) — no need to switch to the main app to set up the database you're importing into.

The five roles every record maps to

However a file is parsed, each record maps to the same fields — this is what turns a raw log into a process:

RoleWhat it is
EVENT_TIMEthe timestamp — analysed and normalised to YYYY-MM-DD HH:MM:SS
EVENT_IDthe case / journey key — stored MD5-hashed, so a raw login or user id never lands in the clear
STEPthe activity name for the event
Metas ×3up to three extra attributes, each given a business name shown in the app
Helpera value used only by compound-step rules; extracted but written to no column
5

Run an import

Press ▷ on a source, pick the destination connection and project. The extractor reads the file, normalises the timestamp, hashes the id and writes one JOURNEYS row per event — creating the PROJECTS row, a STEPS definition per distinct step, and the META titles as needed (existing rows are never overwritten).

Importing…

Delta upload is on by default: a checkpoint remembers how far the file was read, so pressing ▷ again tops the project up with only the new lines instead of duplicating. “Nothing new” is a normal result, not an error.

Which format? Text (unstructured logs), JSON and XML each have their own how-to — guides 31, 32 and 33.

Good to know

  • Sandboxed reads. Only files under the server's integration files directory can be read; paths escaping it (via “..” or symlinks) are rejected. An operator can opt out with PMW_INTEGRATION_ALLOW_ANY_PATH=1 for trusted deployments.
  • Compound steps. Split one activity into several by another field (e.g. a login that returned HTTP 200 vs 500) — covered in the format guides.
  • The watchdog. A file source can be polled automatically; it shares the same checkpoint as a manual run, so neither imports a line twice.
  • Everything is logged. Each import is recorded (DATA + USER tags) — successes at USAGE, failures at WARN/ERROR with the reason.

The console turns any timestamped log into process-mining rows — define the recipe once, then import (or auto-import) as often as you like.
