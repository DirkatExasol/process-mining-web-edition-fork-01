15 Administration: Logging, Backup and Customisation

This chapter covers the last four tabs of the admin interface: Logging, Backup, Customize and Integration. Between them they answer four separate operational questions — what the product recorded and how you read it back, what survives a rebuild of the machine and how you restore it, what the sign-in pages look like, and whether the integration console exists at all. Everything described here lives on the admin interface (http://<host>:8090 or https://<host>:8453) and everything here requires an administrator account.

Requires: Administrator — every tab, control and procedure in this chapter.

The log: one file, three writers

There is exactly one structured log. The main application, the admin interface and the integration console all write into it, so a single view shows a user's sign-in, the SQL the backend then ran on their behalf, and the certificate an administrator activated an hour earlier. The Logging tab is the reader for that file: it configures what gets recorded, filters what you see, and exports or clears what has accumulated.

All timestamps in the viewer, in the row popup and in downloaded log files are rendered in the display timezone set under App Control → Timezone. Changing that setting re-renders every timestamp immediately; it does not rewrite the stored entries and it needs no restart.

The severity ladder

Severities are not ranked by urgency in this product. They form a ladder — INFO → USAGE → WARN → ERROR → DEBUG — and the Max level logged setting is cumulative from the top: choosing a level records that severity and every level before it. This is why DEBUG, which would be the quietest level in many products, is the loudest one here.

Warning DEBUG records every SQL statement the backend issues. On a busy installation this fills the live log quickly, and because only the newest ten archive files are kept, a long DEBUG session can push older history out of the archive altogether. Switch to DEBUG for a specific investigation and switch back afterwards.

Setting the level and the rotation size

  1. Open the Logging tab.
  2. In the configuration banner, choose a value in Max level logged. The caption restates the rule: records this severity and everything above it in the ladder.
  3. Set New file after [N] MB — the size at which the live log rotates. Accepted range is 1 to 1000 MB; the default is 5 MB. The server additionally enforces a 50 KB floor internally, so a rotation can never be triggered by a nearly empty file.
  4. Click Save. The toast “Logging config saved” confirms it. The change applies to what is written from that moment on; it does not retroactively add or remove entries.

Tags, and how they differ from operations

Every entry carries an operation (what part of the product wrote it) and, optionally, a tag. Tags are cross-cutting labels: they are independent of both severity and operation, and they exist so that you can pull one kind of activity out of a mixed log with a single click.

DATA
Data-load events.
SQL
SQL traces. These belong to the DEBUG rung of the ladder, so they only appear when Max level logged is DEBUG.
BACKUP/RESTORE
Every backup and restore action — exports, server-side runs, inspections, restores and their failures.

The All tags dropdown is populated from the tags actually present in the current log, so a tag that has never been written does not appear as an option. Untagged entries show — in the Tag column.

Reading and filtering the log

The filter row sits between the configuration banner and the table. All filters apply to the whole log, not just the page on screen, and any change to a filter returns you to page 1.

The table shows Date, Time, Severity (colour pill: INFO blue, USAGE green, WARN orange, ERROR red, DEBUG grey), Tag, Client IP, User and Message. Every row is exactly one line and long messages are ellipsised, so the table stays readable at a glance.

  1. Click any row to open the Log entry popup with the complete entry: Date, Time, Severity, Client IP, User, Operation, Tag and the full message.
  2. For an sql entry the statement is pretty-printed in the popup, and its execution time — parsed from the SQL (12.3 ms): prefix of the message — is shown as a separate Execution time field.
  3. Press Esc or click Close to dismiss the popup.

Paging controls sit below the table: Per page offers 10, 25 (default), 50 and 100, with « First, ‹ Prev, Next › and Last », a “start–end of total” readout and “Page X / Y”. When nothing matches, the table shows “No matching log entries.” and the pager reads “No entries”. ↻ Refresh re-reads the log without clearing your filters.

Exporting a filtered view

  1. Set the severity chips, operation, tag, client IP and search text so the table shows exactly the entries you want.
  2. Click ↓ Download. The browser saves the currently filtered view as pmw-log.log, up to a maximum of 5000 entries.
Tip Because the export follows the filter, the fastest way to hand a specific incident to support is to search for the message text or filter by client IP first, then download. Timestamps in the exported file use the configured display timezone, so state that timezone when you send the file on.

Rotation, archives and clearing

When the live log passes the configured size it is rotated out to data/logs/pmw-<timestamp>.log. Only the newest ten archive files are kept; older ones are deleted. Archives are plain files on the server — copy them off the machine if you need history beyond that window, and include data/logs/ in your filesystem-level backups, because the product's own backup file does not contain the log.

  1. Click Clear (danger) in the filter row.
  2. Confirm the dialogue: “Clear the live log? — This empties the current log (rotated archive files are kept).”
  3. The live log is emptied. The clearing action is itself written into the now-empty log at WARN, so the record of who cleared it survives.

What the log never contains

Log entries name the action, the actor and the affected object — never the secret involved. This is deliberate, and it is worth knowing precisely, because it defines what a leaked log can and cannot expose:

  • Passwords are never written. A password change is recorded as “changed their password — other sessions invalidated”.
  • Database passwords, LLM API keys and directory bind passwords are not written by connection tests, LDAP tests or saves; those entries record the operation and its outcome only.
  • Rebuild tokens are shown in the browser once at generation and stored only as a hash; the log records that a token was generated or revoked, at WARN, and not its value.
  • The backup encryption password is never written. A backup export records the include-set and whether the resulting file was encrypted or PLAINTEXT — the fact, not the password.
  • Two-factor secrets are stored encrypted and recovery codes only as hashes, so neither can appear in a log message.

Backup

The Backup tab does two independent jobs: it produces backup files (on demand or on a schedule) and it restores from one. Both halves share the same include options and the same encryption password.

What a backup contains

A backup captures everything except the event data itself, as a single JSON file that is byte-compatible with the main application's own backup format. Concretely it holds:

  • database connections and their server settings;
  • filter presets;
  • happy paths;
  • target norms;
  • saved node layouts;
  • LLM prompt templates;
  • application preferences and settings.
Warning The mined data — projects, journeys, steps, metas and notes — lives in the customer database, not in the product, and is therefore not in the backup. A backup restores your configuration onto a working installation; it does not reconstruct an event log. Back the database up separately, by whatever means your database administrator uses.

Whenever secrets are included and no password is typed or stored, the card shows the inline warning “⚠ Secrets will be written in plain text unless you set an encryption password.” A standing note explains the trade-off for unattended operation: for automatic backups the password is stored encrypted on the server so the schedule can run without you.

Warning A backup can only be restored with the password it was written with. There is no recovery path. Store the password somewhere independent of the machine that holds the backups — if you lose it, every encrypted backup you hold is unreadable.

Downloading a backup

  1. Open the Backup tab and set the three include checkboxes as required.
  2. Type an Encryption password, or leave the field blank to reuse the password already stored on the server.
  3. Click ↓ Download backup. The file is saved as ProcessMining-Backup-YYYY-MM-DD.json.
Note A blank password field is not the same as “no encryption”. If an automatic-backup password is stored, downloads silently reuse it and are encrypted too. To produce a genuinely unencrypted file you must have no stored password at all.

Running a backup on the server

  1. Set the include options and, if needed, the password.
  2. Click Run backup on server now.
  3. The file is written into data/backups/ immediately, using the typed password or the stored one, and the toast reports “Backup written on server: <file>”.

If neither a typed nor a stored password exists, the run fails with “Set a backup password first.” Manual server-side runs appear in the status line marked “· manual”.

Automatic backups

Automatic backups are written on a schedule while the admin server is running, saved under data/backups/, with older files pruned beyond the retention count.

  1. Set an Encryption password and save it — enabling the schedule without one is refused with HTTP 400 “Set a backup password before enabling automatic backups.”
  2. Tick Enable automatic backups.
  3. Choose a Frequency and fill in the fields it reveals (see the table below).
  4. Check the live line — “Runs: <cron> — <human summary>”, for example “Every day at 02:00” — to confirm the schedule reads as you intended.
  5. Set Keep newest backups: the retention count, minimum 1, default 30.
  6. Click Save schedule. The toast “Backup schedule saved” confirms it; an unparsable cron expression is rejected with 400 “Invalid schedule: <reason>”.

The status line under the schedule reports one of: “Last backup: <when> — <file> (N KB)”, a red “Last attempt failed: <error> — <when>”, or “No backup has run yet.”

Note — how the scheduler actually runs The scheduler lives inside the admin server process. If the admin interface is stopped, no automatic backups are written, and none are caught up afterwards. It wakes every 15 seconds and fires at most once per minute when the cron expression matches the wall clock of the display timezone configured under App Control — so “daily at 02:00” means 02:00 in that timezone, and changing the timezone moves the schedule. Files are named pmw-backup-YYYYMMDD-HHMMSS-<microseconds>.json; retention pruning deletes the oldest files beyond the keep-count. A scheduled tick that finds no stored password records the failure “No backup password is set.”

Restoring from a backup

Restore is a three-stage flow: load the file, review what it holds, then choose what to apply. The intro states the consequence plainly — this overwrites the corresponding settings.

  1. In the Restore card, choose a file with Backup file (.json). It is inspected automatically as soon as it is selected.
  2. If the file is encrypted, type its password into Password (if the backup is encrypted) and click Inspect again.
  3. Read the Backup contents summary: Created, Connections: N, Projects with settings: N, an Includes line (usernames or —, passwords or “no passwords”, API keys or “no API keys”) and — most importantly — Overwrites: the names of the connections that will be replaced.
  4. Untick anything you do not want applied. The options, all checked by default, are: App settings & preferences, Connections & servers, Usernames, LLM API keys, Database passwords, Saved node layouts, Target norms, Happy paths, Filter presets.
  5. Click Restore (danger) and confirm: “Restore the selected items from this backup? — This overwrites the current settings.” The toast “Backup restored” confirms completion.
Warning Read the Overwrites: line before you restore. Those checkboxes are the only granularity available — you cannot restore a single connection, or merge one backup's presets into another's. A connection named in that line is replaced wholesale by the version in the file.

Customize: the login-page background

The Customize tab holds branding and appearance settings for the application and the admin interface; its header notes that more options are to come. Today it contains one section, Login Page, which sets the background for both sign-in pages — the main application's and the admin interface's — from a single choice.

OptionWhat it does
Default theme colour (default)Keeps the built-in theme colour, which follows the viewer's light / dark mode.
Solid colourReveals a colour picker and a hex field that stay in sync. The server validates the value: “Color must be a #rrggbb hex value”.
Background imageReveals a file input accepting PNG, JPEG, GIF, WebP or SVG — or you can drag an image straight onto the preview.
  1. Open the Customize tab and select one of the three radio options.
  2. For Solid colour, pick a colour or type a #rrggbb value.
  3. For Background image, choose a file or drag one onto the preview. The toast “Image ready — click Save to store it” confirms the image has been prepared.
  4. Check the Preview box, which renders a mock Sign in panel over your chosen background.
  5. Click Save. The result line reads “Saved — new sign-ins use it immediately.” and a toast confirms “Login background saved”. No restart is needed; the next render of either sign-in page picks it up.

Images are processed in the browser before upload. A file over 30 MB is rejected outright (“Image file is too large (max 30 MB)”). Raster images are scaled to a 2560 px long edge and re-encoded as WebP, with JPEG as a fallback, so an ordinary photograph fits comfortably. SVG is kept exactly as supplied and may therefore be animated. The stored image is capped server-side at roughly 3 MB (“Image is too large (max ~3 MB)”). Other validation messages are “Choose a background image first” and “Choose a valid background image first”.

Note Over a background image the sign-in panel becomes 50 % translucent so the picture shows through. A solid colour or the default theme colour keeps the panel opaque. Check legibility in the preview before saving — a busy photograph can make the username and password fields hard to read.

Background changes are logged under operation customize, naming the new background as “a solid colour (#…)”, “an uploaded background image” or “the default theme colour”.

Integration: turning the console on and off

The Integration tab is the master switch for the integration console — the fourth surface, used to configure data sources. This tab decides whether that surface exists; what you do inside it is covered in its own chapter.

The card describes the console as a separate surface for configuring data sources, reachable only by power users, developers and administrators, and points you to the Users tab to grant the Developer role per user.

  1. Open the Integration tab.
  2. Tick or untick Enable the integration console. The toast reads “Integration console enabled — restart to apply” or “Integration console disabled — restart to apply”.
  3. Go to the App Control tab and click ↻ Restart app server. Until you do, the setting is stored but has no effect.
  4. Return to the Integration tab and check the status pill — launcher running or launcher not detected — and the endpoints listed beneath it.

The status area lists the console's addresses: HTTP http://<host>:8100 and HTTPS https://<host>:8463, the latter only when the TLS mode is Optional or Required. Both default to the admin ports plus ten and can be overridden by environment variables. The console follows the same TLS mode and shares the same active certificate as the application and the admin interface; both are changed in the TLS / SSL tab.

Warning — the restart fan-out There is only one restart button, and it restarts three things: the application, then the integration console, then the admin interface itself. Anyone using the application is briefly disconnected. Because the admin interface restarts too, this page may stop responding mid-request — and if you also changed the TLS mode, the admin interface moves between http://<host>:8090 and https://<host>:8453, so you must reconnect on the new address. The launcher status pill is best-effort: “launcher not detected” immediately after a restart may simply mean the process has not written its PID file yet.
Tip Group your changes. TLS mode, certificate activation and the integration on/off switch all wait for the same restart, so make all of them first and restart once, rather than restarting after each.
