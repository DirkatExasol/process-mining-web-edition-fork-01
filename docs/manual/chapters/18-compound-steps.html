18 Compound Steps

A log line rarely names the activity you want to see in the process map. It names half of it — the endpoint, the command, the message code — and leaves the other half in a second field: a status code, a result flag, a return value. Compound steps are the mechanism that joins those halves back together at import time, so that the event stored in JOURNEYS.STEP reads “login successful” rather than “login”. This chapter explains why compound steps exist, how to write and test rules in the source type wizard, exactly how the rules are evaluated when a source runs, how helper fields keep your three META columns free, and which mistakes cost people the most time. It is written for the person who defines source types in the integration console.

Requires: Developer or Administrator. Compound steps are edited inside the source type wizard on the integration console (HTTP :8100, HTTPS :8463). Power users and plain users cannot sign in to that surface, and every /api/integration/* endpoint refuses them with “You need the Developer role to use the integration features.”

18.1 Why compound steps exist

Consider a single line from an Apache access log:

10.0.0.7 - - [03/Aug/2026:14:05:09 +0000] "POST /shop/login HTTP/1.1" 200 512 sess=abc-123

A regex over the request path extracts the step login. So does the next line — the one whose status code is 500. Both events land in the process map as the same activity, and the map can no longer tell a successful sign-in from a failed one. The information is present in the line; it is simply in a different field.

Compound steps close that gap. A source type may carry an ordered list of rules. Each rule names a resulting step and one or more conditions over the fields the source type extracts. When every condition of a rule holds for a line, that rule's step text replaces the step the plain step field captured. When no rule matches, the plain step value is used unchanged — compound rules are strictly additive, never destructive.

The second half of the mechanism is the helper field. The status code in the example above is needed only to decide the step name; it has no business meaning and does not deserve one of the three META columns that carry business attributes such as an order number or a customer segment. A helper field (internally the role aux) is extracted from every line like any other field and offered to the rules by name, but it is written to no database column at all. The wizard states this in the explainer shown when a Step tab has no rules yet:

Note “Build the step from more than one field when the log splits it — e.g. step ‘login’ plus status ‘200’ becomes ‘login successful’. Values needed only for matching can be extracted as helper fields, which are never written to the database, so your META columns stay free for business attributes.”

18.2 Where the rules live

Compound rules belong to a source type, not to a source. They are stored with the source type's name, its pasted sample line and its field list, and they are owned per user. Every source that links to that source type is parsed with those rules, so editing a rule changes the behaviour of every future import through that source type — manual runs and watchdog imports alike.

The editor is the Step tab of step 2 (“Field mapping”) of the source type wizard. Compound rules appear there and nowhere else, because a rule always produces a STEP value; there is no equivalent for timestamps, ids or meta fields.

18.3 The Compound steps panel

Inside the Step tab, below the plain step field, sits a section headed Compound steps with the caption “optional”, a rule count in parentheses once at least one rule exists, and a ＋ Add rule button.

Rules render as badges in a scrolling list. Roughly three badges are visible at a time (each is at least 52 px high, the list is capped at 190 px); beyond that the list scrolls. Each badge shows:

Clicking anywhere else on a badge opens the rule editor.

Under the list the wizard evaluates the whole rule set against the sample line and reports the outcome in one line: green “✓ For the sample line the step becomes ‘<step>’.” when some rule matches, or grey “• No rule matches the sample line — the plain STEP value would be used.” when none does. The second message is not an error; it is the normal reading for a sample line that happens to be an ordinary event.

Tip The preview in the wizard runs the same comparison logic as the backend evaluator, including case handling and trimming. If the badge shows a green tick against your sample line, the same line in the real file will be relabelled the same way.

18.4 The rule editor

Clicking a badge — or ＋ Add rule — opens a nested sheet titled Compound step rule with the icon ⚗. Edits take effect immediately; the Done button in the footer simply closes the sheet. Beside it the footer shows a live verdict against the sample line: “✓ matches the sample line” or “• does not match the sample line”.

18.4.2 Adding a rule

  1. Open the source type wizard (click a badge in the Source types section, or ＋ to create one) and go to step 2, Field mapping.
  2. Select the Step tab. Make sure a plain step field exists and its match line reads “✓ matches: <value>” against your sample.
  3. In the Compound steps section click ＋ Add rule. The rule editor opens with two conditions, the first already pointing at the step field.
  4. Type the resulting activity name into Step becomes, for example login successful.
  5. Complete the first condition: leave the field as the step field, choose the operator is and type the plain step value, for example login.
  6. For the second condition pick the field that carries the other half of the activity — a helper field such as status — choose an operator, and type the value. Use the = <captured value> hint beside the input to see exactly what the field captures from your sample.
  7. Check the footer verdict. If your sample line is one this rule should relabel, it must read “✓ matches the sample line”.
  8. Click Done, then repeat for the remaining variants. Verify the order numbers on the badges.
  9. Go to step 3 and click Create source type / Save changes.
Note Only complete rules survive the save. A rule needs non-blank text in Step becomes and at least one condition that names a field; conditions with no field selected are dropped, and a rule left with none is discarded entirely. This is deliberate: a half-built rule abandoned in the wizard can never silently relabel events at import time.

18.5 Conditions and operators

A condition is a triple: a field name, an operator, and a value. The field is referenced by name, which is why renaming a field is safe (see 18.7) and deleting one is not.

On screenStored idHolds when…
iseqThe captured value equals the condition value.
is notneThe captured value differs from the condition value.
containscontainsThe condition value occurs anywhere in the captured value.
starts withstartswithThe captured value begins with the condition value.
ends withendswithThe captured value ends with the condition value.
matches regexregexThe condition value, read as a regular expression, is found anywhere in the captured value.

Four properties of the evaluation matter in practice:

All conditions must hold
The conditions of one rule are combined with AND. There is no OR: express alternatives as two rules with the same resulting step. A rule with no valid condition never matches at all.
Case-insensitive and trimmed
Every operator except regex compares case-insensitively, and both sides are trimmed of surrounding whitespace first. Log casing is rarely dependable, so is “OK” matches a captured “ok ”. When case really matters, use matches regex, which is the exact-comparison escape hatch.
A missing value makes the condition false
If the field's regex captured nothing on that line, every condition on it is false — including is not. “Missing” is not treated as “different”. To catch lines where a field is absent you must find something else to test.
An unusable regex simply never matches
A matches regex value that is not a valid pattern makes the condition false rather than failing the import. The same is true of a field whose extraction regex does not compile.

18.6 Helper fields

Helper fields carry the role aux. They are extracted from every line exactly like a meta field — same regex convention, capture group 1 if the pattern has groups, otherwise the whole match, searched anywhere in the line — but they are written to no column. Only the first three meta fields map to META_1…META_3; anything you extract purely for matching should therefore be a helper, not a meta, or you will spend a business column on an HTTP status code.

Helpers are rendered in teal. New ones are named helper_1, helper_2, … (skipping names already taken); the name input carries the tooltip “Compound rules reference a helper by this name”.

You can create a helper in two places: on the Helper role tab of step 2 like any other field, or — more conveniently — from inside the rule editor.

  1. In the rule editor, find the Add a helper field panel.
  2. Type a name into the first input (placeholder “name, e.g. status”).
  3. Type the extraction pattern into the second input (placeholder “regex with one capture group”). Watch the live feedback: green “✓ captures ‘<value>’ from the sample”, orange “⚠ invalid regex”, or “• no match in the sample line”.
  4. Click Add (disabled until both inputs are filled). The helper is created as an aux field of the source type and is immediately pointed at by the first empty condition — or, if every condition already has a field, by a newly appended one.
  5. Choose the operator and type the value for that condition.
Note The panel's own explainer states the trade: “Extract a value only needed for matching (an HTTP status, a result code). Helper fields are never written to the database, so your three META columns stay free for business attributes.”

18.7 Renaming and deleting referenced fields

Because conditions reference fields by name, the wizard protects the link in both directions.

Renaming cascades. If you rename a field that any rule references, every condition naming it is rewritten to the new name automatically. Nothing silently stops matching.

Deleting is blocked. On a field row, the ✕ remove button is replaced by an orange 🔒 lock as soon as any rule references that field. The lock is not clickable (the cursor shows “not allowed”) and its tooltip reads: “Used by N compound step rule(s) (<rule steps>). Remove the field from those rules first — deleting it now would stop them matching. Renaming is safe: the rules follow the new name.” An orange caption under the row repeats the message: “🔒 Used by N compound rule(s): <steps> — remove it there before deleting this field. Renaming is safe.” The same guard exists in the code, so no route through the interface can orphan a rule.

  1. Open the rule editor of each rule listed in the lock's tooltip.
  2. Remove the condition on the field with −, or point the condition at a different field.
  3. Close the rule editor with Done. The lock on the field row turns back into ✕.
  4. Delete the field and save the source type.

18.8 What happens at import time

Compound rules are applied while a source runs — from the Run dialog or from a watchdog poll; the two behave identically. For each non-blank line of the file, truncated to its first 2000 characters, the extractor does the following:

  1. Runs the regex of every named field of the linked source type, including helper fields. Regexes are compiled once per run; one that fails to compile is treated as never matching.
  2. Applies the mandatory gate: the line yields an event only if a case id, a step and a timestamp were all captured and the timestamp normalises successfully. Otherwise the line is skipped and counted in the Events skipped KPI.
  3. Evaluates the compound rules in order. The first rule all of whose conditions hold supplies the step text. If none matches, the plain step field's captured value is kept.
  4. Writes the row into JOURNEYS, with the derived value in STEP.
  5. After the run, creates a STEPS row for every step name seen that did not have one, with an empty description, a colour and shape chosen deterministically from the step name, SCORE 0, END_OF_PROCESS false and BELONGS_TO NULL. The run log records “created <n> new step(s): <names>”.
Warning Compound evaluation happens after the id/step/timestamp gate, not instead of it. A line whose plain step regex captures nothing produces no event at all, no matter how well a compound rule's other conditions fit. Compound rules can only relabel an event that would have been written anyway.

Because the derived step is an ordinary step name from the database's point of view, it takes part in everything downstream: it becomes a node in the process map, it gets its own colour and shape in STEPS, and it can be scored, described and grouped like any other activity.

18.8.1 The regex timeout guard

Every regex the extractor runs — field extractions and matches regex conditions alike — is executed under a 0.25-second wall-clock timeout per match, provided the third-party regex module is installed in the backend environment. The reason is blunt: CPython's standard re engine does not release the interpreter lock while matching, so a catastrophically backtracking pattern on a hostile line would freeze the entire compute backend — including the watchdog loop and every other user's request — until it finished.

The consequences are asymmetric and worth remembering:

Where the timeout hitsResult
A field extraction regexThe line counts as unparseable and is skipped. It shows up in the run detail (“… n skipped”) and in the Events skipped KPI, which turns orange above zero.
A matches regex conditionThe condition evaluates to false. The rule does not match, evaluation continues with the next rule, and the event is still written — with the plain step, or a later rule's step.
Warning Without the regex module the backend falls back to the standard library and no timeout applies. A pathological pattern then runs to completion. Keep expressions simple, avoid nested quantifiers such as (\w+)+, and prefer anchored literal context over open-ended wildcards.

The source is an Apache-style access log with a session id appended. The sample line pasted on step 1 of the wizard is the first of these:

18.9.4 Checking the outcome before you save

Steps 2 and 3 of the wizard show a one-row table labelled Example JOURNEYS record, built from the sample line with the current specification. Watch the STEP column: when a compound rule wins, the cell shows the derived text and the column note reads compound. The EVENT_ID cell shows the original captured id with the note “original — stored as MD5”, and EVENT_TIME shows the normalised timestamp. Step 3 also lists a Compound steps summary in the compact form <step> ← field is "value" and …, which is the fastest way to read the whole rule set at a glance before saving.

18.11 Common mistakes

Writing the general rule before the specific one
The first fully-matching rule wins, so a broad rule placed early shadows every narrower rule after it. Put the most specific rules first and read the badge order numbers before saving.
Omitting the step condition
A rule that says only “status starts with 5” relabels every 5xx line as, say, “login failed” — searches, checkouts and all. Nearly every rule should pin the plain step field as well.
Expecting a rule to rescue a line that produced no event
If the id, step or timestamp regex fails, the line is skipped before rules are considered. A large Events skipped count with no compound effect points at the field regexes, not at the rules.
Expecting is not to fire on a missing value
A condition on a field that captured nothing is false for every operator. If a status code is absent from some lines, “status is not 200” will not match them.
Relying on case
All operators except matches regex compare case-insensitively after trimming, so “GET”, “get” and “ Get ” are the same value. If you genuinely need case-sensitive matching, use matches regex.
Using a meta field for a matching-only value
Only the first three meta fields are written, to META_1…META_3; a fourth is silently ignored. Extract status codes, result flags and the like as helper fields so the META columns stay available for business attributes.
Leaving a rule half-finished
A rule with no step text, or with no condition that names a field, is dropped on save without warning. If a rule disappears after saving, it was incomplete.
Targeting content past character 2000
Every line is truncated to its first 2000 characters before extraction. A regex aimed at a field beyond that point never matches, and the condition that uses it is always false.
Typos in the resulting step name
Step names are written verbatim and auto-create STEPS rows. “login successful” and “Login Successful” become two separate activities in the process map. Keep a consistent naming convention across all rules of a source type.
Expecting rules to change events already imported
Rules are applied at import time only. Editing them has no effect on rows already in JOURNEYS. To relabel a historical import you must delete the project in the destination schema, reset the source's checkpoint, and import the file again from the top — resetting a checkpoint on its own deletes nothing from the database and would simply append everything a second time.
Deleting a source type that sources still use
Deletion does not cascade. A source whose source type has gone keeps a dangling link, its Run button warns “This source has no source type linked”, and the watchdog records the checkpoint error “The source has no source type linked.” Pick a replacement source type on the source before running it again.
Tip After changing rules, run the source once against a scratch project id with delta upload switched off, and inspect the process map. New or missing activity names show up immediately, and the run log line “created <n> new step(s): <names>” tells you exactly which step names your rules produced.
