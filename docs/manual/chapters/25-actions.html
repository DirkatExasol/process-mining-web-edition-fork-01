25 Actions

An action is a small, business-readable query you attach to process-map nodes. From a node’s menu you can show the last log entries from that step, from the steps around it, or a transition table for everything that follows — and the result always honours whatever filters you currently have set on the chart. Actions are written in a tiny script language that the system translates into database SQL for you. This chapter explains how the feature is turned on, how to author actions on the Actions surface, the script language and its clauses, how availability decides where an action appears, and how an action runs from the app.

Requires: Administrator to enable the feature; Developer (or Administrator) to author actions; and any signed-in user except a plain standard user (that is, Power, Developer or Administrator) to run them from the app. The feature is off until an administrator enables it.

25.1 Enabling the feature

Actions are opt-in. In the admin interface open the Actions tab and tick Enable Actions, then restart the app server from App Control so the surface binds its listeners. While the feature is off, the Actions surface serves a “disabled” page and the app shows no Actions entry in node menus.

The Actions authoring surface runs on its own port — by default HTTP :8110 and HTTPS :8473 — and follows the same TLS mode and certificate as the app and admin interface. Only developers and administrators may sign in to it.

25.2 Authoring actions

Open the Actions surface, sign in, then pick a connection and a project at the top. Actions are saved per connection and project, so a service provider hosting several customers keeps each customer’s actions separate. The builder then shows the saved actions for that project on the left and an editor on the right.

As you type, the editor validates the script live, restates it in plain English, and shows the exact SQL it will run. The Test panel runs the script against a node you choose (standing in for THIS) so you can see real rows before saving. Save stores the action; Delete removes it.

25.3 The script language

An action is a handful of clauses. Keywords are case-insensitive, and NODE/NODES and ENTRY/ENTRIES are interchangeable. A clause keyword may sit on its own line with its value on the following line(s), or share a line with its value.

ClauseMeaning
AVAILABILITYWhere the action appears in node menus: ALL NODES, or a comma-separated list of step names (e.g. LOGIN, LOGOUT, PAYMENT).
SHOWWhat to display: LAST [N] LOG ENTRIES (N defaults to 1), or TRANSITION TABLE WITH … listing one or more metrics (see below).
FROMNODE(…) relative to the clicked node: THIS, PREVIOUS, FOLLOWING, ALL FOLLOWING, ALL PREVIOUS — combine them, e.g. NODE(THIS, ALL FOLLOWING).
SORTOptional. ASCENDING or DESCENDING (log entries by time; the default is most recent first).
WHEREOptional filter. This version supports EVENT_ID :: [id, id, …] (the :: reads as “is one of”).

A minimal example — show the single most recent event of the clicked node:

AVAILABILITY
    PAYMENT
SHOW
    LAST 1 LOG ENTRY
FROM
    NODE(THIS)
SORT
    DESCENDING

A transition table can list any of the chart’s metrics, in any combination, as quoted names after WITH: "COUNT", "%JOURNEY%" (share of all filtered journeys traversing the edge), "%OUTGOING%" (branching share of the source node’s outgoing journeys), and the transition-time metrics "AVG TIME", "MIN TIME", "MAX TIME" and "STD DEV" (in seconds). Friendly short forms are accepted too — e.g. AVG, MIN, MAX, STDDEV, PERCENTAGE, JOURNEY %. Each metric becomes a column, in the order you list them. As a shorthand, TRANSITION TABLE WITH ALL METRICS includes every metric at once.

A transition table for the clicked node and everything downstream, over the most recent activity:

AVAILABILITY
    ALL NODES
SHOW
    TRANSITION TABLE WITH "COUNT", "%JOURNEY%"
    FOR LAST 50 LOG ENTRIES
FROM
    NODE(THIS, ALL FOLLOWING)

25.4 Availability — where an action appears

The AVAILABILITY clause decides which nodes list the action. ALL NODES makes it appear on every node; a list of step names limits it to those steps. When you right-click a node in the process map, only the actions whose availability matches that node show up in the Actions section of its menu.

25.5 Running an action

In the process map, click a node and choose the action from the Actions section of its menu. The system resolves the FROM selectors against the live graph (so PREVIOUS, FOLLOWING and their transitive ALL forms become concrete steps), runs the query, and shows the result — a log-entry table or a transition table — over the map.

Actions always respect the chart’s current filters — the date range, included and excluded steps, the meta filters, the step-count / journey-time / score ranges and the sample set. The same action therefore answers a different question as you narrow the view, which is the point: it reads the situation you are looking at rather than the whole database.

25.6 Limits of this version

The WHERE clause supports an EVENT_ID list only; richer conditions are not yet available. On a transition table, a FOR LAST N LOG ENTRIES qualifier is applied as an approximate recency cap rather than an exact windowing. Log-entry results are capped to a safe maximum number of rows.
