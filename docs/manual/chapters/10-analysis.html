10 Analysis: Statistics, Conformance, Happy Path and Simulation

The charts in the previous chapters show you what the process looks like. The four views in this chapter tell you what it means: Statistics enumerates and ranks every route your journeys actually take, Happy Path lets you record the route they were supposed to take and scores reality against it, Conformance Check compares individual transitions against numeric target values ("norms"), and Simulation generates synthetic journeys from the observed process so you can test a hypothesis without touching the database. Statistics is available to every user; Happy Path, Conformance Check and Simulation are reserved for power users and administrators and are hidden from the view menu of plain users.

Statistics

Statistics answers three questions: which routes do journeys take, how many journeys take each route, and how are duration and traffic distributed across the process. It is reached from the ☰ (Switch view) menu as 📊 Statistics.

Note Statistics does not have its own filter state. It always uses the same filters as Chart A, and the view says so in an information line: "ⓘ Statistics use the same filters as Chart A." To change what Statistics reports on, change the A-Chart filters in the sidebar. This is the one exception to the rule that each view mode remembers its own filter state.

Loading routes

Route computation runs once per project automatically the first time you open the view. Afterwards you reload it explicitly.

  1. Select a project in the sidebar and set the filters you want on the A-Chart.
  2. Switch to Statistics. If routes have never been computed for this project, the empty state ⑂ No Routes Yet appears with the text "Compute all journey routes for the current filters." — press ↻ Compute Routes.
  3. While the server works, a spinner reads "Computing journey routes".
  4. When the computation fails, ⚠️ Query Failed appears with the backend message and a ↻ Retry button; a modal alert titled "Statistics Error" with Retry and Cancel is shown at the same time.

If you change any sidebar filter after the last computation, an orange banner appears above the tabs: "⚠ Filters changed since last load", with a ↻ Reload button. The figures on screen still describe the old filter set until you reload — the banner exists precisely because the numbers would otherwise be silently stale.

The standard KPI strip sits at the top of the view with its own collapse handle; the expanded/collapsed state is remembered in the setting statistics.kpiExpanded (default expanded). Without a project selected the view shows 🗺 No Project Selected.

The Analytics tab

The Analytics tab summarises the same filtered journey set from four angles.

Histogram of end-to-end journey durations. Reads "No duration data." when the filtered set carries no usable timestamps. A long right-hand tail points at a small number of stuck journeys; two separate humps usually mean two different journey types are mixed in your filter.

Happy Path

Requires: Power user or Administrator

A happy path is your intended step sequence — the route a journey should take when nothing goes wrong. You record it as an ordered list of steps (optionally with alternative branches), and the application scores how closely real journeys follow it. Happy paths are stored on the server per project and per user, so they survive a browser change and are included in backups.

Layout

The view is split in two. The left pane, headed "Actual Process" with the filtered journey count ("N journeys"), is the full process flowchart with the same node, note and drag behaviour as the A-Chart (its node layout is stored under the chart mode "HappyPath", independently of the A-Chart). If no data is loaded it shows 📊 No Process Data — "Apply filters in the sidebar to load the process map." with a Load button.

The right pane holds the ideal path. Drag its left edge to resize it between 300 and 1000 px; double-click the drag handle to reset the width to 460 px. The width persists as happyPath.editorWidth.

Creating and editing a path

  1. Press ＋ New in the top bar. The sheet "New Happy Path" ("Give the ideal step sequence a name.") asks for a name. Creating a path also switches the pane into edit mode.
  2. Use ＋ Add step… to append steps in the intended order. The dropdown lists only steps that are not yet used anywhere in the path — a step may appear only once across the whole path, branches included.
  3. Reorder with ▲ Move up / ▼ Move down on each row, and remove a step with the red ⊖ button.
  4. For genuine alternatives, press ⑂ Split ("Add a split — alternatives that rejoin and continue"). The split card offers ✎ Rename split ("Rename Split"), ▲/▼, 🗑 Delete split, one embedded editor per branch, ＋ Branch to add another, and 🗑 Delete branch on branches beyond the second.
  5. When steps follow the split, name the convergence point with ✎ Rejoin: <name> (prompt "Name Rejoin", confirm Save). Steps after the split are the shared continuation of every branch.
  6. Press ✓ Done to leave edit mode. Use ↻ Recompute conformance at any time to re-run the scoring.

Splits may be nested: a split can be placed inside a branch of another split. The helper text in the editor states the rule the scoring follows: "Each journey is scored against the route it matches best."

Reading the visualisation

Outside edit mode the path is drawn as a vertical trunk of step cards joined by ⌄ chevrons.

  • A card is green-tinted when that step exists in the currently filtered process (tooltip = the step name) and grey when it does not (tooltip "<name> — not present in the filtered process"). A grey card means the step you designed into the process never occurs under the current filters at all.
  • Green cards carry a coverage percentage: min(1, max(incoming, outgoing) ÷ filtered journeys) — the share of filtered journeys that touch this step. A step at 100 % is on every journey; a step at 12 % is an exception in practice, however central it is on paper.
  • A split renders as a "⑂ <label or 'Split'>" fork line followed by side-by-side branch columns headed Branch 1, Branch 2, … (an empty branch shows "No steps"), and, when a shared continuation exists, a "⑃ <rejoin label or 'rejoin'>" line before it.

Two helper states replace the trunk: with no path selected the pane explains "Define an ideal step sequence to measure how closely real journeys follow your intended design. Create one with "＋ New"."; with an empty path it shows 🪧 No Steps Defined — "Use ＋ to add the first step." in edit mode, or "Enable Edit Path to define the happy path." otherwise.

How routes are enumerated and scored

The conformance score is computed on the server and recomputes automatically whenever the project or the selected path changes.

  1. Route enumeration. The path is expanded into every possible start-to-end step sequence: plain step nodes append themselves, and each split multiplies the routes collected so far by all routes through each of its branches. Nested splits are expanded recursively. The expansion is capped at 2 000 routes so that heavily nested paths cannot explode; routes shorter than two steps are discarded because they contain no transition to compare.
  2. Edge sets. Each enumerated route and each observed journey variant is reduced to its set of consecutive transitions ("A → B", "B → C", …).
  3. Best-match coverage. For each observed variant the application computes, against every enumerated route, the fraction of that route's transitions the variant contains, and keeps the highest value. This is why a split costs nothing: a journey is measured against the branch it actually took.
  4. Weighting. Coverage values are averaged weighted by the number of journeys behind each variant, so a route walked by 5 000 journeys moves the score far more than one walked by three. The result is the 0–1 figure in the badge.
  5. Variant limit. The scoring is run against the top 500 journey variants of the current filter. Extremely long-tailed processes are therefore scored on their meaningful mass, not on every one-off route.
Note The score is edge coverage, not equality. A journey that walks the whole happy path and then adds three rework loops still scores 1.00 for that path, because every intended transition is present. Use the Conformance Check norms (below) or the Statistics route table to detect the extra traffic.

Happy paths also feed the AI supported Documentation report: if none are defined, that view warns that conformance data will not be included.

Conformance Check

Requires: Power user or Administrator

Conformance Check compares the measured value of each transition against a target value you store on that transition — its norm. Norms are held per project and per metric in backend storage, so the Count norms and the Avg Time norms of the same edge are independent, and norms follow your account to any browser.

View mode and edit mode

In view mode the flowchart is a compliance overlay: edges are green (compliant), red (violation) or grey (no norm defined), their width still encodes the actual value, and each label is a solid badge showing the actual value. In edit mode every edge is drawn uniform grey at width 6 and the badge shows the stored norm instead ("—" when none is set; the badge is accent-coloured where a norm exists and faint grey where it does not). The deliberate flattening in edit mode stops the visual weight of the data from distracting you while you set targets.

Setting a norm

  1. Select the metric whose norm you want to set.
  2. Press Edit norms.
  3. Click the edge (the line has a generous invisible hit area, and the label is clickable too). The norm editor opens, headed "<from> → <to>" with the line "Actual: <value>" — for Count the wording is "Actual: <value> of outgoing".
  4. Type the target. The placeholder is Target % for Count and Target value (seconds) for the time metrics. Press Enter or Set to save, Clear to delete the norm.
  5. Press Done to return to the compliance overlay.
Note Pressing Set with an empty or non-numeric input clears the norm rather than storing a zero. Clearing is therefore always safe and never leaves a hidden "0" target behind.

Count norms are percentages

For the Count metric a norm is not an absolute number of traversals — it is the transition's share of the source node's outgoing flow, so the norms leaving one step should total 100 %. The editor helps you keep that budget: it shows "X% on N other edge(s) from "<step>"" and "Y% remaining to reach 100%", and if your entry would push the node over, it displays a red border and the message "Total would be Z% — over 100%".

Warning The budget helper warns but does not block. You can store a set of Count norms that adds up to more than 100 % of a node's outgoing flow; the compliance colours will then be arithmetically unreachable for at least one edge.

Reading the gap table

Press Show gaps for a tabular reading of the same data. Rows are sorted by severity — violations first, then by descending delta — so the worst offender is always the first row. Self-loop edges (a step following itself) are excluded from the table.

Simulation

Requires: Power user or Administrator

Simulation fits a Markov model to the process graph currently loaded in the A-Chart and generates synthetic journeys from it: transition probabilities come from the observed occurrence counts, edge durations are drawn from a lognormal distribution fitted to each edge's average and standard deviation, and journeys arrive as a Poisson process. Nothing is written to the database — the result lives in the selected simulation slot for the session and can be exported or used as an A/B data source.

A walk ends when it reaches a step flagged as end-of-process, when the model has no outgoing transition left, or when Max steps per journey is reached — whichever comes first.

Note The whole configuration is retained while you move to another view and back — target slot, counts, dates, excluded/required steps, the resource levers and even which sections are expanded. It is not reset on each visit, so you can flip between Simulation, the charts and A/B Comparison without re-entering anything and only reset a value when you actually want to change it.
Note With Required steps set, a run can finish with fewer journeys than you asked for. The generator makes a bounded number of attempts (twenty times the journey count, and never fewer than a thousand); if the required combination is rare in the observed graph, the attempts run out first. Compare the Journeys tile in the results header with the journey count you configured.

Resource levers: transition-time what-ifs

Excluding a step models removing work; the resource levers model the other kind of change — keeping the process shape but altering how long parts of it take, to see what dedicating more (or fewer) resources to a step does to the whole graph. Routing probabilities are untouched; only the durations move, and cycle time, bottlenecks and variant timing all respond. Two levers combine:

  • Resources per step — a single factor scaling the time of every transition leaving a step. A factor of 0.5 on a step says "double its capacity", halving the time cases spend leaving it; 2.0 halves the capacity. It is the quick "throw staff at this step" knob.
  • Transition time overrides — finer control over one from → to hand-off: either scale its observed mean by a multiplier (×0.5 = twice the resources on that specific transition) or set an absolute mean time in minutes. A step's resource factor still applies on top of an edge override, so the two compose multiplicatively.

Internally, each transition's duration is drawn from the lognormal fitted to its observed average and standard deviation; a lever multiplies that draw. Because scaling a lognormal by a constant scales its mean by the same constant while leaving its shape unchanged, the spread and right-skew stay realistic — the whole distribution shifts faster or slower rather than collapsing to a single value. An absolute override re-centres the mean on the target you type and keeps the same relative spread. Levers that resolve to no change (a factor of 1, or a non-positive or non-finite value) are ignored.

Note The resource levers are a direct time what-if, not an emergent queue. Cycle times are still sampled independently per event, so raising the journey count or the arrival rate alone will not create waiting time — to study contention, set the levers to the slower times you expect under load. The natural workflow is to run the unchanged process into Sim-A and the lever-adjusted version into Sim-B, then compare them in A/B Comparison (including a Process Similarity score).

Running a simulation

  1. Load the A-Chart with the filters that describe the population you want to model. Simulation has no filters of its own — it consumes the A-Chart's graph.
  2. Switch to Simulation and choose the target slot, Sim-A or Sim-B.
  3. Set journey count, start date, average inter-arrival and max steps per journey; add excluded and required steps if needed.
  4. Press Run simulation. The button shows a spinner and is disabled while the run is in flight, and whenever no A-Chart graph is available.
  5. Read the results in the tabs on the right. Re-run as often as you like — each run replaces the content of its slot.

Before any run the results area shows 🎲 Sim-A — no results yet (or Sim-B) with the text "Configure the parameters and run the simulation. Results can then be selected as an A/B data source in the Sampling section." With no project selected it shows 🗺 No Project Selected — "Select a project from the sidebar."

Using a simulation as an A/B data source

Each simulation slot can stand in for real data on either side of the A/B Comparison.

  1. Run a simulation into Sim-A (and, for a two-scenario comparison, a second one into Sim-B).
  2. Switch to A/B Comparison and make the side you want to change active by clicking its panel header.
  3. In the sidebar Sampling section choose Sim-A or Sim-B as that side's data source instead of Original or Sample 1–3.
  4. The panel reloads from the simulation. Its Active Sample KPI tile now reads "Sim-A" or "Sim-B" with that run's journey count.

Re-running a slot that is currently displayed as an A/B data source refreshes that side automatically — you do not need to reselect it.

Warning Simulation output is read-only wherever it appears. The canvas shows a red notice — "Sim-A: simulation data is read-only — interactive filtering, drill-down and step editing are not available." — and the ✓ Require in journeys and ⊖ Exclude from journeys items disappear from the node popover. To change what a simulated scenario contains, change the Excluded steps / Required steps configuration and run it again.

Guard rails and error messages

A simulation runs inside the shared backend, so an oversized request would slow down or crash the service for every user. The size is therefore checked before the run starts and rejected outright; the message appears in red above the Run simulation button.

Both the product limit and the per-dimension limits exist because a cyclic process graph generates one event per step: a modest journey count combined with a very large Max steps per journey produces just as many events as a huge journey count. Every rejection is also recorded in the backend log under the operation "simulation", so an administrator can see who hit which ceiling.

A second guard applies before the request is even sent. If the A-Chart holds no process graph, the configuration column shows an orange warning — "Load the A-Chart first — simulation needs an observed process graph." — and the Run simulation button stays disabled; attempting the run from elsewhere reports "Load the A-Chart first — simulation needs a process graph."

Tip Start small. A run of the default 200 journeys completes in a moment and tells you immediately whether the model produces plausible variants; only then scale the journey count up for a distribution you intend to quote.
