3 Installation and Deployment

This chapter tells you how to get Process Mining Demonstrator — Web Edition running, either directly on a machine with Python and Node.js installed or as a single Docker container. It covers the system requirements, the run.sh launcher and its flags, the shipped Docker Compose file with its port offsets and data volume, the complete reference of PMW_* environment variables, a first-run checklist, where the runtime licence file lives, where backups are written, and what to check after an upgrade. It is written for the person who installs and operates the system — normally the same person who holds the Administrator account. End users need none of it.

Note Process Mining Demonstrator — Web Edition is intended for demonstration and educational purposes. It is not a production-ready process mining solution. Size and secure your deployment accordingly.

3.1 System requirements

Only the compute backend has hard runtime requirements. Node.js is needed solely to build the single-page application (SPA) and is not required at runtime — the Docker image builds the SPA in a separate stage and ships only the compiled result.

Python dependencies

All backend dependencies are pinned in requirements.txt: fastapi 0.139.2, uvicorn[standard] 0.51.0, pyexasol 2.3.0, openai 2.46.0, pydantic 2.13.4, pydantic-settings 2.14.2, cryptography 49.0.0, ldap3 2.9.1, httpx 0.28.1, orjson 3.11.9, python-multipart 0.0.20, regex 2026.7.19 (the ReDoS-safe engine behind admin log search), tzdata 2026.3, webauthn 3.0.0 (passkeys), pyotp 2.10.0 and qrcode 8.2 (TOTP enrolment; the SVG factory is used so no imaging library is required).

Note tzdata is not optional. The slim container image carries no system IANA zone database, and the admin display-timezone setting — which also governs when scheduled backups fire — depends on it.

Test and development dependencies live in requirements-dev.txt and are installed on top of requirements.txt: pytest 9.1.1, pytest-asyncio 1.4.0 and httpx2 2.9.1. The httpx2 package is test-only; production code continues to use httpx.

3.2 Local installation

The launcher run.sh hard-codes the interpreter path ./.venv/bin/python. The virtual environment must therefore live at .venv in the repository root — not elsewhere, and not under a different name.

  1. Open a terminal in the repository root.
  2. Create the virtual environment and install the backend dependencies: 
    python3.13 -m venv .venv
.venv/bin/pip install -r requirements.txt
    Python 3.14 works equally well; substitute python3.14.
  3. Optionally add the test dependencies: 
    .venv/bin/pip install -r requirements-dev.txt
  4. Build the single-page application: 
    ./run.sh --build
    On the first run this prints → installing frontend dependencies and runs npm install inside frontend/web; afterwards it prints → building the SPA and runs npm run build. The script then exits without starting any server.
  5. Start the stack: 
    ./run.sh
Warning If the virtual environment is missing, run.sh refuses to start and prints:
error: virtualenv missing — create it with:
  python3.13 -m venv .venv && .venv/bin/pip install -r requirements.txt

3.3 The run.sh launcher

run.sh is the single entry point for all four Python processes. It changes to its own directory before doing anything, runs under set -euo pipefail, and traps EXIT, INT and TERM so that pressing Ctrl-C kills every child process cleanly. There is no separate stop script.

InvocationWhat it starts
./run.shCompute backend, admin interface, GUI server and integration console. If frontend/web/dist/index.html is missing, the SPA is built first automatically.
./run.sh --devCompute backend, admin interface and the Vite dev server on http://localhost:5173 with hot reload (HTTP only). No GUI server and no integration console. Runs npm install first if node_modules is absent.
./run.sh --buildRebuilds the SPA and exits. No servers are started.

A normal start prints these lines; use them to confirm that all four processes came up:

→ compute backend on https://127.0.0.1:8000 (TLS, internal cert)
→ admin interface (HTTP 8090 / HTTPS 8453, per TLS mode)
→ GUI server (HTTP 8080 / HTTPS 8443, per TLS mode)
→ integration console (HTTP 8100 / HTTPS 8463, per TLS mode)

In development mode the third and fourth lines are replaced by → Vite dev server on http://localhost:5173.

Warning --dev sets PMW_REQUIRE_PROXY_AUTH=0 automatically. This is safe only because Vite proxies straight to the backend over loopback with no GUI proxy in between. Never use --dev for anything but local development: with proxy authentication off, any local process can forge the X-PMW-User header and reach /api/* directly.

Four operational facts follow from this layout and are worth understanding before you plan a deployment:

  • The browser only ever talks to the GUI server. The compute backend can therefore run on a separate host close to the database; point the GUI proxy at it with PMW_BACKEND_URL.
  • The GUI-to-backend hop is always TLS-encrypted, even on loopback. The backend mints an internal self-signed certificate at start (data/certs/internal.crt and internal.key), independently of the user-facing TLS mode, and the GUI proxy pins it through PMW_BACKEND_CA.
  • The integration console ports are derived by convention as the admin port plus ten (8090 → 8100, 8453 → 8463) unless you override them explicitly.
  • All three user-facing surfaces share one sign-in stack (password, TOTP two-factor, WebAuthn passkey) and one TLS mode with one active certificate.
Warning The per-source-IP sign-in throttle keys on the socket peer address and never trusts X-Forwarded-For. Behind a reverse proxy, every client shares a single throttle bucket. Terminate TLS at the application itself, as run.sh does, or add trusted-proxy handling before fronting it.

3.4 Docker deployment

One image, process-mining-web:latest, runs all four services through run.sh as its CMD. The container is named process-mining-web.

  1. Edit docker-compose.yml and set PMW_DEFAULT_ADMIN_PASSWORD (and optionally PMW_DEFAULT_ADMIN_USER) in the environment: block. The lines are present but commented out, with Administrator and "change-me" placeholders.
  2. Build and start: 
    docker compose up -d --build
  3. Open the admin interface at http://localhost:10090 and sign in.
  4. Open the main application at http://localhost:10080.

Host port mapping — the +2000 offset

Host ports are offset by 2000 from the container ports so that they do not clash with other local services; the compose file specifically cites phpLDAPadmin occupying host port 8080.

Host portContainer portSurface

Note The HTTPS host ports do nothing until TLS is switched to Optional or Required in the admin interface. Until then only the HTTP ports answer.
Warning Older README text names http://localhost:8080 and http://localhost:8090 for Docker. That predates the +2000 offset. With the shipped compose file the correct URLs are http://localhost:10080 and http://localhost:10090; the compose file is authoritative.

Container port 8000 — the compute backend — is deliberately not published. It stays private inside the container, where PMW_BACKEND_HOST is baked to 127.0.0.1. The image's EXPOSE lists only 8080, 8443, 8090, 8453, 8100 and 8463.

What the image contains

The build is a two-stage Dockerfile:

  • Stage 1 (node:22-slim) runs npm ci against the lockfile — cached until the lockfile changes — and then npm run build.
  • Stage 2 (python:3.13-slim) creates /app/.venv and pip-installs requirements.txt into it, so run.sh's ./.venv/bin/* paths work unchanged. It copies backend/, admin/, integration/, frontend/, examples/ (the bundled demo logs) and run.sh, and drops the built SPA into frontend/web/dist.

Environment baked into the image: PYTHONUNBUFFERED=1, PIP_NO_CACHE_DIR=1, PMW_DATA_DIR=/app/data, PMW_BACKEND_HOST=127.0.0.1, and PMW_FRONTEND_HOST, PMW_ADMIN_HOST and PMW_INTEGRATION_HOST all set to 0.0.0.0 so that the published ports are reachable from the host.

A HEALTHCHECK fetches https://127.0.0.1:8000/api/health every 30 seconds, with a 5-second timeout, a 25-second start period and 3 retries. Certificate verification is disabled for that probe because the backend serves its internal self-signed certificate and loopback liveness does not need verification. Compose sets init: true, so tini runs as PID 1 for clean signal handling and no zombie processes, and restart: unless-stopped.

.dockerignore keeps local state and secrets out of the build context: .git, .venv, node_modules, frontend/web/dist, the entire data directory, **/*.sqlite3, **/secret.key, **/certs and the usual caches. A locally populated data directory or encryption key can therefore never be baked into an image by accident.

Persistence: the data volume

The compose file declares a single bind mount: ./data, relative to the compose file, onto /app/data inside the container — which is PMW_DATA_DIR. Everything the application must keep lives there.

Note There is no separate integration_files mount in the shipped compose file. The File-source sandbox lives inside the same volume at data/integration_files, and the bundled examples/*.log demo logs are seeded into it on first run. Add a second mount only if you move the sandbox elsewhere with PMW_INTEGRATION_FILES_DIR.

Auto-rebuild during development

Run docker compose watch (or docker compose up --watch) to rebuild the image whenever source changes. The watch rules cover ./backend, ./admin, ./integration, ./frontend (ignoring node_modules/ and dist/), ./requirements.txt, ./run.sh and ./Dockerfile; each change triggers action: rebuild. Docker's layer cache keeps this cheap because untouched layers are reused. This requires Docker Compose 2.22 or newer.

3.6 Enabling TLS

Requires: Administrator

TLS is configured entirely in the admin interface, tab TLS / SSL. One mode and one active certificate are shared by the GUI server, the admin interface and the integration console.

ModeGUI bindsAdmin bindsIntegration binds
OffHTTP only (:8080)HTTP only (:8090)HTTP only (:8100)
Optional:8080 and :8443:8090 and :8453:8100 and :8463
RequiredHTTPS only (:8443)HTTPS only (:8453)HTTPS only (:8463)
  1. Sign in to the admin interface and open the TLS / SSL tab.
  2. Either generate a self-signed certificate — supplying common name, subject alternative names, validity and key size — or upload a PEM certificate together with its key.
  3. Mark exactly one certificate as active.
  4. Choose the mode: Off, Optional or Required.
  5. Open App Control and press ↻ Restart app server. The listeners rebind in place; no terminal is needed.

The restart works because each TLS-aware launcher writes a PID file — data/gui.pid, data/admin.pid and data/integration.pid — and the admin service sends SIGHUP, on receipt of which the launcher rebinds according to the current TLS plan.

Note The design is fail-safe. If a mode needs a certificate but none is active, every server falls back to HTTP so that nothing becomes unreachable — including the admin interface itself. A bad certificate can never lock you out.

The active certificate is materialised to disk as data/certs/active.crt and active.key so that the TLS listener can read it. Certificate private keys are encrypted at rest with Fernet in the security store, and key files are written with mode 0600 from the moment they are created. Both the application and admin servers send X-Frame-Options: DENY, a Content-Security-Policy of frame-ancestors 'none', X-Content-Type-Options: nosniff and Referrer-Policy: no-referrer, plus HSTS when TLS is on.

Warning Losing secret.key orphans every stored secret. Database passwords, API keys, certificate private keys and the backup password become unrecoverable, and no amount of database restore brings them back. Treat it with the same care as a private key, and never copy it into a build context or an image.

3.8 Backups

Requires: Administrator

The admin interface, tab Backup, runs encrypted backups on an in-process scheduler. No external cron job is involved.

  1. Open the Backup tab in the admin interface.
  2. Enable scheduled backups.
  3. Build the schedule either with the dropdowns — hourly, daily, weekly or monthly, plus a time — or by typing a raw five-field cron expression. The panel shows the resulting cron string and a plain-English preview as you edit.
  4. Set the retention count: files beyond this number are pruned automatically.
  5. Set the AES-256-GCM password.
  6. Save, then press Run backup now to test the configuration. The outcome of the last run is displayed.

Backups are written to data/backups/ as timestamped, encrypted .json envelopes. The backup password is stored Fernet-encrypted at rest so that unattended runs work, and it is never returned to the client: the API exposes only a hasPassword flag. Schedule times follow the display-timezone setting in App Control, so "daily at 02:00" fires at 02:00 in the chosen zone and is DST-aware; the default is Server local.

Warning In-app backups are not a substitute for disaster recovery. For that, back up the whole data/ directory, including secret.key — without it the encrypted secrets inside the backup cannot be decrypted.

3.9 Where to put the licence file

Requires: Administrator

The compute backend requires a signed licence. Upload the issued license.json in the admin interface under App Control → License; the panel shows the licensee and the expiry date, and offers a remove option. Verification is Ed25519 against a public key embedded in the application. The uploaded file is stored as data/license.json.

Without a valid licence the system enters Demo Mode. The sign-in panel shows a Demo Mode — remaining time banner during a one-time grace period, 30 minutes by default (PMW_LICENSE_GRACE_SECS). Once the grace is spent the banner reads No License installed and the backend stops itself until a licence is applied.

  1. Open the admin interface — it keeps running even after the backend has stopped, so you can always get in.
  2. Go to App Control and find the License panel.
  3. Upload the issued license.json.
  4. Wait a few seconds. The backend re-reads the licence every 15 seconds by default (PMW_LICENSE_POLL_SECS), so a pending shutdown is cancelled almost immediately.
Note The grace period is anchored in data/demo_grace.json and is never renewed by restarting the application — that is what makes it one-time. Delete the file, or set PMW_RESET_DEMO=1, if you genuinely need a fresh demo window.

3.10 First-run checklist

Work through this list once, in order, after the very first start.

  1. Start the stack with ./run.sh or docker compose up -d --build.
  2. Sign in to the admin interface. The default credentials are Administrator / Administrator, and a password change is forced on first use. If you set PMW_DEFAULT_ADMIN_PASSWORD before the first start, use that instead — it applied only because the security database was still empty, and it is ignored from then on.
  3. Open App Control → License and upload license.json if the sign-in panel showed the Demo Mode banner.
  4. Open Database Connections and define a connection: Exasol host, port, user, password and schema, optionally an OpenAI-compatible LLM server, and the TLS options. Use Test connection, then assign the connection to the users who should see it.
  5. Optionally press Create schema & tables to provision PROJECTS, JOURNEYS, STEPS, METAS and NOTES. The statements are idempotent (IF NOT EXISTS), but the database account needs CREATE SCHEMA and CREATE TABLE privileges, which only a DBA can grant.
  6. Open Users, create the accounts you need, and grant roles: Admin, the Make power action and the Developer checkbox. Enable the Passkey and 2FA columns per user if you want them.
  7. Configure TLS as described in section 3.6, and restart the app server.
  8. Configure scheduled backups as described in section 3.8.
  9. Have a user open the main application, click a connection card under Connections, open Projects, and check that the views load from the ☰ menu.
Tip Leaving a password or API-key field blank when you edit an existing database connection keeps the stored value. It does not clear it. Type a new value only when you actually want to change the secret.

3.11 Upgrading

Everything under data/ is state, and the image contains none of it, so rebuilding the image or redeploying the container is safe — the state survives in the volume. Locally, upgrading means pulling the new source, reinstalling dependencies and rebuilding the SPA.

  1. Stop the stack (Ctrl-C locally, or docker compose down).
  2. Back up the data/ directory.
  3. Fetch the new version of the source.
  4. Locally: run .venv/bin/pip install -r requirements.txt again, then ./run.sh --build. Under Docker: run docker compose up -d --build, which rebuilds both stages.
  5. Start the stack and work through the post-upgrade actions below.

Rebuild TRANSITIONS_RAW

Requires: Administrator

Any pre-materialised transitions table that was built before the partition fix can show wrong per-edge values. Older builds partitioned the LEAD() window by EVENT_ID alone, which produces incorrect edges wherever an EVENT_ID recurs across projects or sample sets. Press Rebuild now once on each affected connection after upgrading. The equivalent API call on the admin server is:

curl -k -X POST \
  -H "Authorization: Bearer <token>" \
  https://localhost:8453/api/connections/<id>/rebuild-transitions
Note The -k flag is present because the admin certificate is typically self-signed. Drop it once you have installed a certificate the client trusts.

Distribution and partition clauses on JOURNEYS

New tables are created with DISTRIBUTE BY EVENT_ID and PARTITION BY EVENT_TIME. Tables that pre-date those clauses are not modified by CREATE TABLE IF NOT EXISTS, because the table already exists and the statement does nothing. Apply the clauses once by hand:

ALTER TABLE JOURNEYS DISTRIBUTE BY EVENT_ID;
ALTER TABLE JOURNEYS PARTITION BY EVENT_TIME;

Migrating existing users to LDAP

A directory login never adopts a local account of the same name. If you switch an existing installation to LDAP authentication, delete or rename the old local rows first; otherwise those users keep signing in with their local passwords and the directory is never consulted for them.

Tip Older README text and the header comment in run.sh speak of "all three services". The current system runs four — the integration console was added later. If a document mentions three, it predates that change.
