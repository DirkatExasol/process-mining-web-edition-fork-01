27 The MCP Server

The previous chapter described how an external program pushes data into the demonstrator. The MCP Server is the mirror image: an endpoint through which an AI client — Claude, ChatGPT or any other client that speaks the Model Context Protocol — asks the demonstrator questions and gets analysis back. It exposes nineteen tools covering connections, projects, metadata and attribute values, the process map, transition metrics, variants, statistics, journey search and lookup, notes, and — for power users — segment comparison, bottlenecks, trends, outcome drivers and conformance rules; most share the application's filter vocabulary. Its only writes are notes: there is no ingest, no event editing, no sampling. This chapter explains what the server is for, how an administrator turns it on, how the identity chain from an OAuth token to a Process Mining user works, how to configure Authentik and the server itself, what each tool returns, what to watch for behind a reverse proxy, and how to read its error codes.

Requires: Administrator to configure the OAuth settings and enable the module, in the admin interface (HTTP :8090, HTTPS :8453). Callers need no human role at the endpoint — they present an OAuth access token issued by your Authentik server, which is mapped to an existing Process Mining user. The module is off until an administrator enables it.
OAuth only, directory-backed The MCP server authenticates callers exclusively via OAuth — it has no login of its own. You must deploy an OAuth provider such as Authentik or Keycloak and configure it in the Administration page (MCP Server), with user federation from OpenLDAP or Active Directory. Only Process Mining users defined in a configured directory service can use the MCP server.

27.1 What the MCP server is, and when to use one

The Model Context Protocol is a convention by which an AI client discovers and calls tools on a remote server. The demonstrator implements it as a seventh surface so that a question asked in a chat — “which variants dominate the credit application process?”, “how much slower are international passengers?” — can be answered from live data rather than from a screenshot pasted into the conversation.

It answers the same questions the work bench answers, through the same analytical code, with the same filters. What it does not do is replace the work bench: there is no map to look at, no drill-down, no A/B view. Reach for the MCP server when the analysis needs to reach a person or a system outside the application — a written summary, a comparison across projects, a figure quoted in a report — and use the application itself when you want to see the process.

27.2 Enabling the module

Like Actions and the Event Receiver, the MCP server is opt-in. In the admin interface open the MCP Server tab, fill in the OAuth settings described in section 27.5, press Test Authentik, and only then tick Enable the MCP server. Enabling and disabling take effect immediately and need no restart; while the module is off the port stays bound but every request is answered with 503.

The server listens on the admin port +40: container 8130 for HTTP and 8493 for HTTPS, published on the host with the usual +10000 offset as 18130 and 18493. Which of the two is live follows the deployment's TLS mode and certificate, exactly as for the other surfaces (chapter 2).

Use HTTPS OAuth clients require it for anything that is not a loopback address, so in practice the MCP server is only reachable by a hosted client when TLS is on. Turn it on in the TLS / SSL tab; a TLS change takes effect after ↻ Restart app server in App Control.

27.3 The identity chain

Every call carries an Authorization: Bearer header holding an access token. The server resolves that token to a Process Mining user in five steps, and a failure at any one of them is reported distinctly:

  1. Signature. The token must be an RS256 JWT signed by a key published in your Authentik's JWKS document. Verification is offline — the keys are fetched once and cached — so no call is made to Authentik per request.
  2. Issuer. The token's iss must match the configured issuer. Authentik emits it with a trailing slash; both spellings are accepted, so you may configure either.
  3. Audience. Checked only if you have filled in the Audience field, and recommended: Authentik does not set aud to the client id unless you add a property mapping, but once you do, filling in the field ties each token to this application so a token minted for a different app on the same Authentik cannot be replayed here. Left blank, the check is skipped and any validly-signed token from the issuer is accepted (still gated by the issuer, signature, user-mapping and group checks) — prefer setting it when the same Authentik serves more than one application.
  4. Group. If a Required group is configured, the token's groups claim must contain it. This is a second gate in addition to whatever binding you placed on the Authentik application.
  5. User. The username claim (default preferred_username) is matched, case-insensitively, against the Process Mining user list. The user must already exist and be enabled.

Once mapped, that user's assigned database connections decide what the caller may see — the same boundary the application enforces for the same person signing in through the browser. A connection not assigned to them is not listed by list_connections and is refused if named directly.

Note The MCP user is a Process Mining user like any other, created in the admin interface's Users tab and given connections in Database Connections. Authentik decides who may connect; the demonstrator decides what they may see. Neither substitutes for the other.

27.4 Configuring Authentik

On the Authentik side you need one provider and one application.

  1. Create an OAuth2/OpenID Provider. Give it your standard authorization flow, and choose client type Public for interactive clients that use PKCE, or Confidential if the client stores a secret.
  2. Give the provider an RSA signing key. This is what makes the access token a verifiable RS256 JWT; without it the MCP server cannot check the signature offline.
  3. Add the client's redirect URIs. A hosted client has a fixed callback — for Claude it is https://claude.ai/api/mcp/auth_callback. A client that runs on the user's own machine binds a random loopback port instead, so it needs a port-agnostic pattern in regular-expression matching mode rather than a fixed URI.
  4. Include the scopes openid, profile and email, plus offline_access if you want the client to be able to refresh its token.
  5. Create an Application bound to that provider and give it a slug. The slug determines the issuer URL, so note it: https://<authentik>/application/o/<slug>/.
  6. Restrict who may use the application with a policy, group or user binding.
Dynamic Client Registration Some clients register themselves rather than being handed a client id. If yours does, enable DCR on the provider — the client then supplies its own redirect URI at registration time and the fixed list above is not consulted for it. If DCR is off and the client expects it, sign-in fails before any redirect URI is ever compared, which makes it look like a redirect problem when it is not.

In the admin interface's MCP Server tab:

Issuer URL
The application's issuer, https://<authentik>/application/o/<slug>/. It must be the URL the client can reach, not an internal one — discovery is performed by the client, from wherever it runs.
JWKS URL
Leave blank to auto-discover from the issuer, or paste the …/jwks/ endpoint explicitly.

Recommended. Set it to the client id once you have mapped an aud claim onto the access token, so tokens issued for other apps on the same Authentik cannot be replayed here. Blank disables the check.
Required group
Optional. Matched against the token's groups claim.
Username claim
Which claim carries the username. Default preferred_username; use email if your Process Mining usernames are email addresses.

Test Authentik fetches the discovery document and the JWKS and reports how many signing keys it found. Use it before enabling the module, and again after any change — it catches an unreachable host or a wrong slug immediately.

The test does not exercise token validation It confirms that Authentik is reachable and publishing keys, which is necessary but not sufficient. A configuration that passes the test can still reject every token, so verify with a real client before declaring success.

27.6 The tools

The tools fall into five groups — discover, analyse, cases, notes and power analysis — and three access levels:

Everyone
Every user who can sign in to the MCP server may call the discovery, analysis, case and note-reading tools, always within their assigned connections.
Notes — the only writes
create_note and update_note apply the application's own note rules. The author is always the signed-in user; the note id and its times are set by the server; a thread is append-only (a comment is prepended, nothing is rewritten); only a note's author may change its severity or scope; and another user's private note is answered exactly like a missing one, so ids cannot be probed. Every field is validated — step names must exist in the project, text is limited to 4000 characters and a title to 200, control and bidi-override characters are stripped, and no text can imitate a thread entry's header to pose as another author — a full thread (100,000 characters) takes no more comments, the permission rule is checked again inside the database write itself, each user may make at most PMW_MCP_NOTE_WRITES_PER_MIN (default 20) note changes a minute, and every write leaves an entry in the admin log naming the user and the note, never its text.
Power users and administrators
compare_segments, get_bottlenecks, get_trend, get_outcome_drivers and check_conformance are reserved for users with the power-user role (granted with Make power in the Users tab) and for administrators. Anyone else receives a polite refusal that names the role and points to the everyday tools; no query is run.
Times Note timestamps — created, edited and each comment's stamp — are local time in the display timezone chosen in the admin interface (App Control → Timezone), and the MCP server returns them with that zone's UTC offset, for example 2026-09-23T12:34:45+02:00. Journey event times are the event log's own recorded times.

connectionId is the connection's string identifier as list_connections returns it; projectId is an integer as list_projects returns it. Mixing the two up is the most common first mistake.

get_journey is the odd one out: it takes no filter, and it returns individual events rather than an aggregate. It exists because every other tool summarises many journeys, so a question about one case — what actually happened to booking FLT-000123 — has no answer in a summary.

find_journeys is what gets you there when you do not already know the case id. It applies the ordinary filter, then returns the matching cases themselves rather than a summary of them, ordered by orderBy: DURATION_DESC (the default, slowest first), DURATION_ASC, START_DESC, START_ASC, STEPS_DESC or STEPS_ASC. limit defaults to 20; minDurationSecs, maxDurationSecs, minSteps and maxSteps bound the whole journey rather than an individual event; and includePath adds each journey's full step path, which costs an extra aggregation and is therefore off by default. The usual shape of an investigation is three calls: get_statistics for the average, find_journeys for the outliers behind it, then get_journey for the one case that explains them.

list_projects spans connections for the same reason. Asked which process is the largest, a client that must call it once per connection and then get_statistics once per project spends a dozen round trips on a one-line answer; omitting connectionId and setting includeCounts answers it in one. Each entry names the connection it came from, and a connection that cannot be opened is reported as a single entry carrying error — one unreachable database degrades that row instead of failing the listing.

get_notes reaches the human layer on top of the data: the notes people attach to a project's steps and transitions. Each note carries a severity (NORMAL, INFO, IMPORTANT or URGENT), a status (open or resolved) and a scope — a private personal note or a shared one visible to the whole team. Any of these narrows the result (severity takes a list; status and scope take one value), and groupBy buckets the output by severity, status, scope or target (the annotated step or transition). Every response also carries a summary with per-severity, per-status and per-scope counts, so “how many open urgent notes are on this process?” is answered without reading each one. Visibility is the application's own rule enforced server-side: the caller sees shared notes and their own, and never another user's private notes.

Note JOURNEYS never stores a case id in the clear: ingest writes its MD5 digest, whether the events arrived from a file import or from a sink. get_journey therefore applies the application's own normalisation — a business id such as FLT-000123 is hashed before the lookup, while a 32-character hex string is taken to be an already-stored id. Both reach the same journey the individual-journey view shows, and neither requires the caller to know that any hashing happens. find_journeys reports the stored digest as its eventId, since the plaintext id is nowhere to report; feeding that value straight back to get_journey is the intended drill-down.

27.7 The filter vocabulary

Most tools accept the same optional filter, mirroring the application's own (compare_segments takes one filter per segment):

fromDate, toDate
ISO dates bounding the events. Day granularity — there is no time-of-day filtering.
includedSteps
Keep only journeys that visit all of the named steps.
excludedSteps
Drop journeys that visit any of the named steps.
meta1, meta2, meta3
Match on the three meta attributes, whatever get_metadata reports them to be titled for that project. The match is case-insensitive and also matches part of a value; get_attribute_values lists the values that occur.
sampleSet
ORIGINAL (the default), or SAMPLE_1, SAMPLE_2, SAMPLE_3.
Splitting a population Because includedSteps is an AND and excludedSteps is a NOT-ANY, a two-way split is expressed as one call each way on the step that distinguishes them. In the shipped airport dataset, excluding ENTER Passport Control gives the domestic journeys and including it gives the international ones; the two counts add up to the unfiltered total. An either/or question — “denied boarding, domestic or international” — needs one call per alternative, because no filter expresses OR.

27.8 Behind a reverse proxy

Exposing the MCP server under a public domain is the normal deployment, because a hosted AI client has to reach it from the internet. Three things must be right, and two of them are easy to get wrong.

  1. Preserve the path. Forward /mcp to the backend as /mcp. In nginx a proxy_pass with a trailing slash strips the prefix and the backend answers 404.
  2. Route the discovery paths too. When an unauthenticated call arrives, the server answers 401 with a WWW-Authenticate header pointing at /.well-known/oauth-protected-resource — at the root of the host, not under /mcp. A proxy that routes only /mcp sends that request somewhere else, the client cannot discover the authorization server, and it reports a sign-in failure that looks nothing like a routing problem.
  3. Advertise reachable URLs. Send X-Forwarded-Proto and X-Forwarded-Host so the metadata carries the public address. The issuer it names must resolve from the client's network; an internal hostname or a Docker-internal name is unreachable for a hosted client and the connection will never complete.

27.9 Limits, error codes and troubleshooting

ResponseMeaning and remedy
503The module is disabled. Enable it in the MCP Server tab.
401 + WWW-AuthenticateNo token, or one that failed signature, issuer or audience checks. The client should run the OAuth flow. If it loops, check the issuer with Test Authentik.
403 no matching userThe username claim does not match an enabled Process Mining user. Create the user with that exact name, or change the Username claim.
403 not in the required groupThe token's groups claim lacks the configured group. Note that a group must exist in Authentik and have the user as a member for it to appear in the token.
Connection is not assigned to youAssign it to the user in the admin interface's Database Connections tab.
“Sorry — … reserved for power users”A deeper-analysis tool was called by a user without the power-user role. Grant it with Make power in the Users tab if that user should have it.
Limit of N note changes per minuteA client is writing notes in a loop. Wait a minute; raise PMW_MCP_NOTE_WRITES_PER_MIN only if the volume is intended.
Step ‘…’ does not exist (create_note)Step names must match the project exactly; list them with get_metadata.
This note's thread is fullThe thread reached 100,000 characters. Start a new note for the follow-up.
A batch may hold at most 20 messagesThe client sent more than 20 JSON-RPC calls in one request; it must split them.

Three environment variables bound the server: PMW_MCP_MAX_ROWS (default 1000) caps the rows any one call returns, PMW_MCP_JWKS_CACHE_SECS (default 3600) sets how long Authentik's signing keys are cached, and PMW_MCP_NOTE_WRITES_PER_MIN (default 20) limits each user's note writes per minute.

Note Only the transport used to fetch the JWKS skips certificate verification, on the assumption that Authentik is a trusted internal host. Token integrity does not depend on that transport: the signature is checked cryptographically against the keys it returns, so a tampered token fails regardless.
When a client connects but shows no tools The transport is up and the token exchange succeeded, but every tool call is being refused — almost always at step 4 or 5 of the identity chain. Check the group and the username claim before touching anything else; the connection state in the client reflects only the OAuth handshake, not whether a single call has ever been answered.
