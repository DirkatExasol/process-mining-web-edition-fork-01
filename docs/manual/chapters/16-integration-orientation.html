16 The Integration Console

The integration console is the fourth surface of the product, alongside the application, the administration interface and the login screen. It is where log files and other raw data are turned into the JOURNEYS events the application analyses. This chapter is your orientation: what the console is for, who is allowed in and how that permission is enforced, how the window is laid out, what each of the three sidebar sections holds, how connections are managed from here, and how to read the Abstraction layer status card, the six ingestion KPI tiles and the live pipeline flowchart. Defining source types and running imports have chapters of their own; read this one first so the surface makes sense before you build anything on it.

What the console is for

The application reads process data that is already in the database. The integration console is the tool that puts it there. In the console you:

Define a source type
An extraction specification: a pasted sample line from your log plus a regular expression for each field you want out of it — timestamp, case id, step, up to three business attributes and any number of helper values used only for matching. A source type is the parser.
Define a source
Where the data actually comes from — today a file on the server, addressed by path — together with its encoding, the source type applied to each line, the transaction bracket and, optionally, a watchdog that imports newly appended lines by itself.
Run an import
Point a source at one of your assigned connections and a project id, and the abstraction layer reads the file, applies the source type and writes JOURNEYS rows — creating the PROJECTS, STEPS and METAS companion rows for you.
Watch what happened
The status card, the KPI tiles and the pipeline flowchart show the run in flight and, over time, the accumulated behaviour of every source, source type and destination you have used.

Everything you create in the console is owned by you. Your source types and sources are yours alone; another developer signing in to the same deployment sees their own, not yours.

Access, sign-in and roles

Requires: Developer or Administrator

The console is served on its own port, by convention the administration port plus ten: 8100 for HTTP and 8463 for HTTPS with the default port assignment. It follows the same TLS plan as the application and the administration interface. In Docker the published ports are offset by 2000.

SettingDefaultPurpose
PMW_INTEGRATION_PORTadministration port + 10 (8100)HTTP port of the console
PMW_INTEGRATION_HTTPS_PORT8463HTTPS port of the console
PMW_INTEGRATION_HOSTthe administration host (127.0.0.1)Interface the console binds to

Who may sign in

Only users holding the Developer role or the Admin role may use the console. Power users and plain users are refused: the server declines the sign-in and drops the session. This is deliberate — the data-source surface writes directly into the analysis database, so it is restricted more tightly than the application itself, where power users have wide privileges.

Sign-in is always required on this surface, even when the deployment's global “require login” setting is switched off for the application. The only exception is a deployment that runs entirely without sign-in (single-user or development mode, where no user identity exists at all); there the surface is open, in step with every other part of the product.

  1. Open the console's address in your browser — for a default local installation http://localhost:8100, or the HTTPS address your administrator gave you.
  2. While the session check runs the console shows a large spinner with the text Starting….
  3. The shared login screen appears, with the subtitle Integration under the product logo so you can tell at a glance which surface you are signing in to. Enter your credentials.
  4. If your deployment mandates two-factor authentication and you have not yet enrolled, the login screen stays up until enrolment is complete — exactly as in the application.
  5. The console loads, applies your personal theme setting and reads your assigned data-source connections.

Why the API re-checks your role

The console's own port is only the first line of defence. All integration endpoints live under /api/integration on the shared compute backend, and the application proxies /api/* for any enabled user. If the role were only checked at the console's front door, a power user could drive the whole data-source surface through the application's proxy instead. To close that, the role check is repeated server-side on the API router, so it covers every integration endpoint — including any added in a later release.

SituationResult
The deployment runs without sign-in (no user identity)Open, no restriction
The administrator has switched the integration surface offHTTP 403 — “The integration console is turned off.”
The user is unknown, disabled, or lacks the Developer/Admin roleHTTP 403 — “You need the Developer role to use the integration features.”
Note Because the switch is enforced on the API and not only on the port, turning the integration surface off in the administration interface disables the entire integration API as well. The switch is on by default.

If your role is revoked while you are signed in

The console does not silently degrade. If an administrator removes your Developer role during your session, the console replaces its whole window with an Access denied page: the product logo, the heading “Access denied”, the text “The integration console is available to developers and administrators only. Ask an administrator to grant you the Developer role.” and a ⏻ Sign out button.

The console layout

The window is divided the same way as the application: a sidebar on the left, a main pane on the right. The main column is centred and no wider than 900 px, so the pipeline and status card stay readable on a large screen.

The sidebar

From top to bottom the sidebar contains:

  1. The brand header — the logo, the title Integration and the caption Data-source configuration.
  2. Three collapsible accordion sections: Connections, Sources and Source types. At most one is open at a time, and clicking the header of the open section closes it. Each header shows a chevron, the title, the item count in parentheses when it is greater than zero, and one or two trailing icon buttons.
  3. Pinned at the bottom, the shared identity footer: a first row reading 👤 <your display name> (<role>) — Admin, Power user, Developer or User — and a second row of buttons, 🔒 Two-factor and 🔑 Passkeys where your deployment allows them, plus ⏻ Sign out.
  4. Below the footer, the theme bar with the light, dark and system switcher.

The console follows your personal app.theme setting, shared with the application: light, dark or system. “System” tracks your operating system's colour scheme live. Until your settings have loaded after sign-in, the operating system's scheme is used.

The main pane

The main pane holds four things, in this order:

The toolbar
A single ？ Help button in the top right, opening the same Help panel as the application.
The Abstraction layer card
Status pill, target line, the six KPI tiles and — after a run that produced messages — the run log. See the status panel below.
The Ingestion pipeline header row
The caption showing how many runs have been recorded, and the ↺ Clear button.
The pipeline canvas
The live flowchart of your ingestion behaviour.

The three sidebar sections

Connections

The Connections section lists the database connections assigned to you, as clickable badges sorted alphabetically by name. Each badge shows a ⛁ icon — green when that connection is connected, accent blue otherwise — the connection name (or “(unnamed)”), the optional comment, a line reading Database: <host>:<port> (“(no host)” when the host is empty) and, when an LLM is configured, LLM: <url> or “(configured)”. About three badges are visible at once; the list scrolls beyond that.

The header carries two buttons: ＋ (“New connection”), shown only to users who may manage connections, and ↻ (“Refresh connections”), which reloads the assigned list.

If you have no connections, the empty state depends on your permissions: managers see “No connections yet. Use ＋ above to create one and assign users.”, everyone else sees “No connections assigned to you. Ask an administrator to grant access.” Any connection error is shown in red under the list.

Sources

The Sources section lists your data sources, with ＋ (“Add a source”) in the header. Each badge shows the kind icon (📄 for a File source), the source name, and a sub-line with the kind label and a summary of its configuration — for a File source, its path, or “(no path)” when none is set. A 👁 eye after the name means the watchdog is switched on for that source (tooltip “Watchdog on — auto-imports new lines”). The ▷ button opens the Run dialog and the ✕ button deletes the source after a confirmation; clicking anywhere else on the badge opens the edit wizard. Sources, the wizard and the Run dialog are covered in their own chapter.

Source types

The Source types section lists your extraction specifications, with ＋ (“Add a source type”) in the header. Each badge shows a 🧩 icon, the name and a sub-line reading “<n> field(s)” or “no fields yet”. Clicking a badge opens the source-type wizard; ✕ deletes it after a confirmation. The wizard — sample line, field mapping, compound steps and the example JOURNEYS record — has its own chapter.

Warning Deleting a source type does not cascade. Sources that reference it keep a dangling link and their runs fail with the warning “This source has no source type linked” until you edit the source and pick a new one.

Managing connections from the console

Requires: ownership of the connection (Power user, Administrator or Developer role to create one)

You do not have to switch to the application to set up a destination database. The console embeds the same connection editor. What differs from the application is not the editor but the permission model, and the distinction is easy to trip over:

Assignment
An assigned connection is one you may use: connect to it from the sidebar, run an import into it, and name it as a watchdog destination. Assignment is granted by whoever owns the connection.
Ownership
An owned connection is one you may edit. Only owned connections show the ✎ pencil on their badge.

A connection that an administrator created and assigned to you is therefore read-only for you: you can import into it all day, but you cannot change its host, credentials or user assignments. This is why the pencil is missing from some badges and present on others.

Connecting and disconnecting

  1. Open the Connections section in the sidebar.
  2. Click a connection badge to connect to it. The badge shows a status dot: green for Connected, orange for Not connected.
  3. Click the active badge again to disconnect.
  4. Clicking a different badge while one is active disconnects the current connection first, then connects the new one.
Note You do not need to be connected in order to import. The Run dialog and the watchdog open the destination themselves using the connection's stored credentials. Connecting from the sidebar is what sets the default target shown in the status card and preselects a destination in the Run dialog.

Creating a connection

  1. Click ＋ in the Connections header. The New Connection editor opens as a wide sheet with the ⛁ icon.
  2. On the Database / LLM Details tab, fill in at least a Name — leaving it blank fails with “Name is required.” — and the Host, Port (default 8563), Username, Schema and Password.
  3. Optionally switch on Use TLS and choose a Certificate mode: “Verify (system trust store)” (the default), “Pin fingerprint” or “Accept any (insecure)”. A pinned fingerprint goes in Fingerprint (SHA-256); Minimum RSA key size defaults to 2048.
  4. Optionally configure an LLM: Server URL, Model and API key.
  5. Tick the usernames that should be able to use this connection under Assigned users.
  6. Click Test to verify. The result appears inline — green when everything answered, orange when one component failed, red when all did, with text such as “Database OK · LLM OK (n models)”.
  7. Click Save. The new connection appears in the sidebar and, being owned by you, carries the ✎ pencil.

Editing an owned connection

  1. Hover the badge of a connection you own and click the ✎ pencil. The click does not connect or disconnect — it only opens the Edit Connection editor.
  2. Change what you need. A stored password shows the placeholder •••••• (unchanged); leave it blank to keep the stored value.
  3. Use Create schema & tables if the target schema does not exist yet. The button stays disabled until a schema name is entered, and it needs a database account with CREATE SCHEMA and CREATE TABLE rights — only your DBA can grant those.
  4. Click Save, or Delete to remove the connection. Deletion asks to confirm: “<name> will be removed for all assigned users. This cannot be undone.”

The editor's other two tabs are equally available here: Demo Content, which generates a Retail, Finance/Insurance or Transportation demonstration data set into a schema (journey count default 500, range 1–20 000), and Projects, which lists the projects in the connection's schema with their journey and event counts and lets you delete one. Both are described in full in the chapter on connections and projects.

The Abstraction layer status panel

The status card is the console's live readout of the extraction engine. It is driven by a single poll of the status endpoint every 1.5 seconds, and re-polls immediately whenever you change the active connection.

The card is titled Abstraction layer and carries a state pill on the right:

PillColourMeaning
● IdleGreyNothing has run yet in this session
RunningAccent blueAn extraction is in progress
CompletedGreenThe most recent run finished successfully
FailedRedThe most recent run failed; the message is shown below

Under the title, the target line tells you where an import would land: Target <schema> · <connection name> when you are connected and the connection has a schema; “The active connection has no target schema” when it does not; and “Pick a connection on the left to choose the target” when you are not connected at all.

Two warning banners can appear: the poll error, if the status endpoint cannot be reached, and Last run failed: <error> after a failure.

When the most recent run produced log messages, a toggle button ▸ Run log (<n>) appears below the KPI strip. Expanding it shows a scrollable monospace list of that run's messages, for example:

reading /data/logs/access.log → SALES.JOURNEYS (project LIVE-LOG)
pushed 500 events, skipped 2 unparseable line(s)
created project 'LIVE-LOG'
watchdog: 14 new line(s) from /data/logs/access.log
Note The status is per user and always reflects the most recent run only — a new run resets its counters. Only one extraction runs per user at a time; a second one started while the first is in flight fails with “An extraction is already running for this user.” Different users can run concurrently.

The ingestion KPI tiles

Six tiles sit inside the status card, using the same visual language as the application's KPI strip. They wrap onto further rows in a narrow window.

TileIconWhat it shows
Manual imports▷How many recorded runs you triggered yourself, from the Run dialog.
Watchdog imports👁How many recorded runs the watchdog started on its own.
Watchdogs active🐕A live “<active> / <total>”: your file sources with the watchdog switched on, out of all your file sources. Green when at least one is active, “—” until a status has loaded.
Last import🕒The age of the newest run: “just now” under 45 seconds, then “Nm ago”, “Nh ago”, “Nd ago”; “—” when there are none. While a run is in flight it reads running… in the accent colour.
Events pushed▦Total journey events written across the recorded history. Always green.
Events skipped⊘Total source lines that could not be parsed across the history. Orange whenever it is greater than zero.

The split between Manual imports and Watchdog imports exists because both write into the same tables through the same engine; without the split you could not tell an unattended import from one you started.

Tip Treat Events skipped as your correctness signal. A run that reports thousands of events written and thousands skipped almost always means the linked source type's regular expressions only fit part of the log. Open the source type and test its fields against a sample line from the file that is actually being read.
Warning If your deployment has switched the watchdog loop off entirely, the third tile's label changes to Watchdogs (off) and the tile turns orange. A source whose watchdog is “on” then never polls. The tile is deliberately loud about this, because the alternative is a count that quietly does nothing.
Note Every tile except Watchdogs active is computed from the console's own recorded run history, not from the backend. They therefore survive a backend restart, and they are reset by ↺ Clear — see Clearing the history.

The ingestion pipeline flowchart

The canvas below the status card draws your whole ingestion behaviour as one accumulating graph, in four columns:

[Source type] ──▶ [Source] ──▶ [Abstraction layer] ──▶ [Connection]

Nodes accumulate across runs

This is not a picture of the last run. Nodes are reused: there is one node per distinct source-type name, one per source name and one per destination connection name, with the Abstraction layer as the single hub in the middle. Edges are drawn for whatever combinations have actually run, so several sources, types and destinations fan in and out of the hub. Over a few days the chart becomes a portrait of how data really reaches your database — which is exactly what it is for.

Every run that has actually started is recorded, whichever way it was triggered: a manual run from the Run dialog, a watchdog poll, or a push through the API. The entry for a run in flight updates in place as the poll progresses.

Row counts

The Source and Connection nodes each carry a line reading ▦ <n> rows imported. This is the cumulative total across every recorded run that touched that node — not the last run's figure. Reading across the chart therefore tells you how much each file has contributed and how much has landed in each destination database.

The hub itself shows either a live state — “Running”, with real progress once the totals are known and an indeterminate animation before that — or, between runs, <total> rows over <n> run(s). With an empty history it simply reads “Idle”.

Colour and state

Each node is tinted with a semi-transparent wash of its own accent colour — purple for a source type, accent blue for a source, the current phase colour for the layer, teal for a connection. The wash is 14 % opaque in light mode and 20 % in dark, so the canvas dot-grid shows through and the chart stays pastel rather than solid.

StateAppearance
RunningThe wash deepens to 24 % (30 % in dark mode) and the node gains an accent ring
CompletedGreen-tinted border
FailedRed border
IdleReduced opacity

Edges take their colour from their own most recent run: green while it is running, red after a failure, blue otherwise. While a run is live, a single animated dot travels the run's path node by node in order — type, source, layer, connection — taking roughly 0.9 seconds per edge and looping until the run ends. Because edges remember their last outcome individually, a red edge tells you precisely which combination failed even when a later run of a different source succeeded.

Before anything has run, the canvas shows a dim idle skeleton — a generic “Source type” feeding a generic “Source”, the layer, and either the connection you are currently connected to or “(no connection)” — so the pipeline's shape stays visible from the first visit.

Moving, resizing and resetting the canvas

The automatic arrangement is a starting point, not a constraint. You can lay the graph out to match how you think about your data flows.

  1. Drag a node to move it. The position is saved for you personally and survives polls, page reloads and backend restarts.
  2. Drag the background to pan the canvas. Zoom is limited to between 0.3× and 1.5×, and scroll-wheel zoom is switched off so that scrolling the page over the canvas behaves normally. Nodes cannot be selected or wired together — the graph is a readout, not an editor.
  3. Drag the grip strip along the bottom edge of the canvas (tooltip “Drag to resize the canvas”) to change its height, anywhere between 520 px and 1400 px. The height is saved for you as well.
  4. Click ⤢ Reset layout in the top right to discard both the saved positions and the saved height and return to the automatic arrangement. The button appears only once you have moved a node or resized the canvas.
Note The canvas also grows by itself as the number of node rows increases, and a height you dragged is never allowed to shrink below what the current rows need — so adding a fifth source cannot push nodes out of sight.

The run history and clearing it

The live status only ever describes the most recent run, so the console keeps its own list, appending each run as it starts. The header above the canvas reads Ingestion pipeline with the caption “no imports yet” or “<n> run(s) · behaviour over time”. The list is capped at 50 runs; older entries drop off and the caption then reads “50+ runs”.

  1. Click ↺ Clear next to the caption (tooltip “Clear the ingestion history”). The button appears only when runs have been recorded.
  2. The confirmation dialog Clear ingestion history asks: “Reset the pipeline flowchart, removing all <n> recorded run(s)? This only clears the console view — nothing already imported is affected.”
  3. Click Clear history. The flowchart returns to its idle skeleton and all KPI tiles except Watchdogs active return to zero.
Warning The run history, the node layout and the canvas height are stored in your browser's local storage, per user and therefore per browser profile. Signing in from a different machine shows that machine's history, which may be empty; a browser with storage disabled keeps nothing at all. None of this affects the database — clearing the history deletes no imported data, and losing the history loses no rows.

How the pieces work together

A run started in the Run dialog is the same run the status card reports, the same run that lights up the pipeline, and the same run the KPI tiles count — they are three views of one live status poll, updating together in real time. That is worth knowing when something looks wrong: if the Run dialog shows progress but the pipeline does not, the problem is the browser, not the import; if the status pill says Failed and an edge on the canvas has turned red, both are telling you about the same failure, and the message is on the status card and in the Run dialog's checkpoint panel.

With the surface understood, the remaining integration chapters build on it in the order you will use them: define a source type, define a source that uses it, then run the import and — where the data keeps arriving — hand the job to the watchdog.
