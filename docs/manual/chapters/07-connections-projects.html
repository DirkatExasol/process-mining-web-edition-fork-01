7 Connections and Projects

A connection is the app's definition of one Exasol database, one schema inside it, and — optionally — one LLM server. Everything you analyse comes out of a connection, so the Connections section of the sidebar is where every session begins. This chapter explains how to connect and disconnect, how to read the status indicators, and, for users who are allowed to manage connections, how to create and edit a connection definition field by field, test it, provision its schema, load ready-made demo data into it, and delete projects from it. If you only ever pick a connection from a list that someone else prepared for you, sections 7.1 to 7.3 are all you need; the remainder requires the Power user, Developer or Administrator role.

The Connections section

Connections is the first accordion section of the sidebar and the one that is open when the app starts. Its header shows the number of connections available to you in parentheses — for example Connections (3) — and the count is omitted when it is zero. Opening any other sidebar section collapses this one; only one section is open at a time.

Empty states and errors

When the list is empty the message depends on your role:

  • Connection managers see “No connections yet. Use ＋ above to create one and assign users.”
  • Everyone else sees “No connections assigned to you. Ask an administrator to grant access.”

The most recent connection error is printed in red beneath the list, or inside the empty state. A failed connect additionally raises an alert titled Connection Failed carrying the error text and the buttons Retry and Cancel; Retry re-attempts the same connection. Unexpected API failures raise the same title with a single OK button.

Connecting and disconnecting

  1. Open the Connections section in the sidebar.
  2. Click the card of the database you want to work with. There is no separate “Connect” button — the card is the button.
  3. Wait for the database dot to turn green. The sidebar then opens the Projects section automatically and loads the project list.
  4. To disconnect, click the card you are connected to. To switch databases, click a different card: the app disconnects from the current one first, then connects to the new one.
Warning Disconnecting clears the whole session state — the selected project, all filters, and the loaded graphs. It does not sign you out of the application; your identity, saved presets and personal settings are untouched.

Each signed-in user gets their own database session. Two users never share a live connection, so one person's queries and results can never leak into another's. Because the Exasol driver is synchronous, all of your queries are serialised: two long-running queries you start yourself queue behind one another, while queries from different users run in parallel.

Ownership versus assignment

The two concepts are independent and it is worth keeping them apart:

Ownership
The user who created the connection becomes its owner. Ownership decides who may manage the definition — edit it, delete it, test it, provision it, generate demo data into it, and delete projects from it. A power user or developer owns only what they created; an administrator manages every connection regardless of owner.
Assignment
The list of users who may use the connection, ticked in the editor's Assigned users list. Assignment decides whose sidebar the connection appears in. It grants no management rights whatsoever.

When you create a connection you are made its owner and are auto-assigned to it, even if you leave your own name unticked in the Assigned users list — otherwise you could build a connection you are unable to open.

The backend enforces both gates independently and will answer with these messages verbatim: “You are not allowed to manage connections.”, “You cannot edit this connection.”, “You cannot delete this connection.”, “You cannot manage this connection.”, “You cannot re-assign this connection.” and “Connection not found.”

The Connection Editor

Requires: Power user, Developer or Administrator (and ownership of the connection, unless you are an administrator)

The editor is a wide modal sheet marked with the ⛁ icon and titled either New Connection or Edit Connection. Pressing Esc, clicking ✕, or clicking outside the sheet closes it without saving. It has two or three tabs: Database / LLM Details, Demo Content, and — only when editing an existing, already-saved connection — Projects.

The footer is visible from every tab and holds Test, the test result text, Delete (edit mode only, red), Cancel and Save. Save validates that a name has been entered; otherwise “Name is required.” appears in red at the top of the sheet. Any error the backend returns is shown in the same place.

Warning Saving any change to a connection immediately disconnects every user currently connected through it; they must reconnect against the new definition. The same applies when you change its assignments or delete it. This is intentional: a revoked assignment has to take effect at once, not at the end of somebody's session.

Write-only secrets

The Password and API key fields never reveal what is stored. When a secret exists the placeholder reads “•••••• (unchanged)”. The rules are the same for both fields:

  • Leave the field untouched and the stored secret is kept.
  • Type a value and it replaces the stored secret.
  • Deliberately clear the field to empty and the stored secret is erased.
Warning Test, Create schema & tables and demo generation all authenticate with the password typed into the sheet, never with the stored one. On a saved connection with a blank password field, the database test runs with an empty password and normally reports an authentication failure even though the saved connection itself works perfectly. Re-enter the password before using any of those three buttons.

TLS and certificate modes

With Use TLS unticked, the database link is not encrypted at all. Ticking it reveals the certificate settings:

Certificate modeBehaviour
Verify (system trust store)Default. The server certificate must validate against the system trust store, and the host name must match.
Pin fingerprintThe driver pins the server certificate to the SHA-256 fingerprint you enter. Colons are stripped, and the remainder must be pure hexadecimal, 16 to 128 characters long.
Accept any (insecure)Disables certificate verification and host name checking. For laboratory and self-signed setups only.

Mode handling fails closed. Any stored value the app does not recognise — a typo, a legacy record, restored data — is treated as Verify, never as “no verification”. In the same spirit, selecting Pin fingerprint without a valid fingerprint refuses to connect rather than silently falling back:

This connection is set to pin a certificate fingerprint, but the
fingerprint is missing or not hexadecimal. Enter the server's SHA-256
fingerprint, or change the certificate mode.
Note Minimum RSA key size is stored with the connection and carried through connect, test, provisioning, demo generation and rebuilds for compatibility with connection records created by the macOS edition, but the web backend does not currently enforce it. Do not rely on it as an active security control.

The LLM section

The LLM section is optional. When a Server URL is set, the app probes it at connect time and during every test by requesting GET <serverURL>/models, sending Authorization: Bearer <API key> when a key is stored, with a 5-second timeout. The server counts as reachable unless the request errors or answers with HTTP 500 or above — a 4xx still means a server is there. The user-visible failure text is always “LLM server not reachable.”; the underlying cause is logged under the operation llm-test.

Because the URL is user-supplied it passes an SSRF guard before any request is made. Only http:// and https:// are accepted, the host must resolve, and every resolved address is checked; link-local and cloud-metadata addresses (such as 169.254.169.254), multicast, reserved and unspecified addresses are always refused. Loopback and private RFC 1918 addresses are permitted by default, because local model servers are a first-class use case. The outbound connection is pinned to the vetted address and redirects are disabled. A refusal is not shown as an error — the LLM simply reports as unreachable, and the reason is logged.

Testing a connection

  1. Open the connection in the editor and go to the Database / LLM Details tab.
  2. Re-enter the database Password (and the LLM API key, if you want the LLM half of the test to be authenticated).
  3. Click Test in the footer.
  4. Read the result text beside the button.

The result is colour-coded: green when everything tested succeeded, orange when one of two components failed, red when everything failed. The database half reads “Database OK” or “Database: <error>”. When an LLM URL is configured, the LLM half is appended after a “ · ” separator and reads “LLM OK (N models)” — the model count is omitted when it is zero — or “LLM: <error>”.

Tip The test opens a throwaway database session and closes it again immediately. It never touches your own live session or anybody else's, so it is safe to run at any time — including while other users are working through the same connection.

Creating the schema and tables

Requires: a database account permitted to CREATE SCHEMA and CREATE TABLE

The boxed panel on the Database / LLM Details tab holds the Create schema & tables button and this explanation:

Creates the “<schema>” schema and the process-mining tables (PROJECTS, JOURNEYS, STEPS, METAS, NOTES) if they don't exist. This needs a database account permitted to CREATE SCHEMA and CREATE TABLE — only your database administrator can grant those rights; the app cannot. Uses the credentials entered above.

  1. Enter Host, Port, Username, Password and Schema. The button stays disabled while the Schema field is blank or an operation is already running.
  2. Click Create schema & tables.
  3. On success a green line appears to the right of the button: “Created: <list>”, naming the schema and each table that was created.
  4. On failure a red error line appears, with the fallback text “Could not create the schema.”

Provisioning connects without opening a schema (the target may not exist yet), then issues CREATE SCHEMA IF NOT EXISTS, OPEN SCHEMA, and the table definitions in the order PROJECTS, JOURNEYS, STEPS, METAS, NOTES. Everything uses IF NOT EXISTS, so the operation is idempotent and re-running it never disturbs existing data. If a step fails part-way, the reported list still names everything that was created before the failure, so you can see how far it got. A blank schema name produces “A schema name is required.”

Note The schema identifier is quoted safely, so mixed-case and special-character names work — but remember that a quoted identifier is case-sensitive in Exasol. Type the schema name exactly as it must exist.
Warning Because provisioning uses IF NOT EXISTS, it never alters a table that is already there. If JOURNEYS already existed before the app saw it, the performance layout the app would have declared (DISTRIBUTE BY EVENT_ID, PARTITION BY EVENT_TIME) is not applied. A database administrator must apply it manually with ALTER TABLE JOURNEYS DISTRIBUTE BY EVENT_ID; and ALTER TABLE JOURNEYS PARTITION BY EVENT_TIME;

Generating demo content

Requires: a database account permitted to CREATE SCHEMA, CREATE TABLE and INSERT

The Demo Content tab loads a complete, realistic dataset into the connection's schema so that you can explore every feature of the app without waiting for a customer extract. It creates the schema and tables if they are missing, then writes the journeys. It uses the credentials on the Database / LLM Details tab — including the typed password.

Three datasets are offered, grouped under the headings Retail, Finance/Insurance and Transportation:

  1. Open the connection in the editor, re-enter the database Password on the Database / LLM Details tab, then switch to Demo Content.
  2. Check the Schema field in the dataset panel. It is the same value as the Schema field on the details tab — editing it in any demo panel changes the connection's schema draft everywhere.
  3. Set Journeys. The default is 500; the field accepts 1 to 20,000 and is typed rather than stepped.
  4. Click Generate. The button reads “Generating…” with a spinner while it runs and is disabled while busy, while the schema is blank, or while the journey count is below 1.
  5. Read the result line: green for success, with the fallback text “Created N journeys.”, or red for failure, with the fallback “Could not generate demo content.” The full success message is Created N journeys for "<title>" in <SCHEMA>.JOURNEYS.
  6. Connect to the database and open the new project from the Projects section.

Event times are spread randomly across 1 January 2024 08:00 to 31 December 2024 22:00, so the generated data always falls in a fixed, predictable window. Each EVENT_ID is the MD5 hash of a synthetic key — ORD-000001, ORD-000002, … for the bookstore, CRA-000001… for credit applications, and FLT-000001… for flights — which is why event identifiers look like long hexadecimal strings in the Individual Journey view and in its autocomplete suggestions.

Other error messages you may see: “Unknown demo dataset '<x>'.”, “A schema name is required.” and “Enter how many journeys to generate.” (when the count is below 1), plus the ordinary connection errors listed in section 7.2.

Note If the connection uses pre-materialised transitions, generated data does not rebuild the TRANSITIONS_RAW table. Until an administrator rebuilds it, the chart header shows the pill ⚠ Live (not built) and the map is computed live. That is a performance matter only — the results are identical.

Managing the projects in a connection

Requires: Power user, Developer or Administrator, plus ownership of this connection (administrators may manage all)

The Projects tab exists only when you are editing a connection that has already been saved; a brand-new, unsaved connection has no Projects tab. It reads the schema with the connection's stored credentials — this is the one operation in the editor that does not need you to retype the password.

The tab's description reads: “Projects stored in the “<schema>” schema, with their journey and event counts. Deleting a project clears its rows from every table (PROJECTS, JOURNEYS, STEPS, METAS, NOTES, TRANSITIONS_RAW) — this cannot be undone.”

The list loads automatically the first time you open the tab and can be reloaded with ↻ Refresh. While loading it shows “Loading projects…” with a spinner; when the schema holds nothing it shows “No projects found in this schema.”; on failure it shows the backend message in red, or the fallback “Could not read the projects for this connection.”

Each row shows the project title — with the raw project ID printed underneath when the two differ — then “N journeys”, “N events”, and a red Delete button.

Note The counts consider ORIGINAL data only; sample sets are excluded. “Journeys” is the number of distinct EVENT_IDs and “events” is the number of rows. A project is listed if it appears in either PROJECTS or JOURNEYS, so orphaned rows on one side are still visible. A project with no title displays its PROJECT_ID instead. Missing tables are tolerated: before provisioning you get an empty list rather than an error.

Deleting a project

  1. Open the connection in the editor and switch to the Projects tab.
  2. Confirm the counts on the row — they are your last sanity check on which project you are about to erase.
  3. Click Delete on that row.
  4. Read the confirmation dialog Delete project?: “<title>” (N journeys, M events) will be cleared from PROJECTS, JOURNEYS, STEPS, METAS, NOTES and TRANSITIONS_RAW in this schema. This cannot be undone.
  5. Click Delete project to proceed, or Cancel to abandon. A failure shows the backend message or “Could not delete the project.”

The deletion runs one DELETE … WHERE PROJECT_ID = '<id>' per table, children before parents, in this order:

OrderTableWhat is removed
1JOURNEYSEvery event row of the project — including every sample set, because no SAMPLE_SET filter is applied.
2STEPSAll step presentation and scoring rows: colours, scores, shapes, groups, step notes.
3METASThe project's meta-attribute titles.
4NOTESEvery note attached to a node or edge of the project, from every author.
5TRANSITIONS_RAWThe pre-materialised transition pairs, when that optional table exists.
6PROJECTSThe project row itself.

Tables that do not exist are skipped rather than treated as errors — NOTES may never have been created, and TRANSITIONS_RAW is optional — and the response reports exactly which tables were actually cleared, together with the project's pre-deletion counts. Blank inputs are refused with “A schema name is required.” or “A project id is required.”, and a permission failure with “You cannot manage this connection.” or “Connection not found.”

Warning Project deletion is permanent. There is no undo, no recycle bin and no automatic backup, and it takes every note written about that process with it. If the notes matter, export or copy them first. Every deletion is written to the administration audit log, recording who deleted which project from which connection.

Assigning users to a connection

Requires: Power user, Developer or Administrator (owner of the connection, or any administrator)
  1. Open the connection with ✎ Edit connection, or create a new one with ＋.
  2. Scroll to the Assigned users section at the foot of the Database / LLM Details tab.
  3. Tick every user who should see and use this connection. The list contains every enabled account; if there are none it reads “No users available.”
  4. Click Save.

Assignment changes take effect immediately, in both directions. A newly ticked user finds the connection in their sidebar on their next refresh. A user you untick is disconnected on the spot: their live session is dropped and the connection disappears from their list. Attempting to reconnect to it produces “This connection is not available to you.”

Tip Because saving an edit kicks everyone off the connection, batch your changes. Adjust the endpoint, the LLM settings and the assignment list in one editing session and save once, rather than saving after each individual change.

Deleting a connection

  1. Open the connection with ✎ Edit connection.
  2. Click the red Delete button in the sheet footer.
  3. Read the confirmation Delete connection?: “<name>” will be removed for all assigned users. This cannot be undone.
  4. Click Delete to confirm, or Cancel. A backend failure shows “Delete failed.”

Deleting a connection first drops every live session on it, then removes the definition — including its stored secrets and, where one exists, its scripted-rebuild token and materialisation status.

Note Deleting a connection removes the app's definition of the database. It does not touch the database itself: the schema, its tables and all their data remain exactly as they were. To erase data you must delete the projects first, from the Projects tab described above.
