5 Signing In, Sessions and Security

This chapter explains how you get into the Process Mining Demonstrator and how you stay in. It covers password sign-in on all three browser surfaces — the main application, the integration console and the admin interface — together with two-factor authentication using an authenticator app, passkeys (Touch ID, Windows Hello, security keys), how long a session lasts, what happens when it ends, and what the system does after repeated failed attempts. It closes with the full role capability matrix and a catalogue of every message you may see on a sign-in screen. Read the first three sections if you only need to sign in; read the rest if you administer accounts or are troubleshooting an access problem.

5.1 The three surfaces and who may sign in

The product presents three separate web surfaces. Each has its own session cookie and its own access rule. Signing in on one surface does not sign you in on the others: the cookies are audience-bound, so an application cookie is never accepted by the integration console or the admin panel, and vice versa.

All session cookies are HttpOnly, use SameSite=Lax, are marked Secure when the surface is served over HTTPS, and are scoped to path /.

The main application and the integration console share the same sign-in panel; the only visual difference is that the integration console adds a second title line, Integration, beneath Process Mining Demonstrator. The admin sign-in is rendered by the admin server itself but deliberately mirrors the same panel, with the second title line Administration; its page title is "Administration — Sign in".

All three sign-in panels show a small release label beneath the caption (for example V0.95 — Milford Sound). It is read from the top-level VERSION file — edit that one line to change the label everywhere, or override it with the PMW_APP_VERSION environment variable. It is display-only and never affects behaviour.

Note The first start of a new installation seeds a built-in administrator with the username Administrator and the password Administrator (both overridable with the environment variables PMW_DEFAULT_ADMIN_USER and PMW_DEFAULT_ADMIN_PASSWORD). Until that password is changed, the admin dashboard displays the banner "⚠️ The Administrator account is still using its default password. Change it now in 👤 Profile (top right)." Changing the password clears the banner permanently.
Warning An administrator can switch the integration console off entirely (Admin → Integration tab → Enable the integration console). While it is off, browser navigations to that surface receive a 503 page headed Console unavailable with the text "The integration console has been turned off by the administrator."; programmatic calls receive the same text as JSON.

Signing in

  2. Type your Username.
  3. Type your Password.
  4. Press Sign in (or Enter).

When a sign-in fails, the message appears in the red box, the password field is cleared and the username is kept, so you can retype the password without retyping your name.

The integration console role gate

Requires: Developer or Administrator

On the integration console the role check runs before any second factor. A correct password from an account that is neither a developer nor an administrator is refused with "You need the Developer role to use the integration console. Ask an administrator to grant it." — no code step is offered. Power users are refused in exactly the same way; the power role grants nothing here.

If the Developer role is revoked while you are working, the console does not wait for your session to expire: your next request drops you to an Access denied screen reading "The integration console is available to developers and administrators only. Ask an administrator to grant you the Developer role.", with a ⏻ Sign out button.

Directory (LDAP) accounts

When a directory server is configured and enabled, the application and integration sign-in also accept directory accounts. Local accounts are always checked first, so a local break-glass account can never be taken over by a directory identity that happens to share its name.

Directory users are provisioned on their first successful sign-in as ordinary enabled local rows marked ldap. Administrator rights are never granted from the directory — a local administrator must promote the account. Directory users have no local password, so the failed-sign-in lockout counter does not apply to them, and the admin Users tab hides Reset password on their rows.

5.3 Signing in to the admin interface

Requires: Administrator
  1. Open the admin interface (by default port 8090, or 8453 over HTTPS). Visiting / without a session redirects you to /login; visiting /login with a valid session redirects you to the dashboard.
  2. Enter your Username and Password and press Sign in.
  3. Complete the authentication code step or the forced enrolment step if your account requires them (sections 5.4.3 and 5.4.4).
  4. You arrive at the admin dashboard.

To leave, press Log out in the top-right corner, next to 👤 Profile. You are returned to /login.

Note Bad credentials and valid credentials belonging to a non-administrator produce the same message here: "Invalid credentials, or the account is not an administrator." This is deliberate — the page never reveals whether a username exists or which of the two conditions failed.

Directory accounts can sign in to the admin panel only when Also allow directory sign-in to this admin interface is enabled and the account has been locally promoted to administrator. The 🔑 Sign with Passkey button appears on this page only when the browser supports WebAuthn and you reached the panel by a usable hostname; it is hidden entirely when you reach the panel by IP address.

Adding ?inactivity=1 to the login URL — which is what the idle watcher does — shows the same orange "You were signed out due to inactivity." notice.

5.4 Two-factor authentication (TOTP)

5.4.1 How it works

Two-factor authentication adds a six-digit time-based one-time code on top of your password. It never replaces the password. Two independent facts govern it for each account:

Allowed
An administrator has ticked the per-user 2FA checkbox in the Users tab (or the all-users master checkbox). This means two-factor applies to the account.
Enrolled
You have scanned the QR code and confirmed a code, so a secret is stored for your account (encrypted at rest).

The login gate is allowed and enrolled. The consequences are worth understanding:

AllowedEnrolledWhat happens at your next sign-in
NoNoPassword only.
YesNoEnrolment is forced. The password step succeeds but no session is issued until you finish enrolling.
YesYesPassword, then a six-digit code or a recovery code. A passkey sign-in skips the code step entirely.
NoYesPassword only. The secret is kept, not deleted — re-ticking 2FA re-arms the same authenticator without re-enrolment.
Warning Allowing 2FA for a user is the same as making it mandatory for that user. They cannot decline: their next sign-in on any surface stops after the password and forces enrolment.

One secret protects all three surfaces. Codes are six digits on 30-second steps with one step of clock-skew tolerance either side; spaces in a typed code are ignored. Your authenticator app labels the entry with the issuer Process Mining Demonstrator (overridable with PMW_MFA_ISSUER). Any standard authenticator works — Google Authenticator, 1Password, Authy and equivalents.

5.4.2 Setting up two-factor yourself

Requires: two-factor allowed for your account by an administrator

In the main application and the integration console, the sidebar footer shows a 🔒 Two-factor button (tooltip "Manage two-factor authentication"). It is visible only when an administrator has allowed 2FA for your account.

  1. Press 🔒 Two-factor in the sidebar footer. The Two-factor authentication sheet opens.
  2. Press Set up authenticator. A QR code appears with the instruction "Scan this with your authenticator app, then enter the 6-digit code it shows."
  3. Scan the QR code with your authenticator app. If your device cannot scan, use the line "Can't scan? Enter this key manually:" and type the key shown.
  4. Type the six-digit code your app displays into the field marked with the placeholder 6-digit code and press Confirm. A wrong code gives "That code didn't match. Try again." — the QR code and secret stay valid, so you do not need to rescan.
  5. The recovery block appears, headed Save your recovery codes. Press Copy codes or write them down, then press Done.

On the admin interface the same functions live in the 👤 Profile overlay, section Two-factor authentication, with the banner states "Two-factor is on. N recovery codes left.", "Two-factor is off for your account." and "Two-factor is not enabled for your account — enable it in the Users tab first." Its buttons are Set up authenticator, Regenerate recovery codes and Turn off, and it confirms with the toasts "Two-factor enabled", "Recovery codes regenerated" and "Two-factor turned off".

5.4.3 Signing in with a code

  1. Enter your username and password as usual and press Sign in.
  2. The panel switches to the caption "Enter your authentication code" with the field Authentication code (placeholder "6-digit code or a recovery code").
  3. Type the current code from your authenticator app, or one of your recovery codes, and press Verify.

Back returns you to the username and password step and clears both the code and the password. On the admin interface the code step is a plain form with a Verify button and no Back button — reload /login to start again.

Note You have 5 minutes after the password step to enter the code. The state is carried by a short-lived signed cookie, not a session — no session exists until the code is accepted. After 5 minutes you see "Your sign-in session expired. Start again." (the admin wording is "Your sign-in session expired. Please start again.") and must re-enter your password.
Tip Wrong codes are throttled per source IP but never count towards the account lockout. A mistyped or expired code can never disable your account.

5.4.4 Mandatory enrolment at sign-in

If an administrator has allowed 2FA for your account and you have not yet enrolled, the sign-in panel switches after the password step to the caption Set up two-factor to continue.

  1. Read the text "Two-factor is required for your account. Scan this with an authenticator app (Google Authenticator, 1Password…), then enter the 6-digit code." While the QR code is being fetched, a spinner shows Preparing…
  2. Scan the QR code, or use the "Can't scan? Key:" line to enter the secret manually.
  3. Type the code into the 6-digit code field (placeholder "123456") and press Confirm & sign in. On the admin interface the button is the same and success leads straight to the recovery-codes page.
  4. Your session is issued, but the panel stays up for one more screen headed Two-factor is on — save your recovery codes. Press Copy codes, store them, then press Continue to enter the application. On the admin interface, follow the Continue to the admin panel link.

Back abandons enrolment and no session is issued. Nothing is stored on the server until a code confirms the authenticator, so an abandoned enrolment leaves no half-configured account behind. The QR code and secret are valid for 10 minutes; after that you see "Setup expired. Start again."

5.4.5 Recovery codes

Each set contains 10 codes in the form a1b2c3d4-e5f6g7h8 — lower case, with look-alike characters avoided. Each works exactly once. They are stored only as salted hashes, so nobody, including an administrator, can read them back.

You may type a recovery code anywhere a TOTP code is accepted: at the sign-in code step and in the turn-off confirmation. Dashes, spaces and letter case are ignored.

Warning Recovery codes are displayed exactly once, at setup or regeneration. Generating a new set with Regenerate recovery codes replaces the previous set entirely — every old code stops working immediately.

5.4.6 Turning two-factor off

  1. Open the Two-factor authentication sheet from the sidebar footer. The status row reads "✅ Two-factor is on. N recovery code(s) left."
  2. Press Turn off. You are asked: "Enter your current code (or a recovery code) to turn two-factor off."
  3. Type a current code into the field (placeholder "Current code") and press Confirm off.

The re-authentication is deliberate: it stops someone who has hijacked an open session from silently stripping the second factor. A wrong code gives "Enter your current authentication code to turn off two-factor." Turning 2FA off deletes both the secret and all remaining recovery codes. On the admin interface the equivalent control prompts "Enter your current authentication code (or a recovery code) to turn off two-factor:".

5.4.7 If you lose your authenticator

There are two routes back in:

  1. Sign in with your password and enter one of your recovery codes at the code step.
  2. If you have no recovery codes left, ask an administrator to untick the 2FA checkbox on your row in the Users tab. Your password alone then works again and you can re-enrol from scratch.
Note There is no administrator function that resets your two-factor while preserving enrolment. Unticking the permission relaxes the requirement but leaves the old secret in place; if the administrator re-ticks it before you re-enrol, your lost authenticator is re-armed and you are back where you started. Turn 2FA off from the sheet first (which deletes the secret), then enrol again.

5.5 Passkeys (WebAuthn)

5.5.1 What a passkey is here

A passkey lets you sign in with Touch ID, Windows Hello or a hardware security key instead of typing a password. It is an alternative to the password, never a replacement: your password always remains a fallback.

Requires: passkeys allowed for your account by an administrator

An administrator controls this with a per-user Passkey checkbox in the Users tab and an all-users master checkbox. Both local and directory accounts may be allowed. Turning the permission off blocks passkey sign-in immediately — the check runs at every step — and hides the management controls.

A passkey registered on a host works on all surfaces of that host: the application, the integration console and the admin panel share the same relying-party identifier, which is the hostname without the port.

Warning A passkey sign-in satisfies two-factor by itself. Even for an account enrolled in TOTP, no code step is shown after a successful passkey ceremony — the passkey counts as strong authentication on its own. If your organisation requires a TOTP code on every sign-in, do not allow passkeys.

5.5.3 Enrolling a passkey

  1. Sign in with your password.
  2. Press 🔑 Passkeys in the sidebar footer (tooltip "Manage passkeys for this account"). The Passkeys sheet opens; with none registered it reads "No passkeys registered yet."
  3. Type a name in the field marked Name (e.g. MacBook Touch ID). The name is capped at 60 characters and defaults to "Passkey" if you leave it empty.
  4. Press Add a passkey and complete the ceremony your operating system or browser presents.
  5. The passkey appears in the list with its name and "Added" date and time.

On the admin interface, use 👤 Profile → Passkeys, the field Passkey name (placeholder "e.g. MacBook Touch ID") and the button Add a passkey. Toasts confirm with "Passkey added" and "Passkey removed".

To remove a passkey, press Remove on its row (tooltip "Remove this passkey"). There is no confirmation prompt.

Note If your device already holds a passkey for this account you see: "A passkey for this account already exists on this device. If it isn't shown in the list here, remove it from your device's passkey settings (iOS: Settings → Passwords) and try again."

5.5.4 Signing in with a passkey

  1. Type your Username on the sign-in panel. The passkey button stays disabled until you do.
  2. Press 🔑 Sign with Passkey. Leave the password field empty.
  3. Complete the biometric or security-key prompt. You are signed in — with no code step, even if your account uses TOTP.

A challenge is valid for 5 minutes; after that you see "Passkey challenge expired. Try again." Replay is prevented by signature counters. Cancelling the browser or operating-system prompt is treated as a silent cancellation — no error is shown.

Note Asking for a passkey challenge for an unknown or ineligible username produces an indistinguishable decoy challenge, so the sign-in page cannot be used to discover which usernames exist. Your device then finds no matching passkey and the browser cancels, which looks exactly like a user cancellation.

5.6 Sessions, idle sign-out and session lifetime

5.6.1 How long a session lasts

Session tokens are stateless signed cookies, re-minted on every authenticated request (including the background session polls). Each token carries your username, your personal session epoch, the surface it belongs to, and the time of your original sign-in — the last of which is carried through every refresh.

LimitValueSetting
Idle window (application / integration), when no idle timeout is configured12 hoursPMW_SESSION_TTL (seconds)
Idle window (admin), when no idle timeout is configured8 hoursPMW_ADMIN_SESSION_TTL (seconds)
Idle window when an idle timeout is configuredEquals the configured timeout, sliding on activityUsers tab / App Control tab
Absolute session lifetime, all three surfaces7 days from the original sign-inPMW_SESSION_MAX_LIFETIME (seconds)
Warning The absolute lifetime is not a sliding window. Seven days after you first signed in, the session dies even if you have been working continuously, and you must sign in again.

Every request also re-validates the live user record. If your account is disabled or deleted, the session is dead at once. If a role that gates the surface is revoked, the session is dead on that surface immediately.

5.6.2 Idle sign-out

Requires: Administrator to configure

Two separate settings govern idle sign-out.

  1. Open the admin interface and go to the Users tab.
  2. Set Auto sign-out after [N] minutes of inactivity — accepted range 0 to 1440, where 0 disables the feature.
  3. Save. The hint below the field confirms the effect: "Idle sessions are signed out after N min." or "Disabled — sessions never time out on inactivity."

In the main application, an invisible watcher observes mouse movement, mouse clicks, key presses, touches, scrolling and wheel events. After N idle minutes it signs you out and the sign-in panel shows "You were signed out due to inactivity." While you are active it pings the session endpoint — at most once every 15 to 60 seconds — so the server-side sliding window stays alive even during long stretches without API calls. The watcher runs only when sign-in is required, a user is signed in, and N is greater than zero.

Warning The integration console honours the same idle value on the server side, so its session expires after N idle minutes — but it has no client-side watcher. You are not bounced to a sign-in screen; instead your next action simply fails authentication. Expect this if you leave the console open in a background tab.

The admin interface has its own, independent setting.

  1. Go to the App Control tab and find the card Admin session — "Automatically sign out of this admin interface after a period of inactivity. This is separate from the main app's auto sign-out (set in the Users tab)."
  2. Set Auto sign-out after [N] minutes of inactivity.
  3. Press Save. The toast reads "Admin auto sign-out updated" and the hint becomes "You are signed out of this admin after N min idle." or "Disabled — the admin session never times out on inactivity."

The admin watcher mirrors the application's and redirects you to /login?inactivity=1.

5.6.3 Signing out — and what else it ends

⏻ Sign out in the application and integration console sidebar footer, and Log out in the admin interface, do more than delete the local cookie. They bump your session epoch on the server, which invalidates every outstanding session token of yours on all three surfaces.

Warning Signing out of the main application also kills your admin and integration sessions — they fail on their next request. This is intentional, but it surprises people who keep the admin panel open in another tab. Signing out also releases your per-user database connection on the backend.

5.6.4 Password changes invalidate sessions

Any password set or reset bumps the session epoch, so all of that user's sessions die.

You change your own password (admin Profile overlay)
Your current admin session survives — a fresh cookie is issued in the same response. Every other session of yours is invalidated.
An administrator resets someone else's password
That user is signed out silently at their next request and must sign in again with the new password.

5.6.5 When a session dies while you are working

API calls begin returning 401 with "Authentication required." The application surfaces this as an error, and reloading the page lands you on the sign-in panel. Two other server messages you may meet are unrelated to authentication but appear in the same place: "The compute backend is not reachable. Start it with ./run.sh or check PMW_BACKEND_URL." (502) and "The compute backend timed out." (504).

5.6.6 Resuming where you left off

The main application remembers your last working position and restores it automatically the next time it loads. When you sign in again — including after an idle sign-out — it reconnects to the database connection you were using, reopens the project you had open and returns to the view you were in (A-Chart, Statistics, A/B Comparison, and so on). The same restore happens on a plain page reload while your session is still alive.

The position is stored per user in your server-side settings, so it follows you between browsers and machines, exactly like your presets and layouts. It records only where you were — the connection, the project and the view — not any transient in-progress edits. A few natural limits apply:

  • If the saved connection has since been un-assigned from you, or the saved project no longer exists, that step is skipped silently and you land one level up (connected but no project, or signed in but not connected).
  • If the automatic reconnection fails — for example the database is down — the usual "Connection Failed" retry dialog appears, just as if you had clicked the connection yourself.
  • Explicitly pressing Disconnect clears the saved connection, so a deliberate disconnect is never silently undone on your next sign-in. (An idle sign-out does not count as a disconnect — that is exactly the case this feature is for.)

5.7 Account lockout and attempt throttling

5.7.1 Failed-sign-in lockout

Requires: Administrator to configure
  1. In the admin interface, open the Users tab.
  2. Set Disable an account after [N] failed sign-in attempts — accepted range 0 to 100, where 0 turns the feature off. Fresh installations default to 3.
  3. Press Save. The toast reads "Failed-sign-in lockout updated" and the hint becomes "Accounts (incl. the Administrator) are disabled after N failed sign-ins." or "Disabled — accounts are never locked on failed sign-ins."

The counter records consecutive wrong-password attempts against a local account, pooled across all three surfaces — they share one store. A successful sign-in resets it. The following do not count: wrong TOTP codes, failed passkey ceremonies, directory (LDAP) accounts, and accounts that are already disabled.

When the threshold is reached the account is disabled and flagged. Its row in the Users tab shows a locked pill (tooltip "Disabled after too many failed sign-ins — Unlock to restore.") and the action button reads Unlock.

Note Despite the admin hint's wording, the built-in Administrator is never auto-locked. Its failures are counted, but it is the break-glass account and must stay reachable; its protection is the per-IP throttle plus deliberately slow password hashing. Other administrator accounts do lock.

There are three ways back in:

RouteDetail
WaitA lockout lifts itself after 15 minutes. The expiry is applied lazily, at the next sign-in attempt, so simply trying again after the window works.
AdministratorPress Unlock (or Enable) on the user's row in the Users tab. This also clears the counter. Disabling and re-enabling an account clears it too.
Break-glass restartRestart the server with PMW_RESET_LOCKOUTS=1 to clear every lockout — for the case where your only non-built-in administrator is locked out.
Warning The 15-minute auto-expiry is a fixed value with no control in the admin interface. Only the threshold is configurable there.

5.7.2 Why the message is sometimes vague

The sign-in panel avoids telling an attacker whether a username exists. The specific reason for a refusal is shown only when the supplied password is correct:

  • Correct password, account auto-locked → "This account has been locked after too many failed sign-in attempts. Contact an administrator."
  • Correct password, account disabled by an administrator → "This account has been disabled. Contact an administrator."
  • Anything else — wrong password, unknown username, disabled account with a wrong password → the generic "Invalid username or password." (application and integration console) or "Invalid credentials, or the account is not an administrator." (admin interface).

The same principle governs the passkey path: a request for an unknown or ineligible account receives a decoy challenge rather than a refusal.

5.7.3 Per-IP throttle

Independently of the account lockout, all three surfaces throttle by source address. After 3 failures within 15 minutes from one IP, that IP must wait a 5-minute cooldown, measured from its last failure. The counter lives in memory in the serving process and is cleared by a restart, or by one fully successful sign-in from that address.

The throttle covers password sign-ins, TOTP verification, forced-enrolment confirmation, the 2FA turn-off re-authentication and, on the admin panel, passkey sign-in completion. The socket peer address is used; the X-Forwarded-For header is deliberately ignored, so a client cannot forge its way around the limit.

Messages differ slightly by surface: "Too many attempts. Try again shortly." on the application and integration console; "Too many failed attempts. Try again in about N seconds." on the admin login page (accompanied by a Retry-After header); "Too many failed attempts. Try again shortly." on the admin code and setup steps.

5.8 Single-user (open) mode

Requires: Administrator

For a single-user installation or a demonstration machine, sign-in on the main application can be switched off entirely.

  1. Open the admin interface and go to the Users tab.
  2. Untick Require sign-in for the main application. The toast reads "Access updated" and the hint changes from "Users must sign in." to "The app is open — no sign-in required."
SettingBehaviour
On (default)Every visitor sees the sign-in panel. All API calls require a session; without one they return 401 "Authentication required." Only the health probe is open.
Off (open mode)The application loads with no sign-in panel and no user identity at all.

In open mode:

  • Personal settings and filter presets are shared by everyone who uses the machine — there is one profile.
  • The sidebar authentication footer disappears: no name, no 🔒 Two-factor, no 🔑 Passkeys, no ⏻ Sign out.
  • The idle sign-out is inactive.
  • Power-user and administrator features are hidden in the interface and refused by the server — with no identity there is nothing to authorise, so those endpoints return 403.
  • Notes carry no author.
Note If the session probe itself fails at start-up, the application assumes open access so that it still loads rather than trapping you on a broken sign-in panel.

The integration console ignores this toggle and always requires sign-in, because it is role-gated. So does the admin interface.

The sidebar footer shows your identity as "👤 name (Role)" using the highest role you hold, in the order Admin > Power user > Developer > User. The admin Users tab instead shows a combined badge such as admin·power or power·dev, with tooltips "administrator", "power user (manages own connections)", "developer (integration console)" and "Regular user".

It does not confer power features — a developer who tries to use journey sampling is refused with "Journey sampling is available to power users and administrators only." — although developers can manage their own database connections.
  • Power does not open the integration console. Power users are refused there at the password step.

Role revocation is enforced live: the surface predicate is re-checked on every request, so a demoted user loses access on their next action rather than at their next sign-in.

Note The built-in Administrator cannot be disabled, demoted or deleted — attempts produce "The built-in Administrator account cannot be disabled.", "…must remain an administrator." and "…cannot be deleted." In addition, any change that would leave the installation with no enabled administrator is refused: "This would leave no enabled administrator. Promote or enable another admin first."

5.10 Administering accounts and permissions

Requires: Administrator

The Users tab carries the note "Only enabled users will be allowed to sign in to the main application." and holds the three global settings described above — require sign-in, application idle timeout and the failed-sign-in threshold — plus the per-user controls.

Filter chips All / Local / LDAP with counts and a search field ("Search users by name…") narrow the list; an empty result reads "No matching users."

The all-users master row

The master row is introduced by the sentence "Passkey and two-factor are optional alternatives/additions to the password (which always works)." It offers, under the label "All users:", a Passkey checkbox ("Allow every user to enrol and sign in with a passkey") and a 2FA checkbox ("Allow every user to set up two-factor (TOTP)"). Ticking either writes the flag for every existing user at once, confirmed by "Passkeys allowed/disabled for all users" or "Two-factor allowed/disabled for all users". Each checkbox reflects whether every user is currently allowed.

Warning The master checkboxes act on the users that exist at the moment you tick them. They do not set a default for users created later — you must tick the flag on new accounts yourself.

Per-user controls

Each user card shows the username and display name, a local or LDAP pill, the role badge, an enabled / disabled / locked pill, and the per-user Passkey and 2FA checkboxes ("Allow this user to enrol and sign in with a passkey" / "Allow this user to set up two-factor (TOTP)"). The second line shows "Last sign-in: …" followed by the action buttons.

5.12 Points to remember

  1. Enabling 2FA for a user enables mandatory 2FA. There is no opt-out and no grace period.
  2. A passkey sign-in bypasses the TOTP step by design. Do not allow passkeys if you require a code on every sign-in.
  3. Signing out anywhere signs you out everywhere, as does any password change or reset — except that an administrator changing their own password keeps their current admin session.
  4. Revoking the 2FA permission does not delete the enrolment; re-granting it re-arms the same authenticator. Only Turn off from the sheet deletes the secret and the recovery codes.
  5. Recovery codes are shown once. Regeneration invalidates every earlier code, and no administrator can retrieve them.
  6. Remember the three timers: 5 minutes to enter a code after the password, 10 minutes for an enrolment QR code, 5 minutes for a passkey challenge.
  7. Wrong codes never lock an account; wrong passwords do — three attempts by default, auto-unlocking after 15 minutes. The built-in Administrator never auto-locks, and PMW_RESET_LOCKOUTS=1 at start-up clears every lockout.
  8. The integration console has no idle watcher, always requires sign-in even in open mode, and refuses power users before any second factor.
  9. Open mode has no identity: shared settings and presets, unattributed notes, and no power features at all.
  10. The absolute 7-day session cap ends even a continuously active session.
