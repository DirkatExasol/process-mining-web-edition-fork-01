12 Administration: Overview, App Control and TLS

This chapter introduces the administration interface — the separate web surface from which the whole installation is configured — and then covers its first two tabs in full. You learn how to reach the panel and sign in, how its top bar and tab strip are laid out, what the profile menu does and why the default-password banner must be dealt with on day one. The App Control tab is then described in detail: installing and removing the licence, reading the licence status banner, understanding Demo Mode and the one-time grace countdown, and restarting the servers. The TLS / SSL tab follows: the three connection modes, generating a self-signed certificate, uploading a certificate of your own, activating one, and the fact that a single restart re-binds all three browser surfaces at once. The chapter is written for administrators; nothing described here is reachable by other users.

Requires: Administrator — every task in this chapter

12.1 Reaching the administration interface

The administration interface is not a page inside the main application. It is a separate server, on its own port, with its own sign-in and its own session cookie. This separation is deliberate: it lets you keep the admin panel off the network path that ordinary users take, and it means an ordinary application session can never be escalated into an administrative one.

SurfaceHTTP portHTTPS portEnvironment variables
Main application (the GUI)80808443PMW_FRONTEND_PORT / PMW_FRONTEND_HTTPS_PORT
Administration interface80908453PMW_ADMIN_PORT / PMW_ADMIN_HTTPS_PORT
Integration console81008463PMW_INTEGRATION_PORT / PMW_INTEGRATION_HTTPS_PORT

The integration console defaults to the admin ports plus ten. Which of the two port columns is live depends on the TLS mode described in section 12.6.

12.1.1 Signing in

  1. Open http://<server>:8090/ (or https://<server>:8453/ when TLS is required) in a browser. Visiting / without a session redirects you to /login.
  2. Type your Username. The Sign in button stays disabled until the username field is non-empty.
  3. Type your Password and press Sign in. The button shows a spinner while the request is in flight.
  4. If your account has two-factor authentication enrolled, the panel switches to the code step: enter the six-digit code (or one of your recovery codes) in Authentication code and press Verify.
  5. The dashboard opens on the App Control tab.

The sign-in page mirrors the main application's panel exactly; the only difference is the second title line, which reads Administration. Where a directory server is configured, a green or red LED with Directory server available / Directory server unavailable appears below the form; it is a cached probe and never blocks the page. A 🔑 Sign with Passkey button is shown only when the browser supports WebAuthn and you reached the panel by a real host name — passkeys cannot be bound to a bare IP address.

Note Only administrators may sign in here. A correct password belonging to a non-administrator produces exactly the same message as a wrong password — "Invalid credentials, or the account is not an administrator." — so the page never reveals whether an account exists. Directory (LDAP) accounts can sign in only if Also allow directory sign-in to this admin interface is enabled in the Directory tab and the account has been promoted to administrator locally. Local administrator accounts always work; they are the break-glass path.
Note Admin and application sessions are not interchangeable. The admin cookie is pmw_admin; it is bound to the admin surface and is rejected by the application and by the integration console, and vice versa. Signing in on one surface does not sign you in on the others. Conversely, Log out invalidates every outstanding session of that user on all three surfaces, not just the cookie in the current browser.

Sign-in attempts are throttled per source IP address. After repeated failures the endpoint answers HTTP 429 with "Too many failed attempts. Try again in about N seconds." An unauthenticated GET /health is always open and returns {"status": "ok"}; use it for load-balancer probes.

12.1.2 The default-password warning

The first start of a fresh installation seeds a built-in local administrator with the username Administrator and the password Administrator (both overridable at first start with PMW_DEFAULT_ADMIN_USER and PMW_DEFAULT_ADMIN_PASSWORD). While that default password is still in place, a persistent banner sits at the top of the dashboard:

⚠️ The Administrator account is still using its default password.
   Change it now in 👤 Profile (top right).
Warning Change this password before the server is reachable by anyone else. The banner disappears permanently as soon as the built-in Administrator's password is changed. Note also that the built-in Administrator is never automatically locked by the failed-sign-in threshold — it is the break-glass account — so a weak password on it is not protected by lockout, only by the per-IP throttle.

Every action you take in this panel is written to the shared structured log, together with your username and client IP. Destructive actions — deletions, restores, clearing the log, generating or revoking tokens — are deliberately recorded at WARN severity so that they stand out when the log is filtered.

12.3 The Profile overlay

The 👤 Profile button in the top bar opens an overlay covering your own administrator account. Its introduction reads: "Your own admin account — password, passkeys and two-factor. These protect both this admin interface and the main app." It has three sections.

12.3.1 Changing your password

  1. Open 👤 Profile in the top bar.
  2. Type the new password in New password and repeat it in Confirm.
  3. Press Change password.

An empty field is rejected with "Enter a new password." and a mismatch with "The passwords don't match." On success every other session of your account — application, integration console and any other browser on the admin panel — is invalidated immediately; your current session is re-issued in the same response, so you are not signed out of the page you are working in. The log records "changed their password — other sessions invalidated".

12.3.2 Passkeys and two-factor

The remaining two sections let you register passkeys (Touch ID, Windows Hello, a security key) and set up TOTP two-factor authentication for your own account. Both are permissions that must first be granted to your account in the Users tab; until then the overlay states "Passkeys are not enabled for your account — enable them in the Users tab first." or "Two-factor is not enabled for your account — enable it in the Users tab first." The same credential works on all three surfaces of the host. These features are described in full in Chapter 13; the mechanics are identical whether you manage them here or in the application.

Note Passkeys require a secure context (HTTPS, or localhost) and a real host name. If you reach the panel by IP address, the passkey controls hide themselves and the overlay explains: "Passkeys need a hostname, not an IP address. Reach this panel by its name over HTTPS — e.g. its '.local' name — instead of its IP to add or use one."

12.4.1 Licensing

The compute backend — the component that runs the mining queries — requires a valid licence. The card explains it plainly: "The compute backend requires a valid license. Without one it runs for a short grace period and then stops. Upload the license.json you were issued to apply it."

A licence is a small JSON document signed with an Ed25519 key by the vendor. The signature is verified before anything is stored, so a hand-edited expiry date or a file from another installation is refused outright. The installed file lives at data/license.json.

Licence states

The status banner loads with "Checking license…" and then settles into one of three colours:

ColourStateBanner text
GreenValid"Licensed to '<name>', valid until <date>." with the sub-line "Licensed to <name> · expires <date> · issued <date>"
OrangeExpired"License for '<name>' expired on <date>."
RedMissing or invalid"No license installed.", "License signature is not valid.", "License file is not valid JSON.", "License file is missing 'license' or 'signature'.", "License signature is malformed.", "License has no valid expiry date.", or "License file could not be read: …"

Installing a licence

  1. Open the App Control tab and find the License card.
  2. In Upload license, choose the license.json file you were issued. The file input accepts .json only.
  3. Press Upload license.
  4. Wait for the confirmation "License installed. The backend applies it within a few seconds." The status banner turns green and shows the licensee and expiry date.

No restart is needed: the backend polls for the licence file and picks up a new one within seconds. If the compute backend has already stopped because the grace period expired, uploading a valid licence here is still possible — see section 12.4.2.

Upload errorMeaning
HTTP 400 with the specific reason from the table aboveThe file is not a valid, correctly signed licence. Nothing is stored.
HTTP 413 "License file is too large."The encoded file exceeds 100,000 base64 characters. A genuine licence is far smaller.
"Invalid file content."The upload could not be decoded at all.
Note A rejected upload never replaces the licence you already have. The signature is checked first, and only a verified file is written to disk.

Removing a licence

  1. In the License card, press Delete license.
  2. Confirm the dialog: "Delete the installed license? — The compute backend drops to Demo Mode and stops after the grace period unless a new license is applied."
  3. The result is either "License removed — the backend is now in Demo Mode." or, if there was nothing to remove, "No license was installed."
Warning Deleting the licence does not hand you a fresh grace period. The demo window is granted once per installation and is not restored by removing and re-adding a licence. If the window has already been spent, the compute backend stops as soon as the licence is gone.

12.4.2 Demo Mode and the grace countdown

An installation with no valid licence runs in Demo Mode. The first unlicensed run stamps a deadline into the marker file data/demo_grace.json; the window is 30 minutes by default and is configured at deployment time with PMW_LICENSE_GRACE_SECS. The stamp is written once per installation and is never rewritten.

While the window is open, users of the main application see an orange banner on the sign-in panel — "Demo Mode — remaining time: N min", or "No License installed" when the window has been spent. The banner refreshes every 30 seconds, so the countdown visibly ticks down.

Uploading a valid licence at any point during the window cancels the shutdown; the banner disappears at the users' next refresh.

What happens when the grace period expires

When the deadline passes, the compute backend stops. The main application can no longer run queries; API calls that reach for the backend fail, and users see "The compute backend is not reachable. Start it with ./run.sh or check PMW_BACKEND_URL." (HTTP 502).

Note The administration interface is deliberately unaffected. It keeps running after the backend has stopped so that a licence can always be uploaded — you never have to reach a terminal to recover an installation whose demo window has expired. Upload the licence in the License card as usual, then restart the app server (section 12.5) if the backend does not come back on its own.

12.5 Restarting the app server

The App Control card at the top of the tab carries the caption "Operational controls for the running servers." and a single primary button, ↻ Restart app server (tooltip: "Rebind the app + admin listeners with the current TLS settings"). Its side note explains the purpose: "Rebinds the main application and this admin interface in place with the current TLS mode & active certificate — no terminal needed."

A permanent information banner sits beside it:

TLS mode and certificate changes (in the TLS / SSL tab) take effect on
restart. This restarts the app, the integration console and the admin
interface (they share the certificate), so this page may briefly drop —
and if you changed the mode, the admin moves between HTTP :8090 and
HTTPS :8453; reconnect there if it stops responding.
  1. Make the changes you want to apply — typically a TLS mode or certificate change, or enabling the integration console.
  2. Return to the App Control tab and press ↻ Restart app server.
  3. Confirm the dialog: "Restart now? — The app AND this admin interface rebind their HTTP/HTTPS listeners with the current TLS settings. Anyone using the app will briefly disconnect, and if you changed the TLS mode this admin page may move between :8090 (HTTP) and :8453 (HTTPS)."
  4. The page reports "Restart signalled. Listeners rebind with the current TLS plan; reconnect on the new address if this page stops responding." and a toast shows "Restarting (app pid N, admin pid M)…"
  5. If the panel stops responding, reload it on the address the new TLS mode implies — http://<host>:8090/ for Off, https://<host>:8453/ when HTTPS is in play.

Internally the restart signals the launchers in sequence: first the application, then the integration console (best effort — it may not be running), then the admin panel's own launcher. Because the admin server tears itself down last, the HTTP response can occasionally race the teardown; a missing response after a confirmed restart is not an error.

Warning One button restarts three servers. Everyone using the main application is briefly disconnected, and any long-running query in flight is lost. Restart during a maintenance window where possible.
StatusMessageWhat to do
409"The app server is not managed by the launcher (no PID file). Start it with ./run.sh, then try again."The application was started outside the launcher; restart it the way it was started.
409"The app server process is not running."Start the application with ./run.sh.
500"Invalid PID file."The launcher state is corrupt; restart the installation from the shell.
500"Could not signal the app server: <os error>"The operating system refused the signal — usually a permissions problem.

12.6 The TLS / SSL tab

This tab decides how the browser surfaces accept connections and which certificate they present. It holds two cards: the mode selector at the top and the certificate store below it.

12.6.1 The three modes

The card is captioned "Choose how the main application (the GUI server) accepts connections." and offers a segmented control with three positions. The currently stored mode is highlighted.

ModeHTTP endpointHTTPS endpointUse it when
Off (HTTP only)http://<host>:8080/disabledThe server sits behind a reverse proxy that terminates TLS, or on an isolated evaluation network.
Optional (HTTP + HTTPS)http://<host>:8080/https://<host>:8443/You are migrating to HTTPS and want both addresses live during the transition.
Required (HTTPS only)disabledhttps://<host>:8443/Normal production. Also the prerequisite for passkeys away from localhost.

After you load or save the mode, the card prints the resulting endpoint plan: an HTTP endpoint row and an HTTPS endpoint row, each showing either a clickable URL or the word disabled.

  1. Open the TLS / SSL tab.
  2. Select Off (HTTP only), Optional (HTTP + HTTPS) or Required (HTTPS only).
  3. Press Save mode. The toast confirms "TLS mode saved — restart in App Control to apply".
  4. Check the endpoint plan and, if the mode needs HTTPS, make sure a certificate is marked active (section 12.6.2).
  5. Go to App Control and press ↻ Restart app server.
  6. Reconnect on the address shown in the endpoint plan.

If the selected mode needs a certificate and none is active, the card warns: "No active certificate — HTTPS cannot start. Generate or upload one and activate it below."

Warning If a mode that requires HTTPS is saved while no certificate is active, every server falls back to HTTP on the next restart, so that nothing becomes unreachable. This is a safety net, not a configuration: the installation is then serving in clear text despite being set to Required. Always confirm that a certificate is active before you restart, and confirm the address afterwards.
Note The mode and the active certificate are shared. The main application, this administration interface and the integration console all follow the same setting and present the same certificate. There is no way to run the panel over HTTPS while leaving the application on HTTP. The card's footer says so: "Mode & certificate changes take effect after a restart — use ↻ Restart app server in the App Control tab."

12.6.2 The certificate store

The Certificates card lists every certificate known to the installation. When it is empty it reads "No certificates yet. Generate or upload one below."

ColumnContents
NameThe name you gave the certificate. The one currently in use carries a green active pill.
SubjectThe subject read from the certificate itself.
TypeSelf-signed or CA-signed.
ExpiresThe not-after date.
ActionsActivate (hidden on the row that is already active), Download, Delete.

Download saves the certificate in PEM form as <Name>.crt, with spaces in the name replaced by underscores — useful for distributing a self-signed certificate to client trust stores. Delete asks Delete certificate "<name>"? and is recorded in the log at WARN severity.

Tip Keep the active certificate valid. An expired certificate does not degrade gracefully — HTTPS clients simply refuse to connect. The Expires column is the one to check during routine maintenance.

12.6.3 Generating a self-signed certificate

The left half of the card creates a certificate on the server. This is the fastest route to working HTTPS on an internal network, at the cost of a trust warning in browsers that have not been given the certificate.

FieldDefaultNotes

  1. Fill in Name and Common name / host.
  2. Add any further names or addresses under Additional SANs, separated by commas. Include every name and IP by which the server is actually reached, otherwise browsers report a name mismatch.
  3. Adjust Valid for (days) and Key size if your policy demands it.
  4. Tick Activate after generating if this certificate should be used immediately.
  5. Press Generate. The toast confirms "Certificate generated" and the certificate appears in the table.
  6. Restart from App Control to put it into service.
Tip For passkeys to work, clients must reach the server by a host name over HTTPS — never by IP. Put that host name in Common name / host and add its aliases (for example the .local name) to Additional SANs.

12.6.4 Uploading your own certificate

The right half of the card takes a certificate issued elsewhere — by a corporate CA or a public one.

  1. Enter a Name for the entry (placeholder: e.g. Corporate CA).
  2. Paste the full certificate chain into Certificate (PEM).
  3. Paste the matching key into Private key (PEM, unencrypted).
  4. Tick Activate after uploading if it should become the active certificate.
  5. Press Upload. The toast confirms "Certificate uploaded".
  6. Restart from App Control to put it into service.
Warning The private key must be unencrypted PEM — the server has no way to prompt for a passphrase at start-up. Decrypt the key before pasting it, and treat the clipboard and any intermediate file accordingly.

Each of the two PEM fields accepts at most 200,000 characters; anything larger is rejected. Validation errors raised while parsing the certificate or key are surfaced verbatim as the toast text.

12.6.5 Activating a certificate

  1. In the certificate table, press Activate on the row you want to use. The green active pill moves to that row.
  2. Go to the App Control tab and press ↻ Restart app server.
  3. Reconnect and confirm in the browser that the expected certificate is being presented.
Note Activation only marks the certificate as the one to use. Nothing changes on the wire until the restart — the running listeners keep the certificate they were bound with. The same is true of the TLS mode.

Generation, upload and activation are logged at INFO severity under the operation tls; deletion is logged at WARN. You can therefore reconstruct the certificate history of an installation from the Logging tab by filtering on that operation.

12.7 Putting it together: enabling HTTPS from scratch

The following sequence takes a fresh installation from plain HTTP to HTTPS on all three surfaces.

  1. Sign in to the admin panel at http://<host>:8090/.
  2. Open 👤 Profile and change the built-in Administrator's password. The default-password banner disappears.
  3. Open App Control and install the licence you were issued; check that the status banner turns green.
  4. Open TLS / SSL and generate a self-signed certificate — or upload your CA-issued one — with Activate after generating / Activate after uploading ticked.
  5. Verify that the certificate row shows the green active pill.
  6. Set the mode to Required (HTTPS only) and press Save mode. Confirm that the endpoint plan shows the HTTPS URL and that the HTTP row reads disabled, and that no "No active certificate" warning is displayed.
  7. Open App Control and press ↻ Restart app server, confirming the dialog.
  8. Reconnect on https://<host>:8453/. Tell users the application has moved to https://<host>:8443/, and — if the integration console is enabled — its users to https://<host>:8463/.
  9. If a self-signed certificate was used, download it from the certificate table and distribute it to the client trust stores.
Warning If the admin panel does not answer on https://<host>:8453/ after the restart, try http://<host>:8090/. Answering there means the HTTPS fall-back was taken because no certificate was active; return to the TLS / SSL tab, activate one and restart again.

12.8 The Reporting tab

The Reporting tab governs the high-gloss AI supported Documentation report (see §11). The report is produced in two stages — a language model analyses the transition table and returns structured findings, then the server assembles those findings plus the process Sankey, the Happy Path / Conformance sections and the project notes into a styled, printable document — a cover with executive summary, a clickable table of contents, and one topic per page. This tab configures all three parts, and is entirely separate from the LLM attached to a connection (which the app uses for the interactive analysis).

12.8.1 Report language model

An OpenAI-compatible endpoint dedicated to the report: a /v1-style Server URL, a Model and an optional API key. Test probes it and lists the available models. Leave the API-key field blank to keep the stored key; leave the whole Server URL blank to fall back to the LLM configured on the connection. Press Save language model to store it. The model is shared by every project; the key is encrypted at rest and never returned to the browser.

Tip For confidentiality, prefer a locally hosted model server (Ollama, llama.cpp, vLLM, LM Studio). Only the aggregated transition table is ever sent to it; the Sankey, Happy Path and Conformance sections are assembled locally and never leave your network.

12.8.2 Style & sections (per project)

The report look is configured per (connection, project), so one environment can brand reports differently for each customer — a service provider running many customers from the same installation gives each project its own theme. Pick the connection, then one of its projects (loaded live from its database, shown by title, stored by id); the fields below load that project's saved style, or defaults when it has none.

Each project's style holds an accent colour (a #rrggbb hex, applied to headings, the executive-summary callout and table headers), an optional organisation / letterhead line, an optional logo with a Left/Right position and a size slider (0.5×–2×, aspect ratio kept), and three switches to include or omit the process-flow Sankey, the Happy Path section and the Conformance gap analysis. Press Save style to store it for the selected project, or Remove to revert that project to the plain default theme. Configured projects are listed below with Edit / Remove actions.

The logo accepts a PNG, JPEG, WebP or SVG. Raster images are scaled down and re-encoded in the browser before upload, so even a large original ends up small; the stored logo is placed on the first page of that project's reports, on the chosen side. When both a logo and an organisation name are set, the logo sits on its chosen side and the organisation name appears as a letterhead on the opposite side; with no logo, the organisation name leads the cover.

Note A project with no style of its own uses a plain built-in theme (accent, no letterhead or logo, all sections included). There is no shared company-wide default — configure each customer's projects explicitly.

12.8.3 Analysis prompts

The instruction the report model follows can be tailored per process by linking a prompt to a connection and a project. Choose the connection from its dropdown; the project dropdown then lists that connection's projects (shown by title, stored by id), loaded live from its database. Pick the project, type the prompt, and Save prompt. The saved mappings are listed below with Edit / Remove actions. When a project has no prompt of its own, the app's per-project prompt template is used instead.
