11 AI Documentation and Notes

This chapter covers the two views that turn a process map into written record: AI supported Documentation, which sends the current A-Chart transition table to a language model and renders the answer as a structured report, and Notes, the annotation layer that lets you attach threaded, prioritised comments to individual steps and transitions. Both are available to every signed-in user; neither requires the power or administrator role. Read the AI section if you produce process documentation for others, and the Notes section if you work with colleagues on the same database — notes are stored in the database itself, not in your browser, so they travel with the data.

AI supported Documentation

The AI supported Documentation view (🧠 in the ☰ Switch view menu) produces a written analysis of your process, in two stages with a clear division of labour. First a language model does the analysis: it is sent only the current A-Chart transition table and an instruction, and returns structured findings (a title, an executive summary and numbered sections). Then the server does the assembly: it lays those findings out — together with the process-flow Sankey and the locally-computed Happy Path and Conformance sections — into one polished, self-contained HTML report, styled with the accent colour and letterhead set by your administrator. The report is shown in its own frame; ⎙ Save as PDF exports it via the browser's print-to-PDF (the same way the reference report was produced).

The report's language model is configured once by an administrator in the admin Reporting tab, while the style & sections (accent, letterhead, logo and position, and which optional sections to include) and the analysis prompt are both configured per connection and project — so a single installation can brand and tailor reports differently for each customer. A project with no style of its own uses a plain default theme. All of this is separate from the interactive LLM attached to the connection; when no report LLM is configured, the report falls back to the connection's LLM.

Note The view always analyses the A-Chart dataset and the A-Chart filters, no matter which view you were in when you switched to it. If you want the report to describe a particular segment, set that segment up in the A-Chart first, tap Apply, and then switch to AI supported Documentation. The B-Chart, samples and simulation slots are never used as the source.

What is sent to the language model

Only two things leave the deployment: the transition table of the currently loaded A-Chart (the aggregated directly-follows pairs behind the map you can see) and the prompt template stored for this project. They are posted to the base URL of the report LLM configured in the admin Reporting tab (or, when none is set, the active connection's LLM).

Everything else in the report is computed on your own servers and is never sent to the model:

Warning If the connection points at a cloud model endpoint, the transition table — step names and their aggregated counts and durations — leaves your network and is processed by that provider. Step names frequently carry business meaning. Where that matters, ask your administrator to attach a locally hosted OpenAI-compatible server (Ollama, llama.cpp, vLLM or LM Studio all work) so that nothing crosses the network boundary. Individual journeys, event IDs and meta values are never part of the payload — only the aggregated transition table is.
Warning AI models can produce results that are incorrect, incomplete or misleading. Verify every finding independently before acting on it or circulating the report.

Requirements

The feature is only usable when the connection you are currently connected to has a model server attached and that server answers.

A report language model
The report is analysed by the report LLM configured by an administrator in the admin Reporting tab (its own base URL, model and optional key, independent of the interactive LLM attached to the connection). When no report LLM is configured, the report falls back to the connection's LLM. Because the report has its own model, the run button is not gated on the connection's LLM reachability dot — you can generate a report even when the connection carries no interactive LLM.
The connection's own LLM (optional)
Independently, a connection may bundle its own OpenAI-compatible LLM server for the interactive features; when attached, the connection card shows an LLM line and a second status dot — blue when reachable, orange when not. That dot reflects the interactive LLM, not the report LLM.
A selected project
Without one the view shows 🗺 No Project Selected.
Requires: any signed-in user. The LLM base URL, model and API key are configured by an administrator (or, for their own connections, by a power user) — you cannot set them from this view. API keys are encrypted at rest and are never sent to the browser.

The pre-run screen

Before the first run the view shows a large 🧠 glyph and three notice cards that tell you exactly what the report will be based on. Read them: two of the three warn you when material is missing.

CardContent
⛃ A-Chart filters in useA one-line summary of the dataset: <from> – <to> · N journeys · include: … · exclude: … · <meta values>. This same summary is repeated in the report header and on the report toolbar.
🪧 Happy Path ConformanceWarning-orange when nothing is defined: "No Happy Paths defined — conformance data will not be included. Create one in the Happy Path view to enrich the analysis." Otherwise "N path(s) will be evaluated: <names>".
🛡️ Conformance CheckWarning when no norms exist: "No norms defined — gap analysis will not be included. Open Conformance Check and click edges in Edit mode to define target values." Otherwise "N norm(s) across M metric(s) — gap analysis will be appended to the report."
Note The two warning cards are not errors — the report runs perfectly well without happy paths or norms, it is simply thinner. Note also that Happy Path and Conformance Check are power/admin-only views. As a regular user you can read a report enriched with them, but you cannot create the underlying paths or norms yourself; ask a power user or administrator to define them once, after which every user's report includes them.

Running an analysis

  1. Connect to the connection whose project you want to document. The report uses the report LLM set in the admin Reporting tab, so the connection does not need its own interactive LLM attached.
  2. Open the A-Chart, set the date window, included/excluded steps and meta filters you want the report to describe, and tap Apply.
  3. Open the ☰ Switch view menu in the top-right corner and choose AI supported Documentation (🧠).
  4. Check the three notice cards. If the Happy Path or Conformance Check card warns that material is missing and you want it included, define it first and come back.
  5. Tap the 🧠 AI supported Documentation run button. While the model works, the view shows a spinner, the text "AI is analyzing" and the filter summary.
  6. When the answer arrives the report replaces the pre-run screen.

If the run fails, the view shows ⚠️ Analysis Failed with the error message returned by the server and a ↻ Try Again button. A common cause is the report LLM being unconfigured or unreachable — check the admin Reporting tab's Test button.

Reading the generated report

The report opens with a cover — the model's report title and subtitle, your letterhead, the line Prepared for <name> with the generation date, and the model's executive summary — followed by a clickable table of contents. Each entry in that contents list jumps to its chapter, both on screen and in the exported PDF. Every chapter then starts on a fresh page under a large section title, so the printed report reads one topic per page. The chapters, present only when their material exists, are:

  1. Analysis — the model's findings, laid out as numbered sections with any tables it returned.
  2. Process flow — the process-flow Sankey embedded as a vector image, with its caption.
  3. Conformance – Gap Analysis, Happy Path Conformance and Journey Paths — the locally-computed material, each its own chapter, present only when the corresponding paths or norms exist.
  4. Notes — the project's annotations, split into Open and Resolved sub-tables, each sorted by severity (most severe first) and then by date. The columns are Severity, Element, Title, Note, Author and Date. This is where the annotation layer described in the second half of this chapter enters the printed record.

The report toolbar carries the filter summary and three controls:

Show prompt
Opens the sheet "Prompt sent to the LLM" containing the exact prompt text that was transmitted. Use it when you need to reproduce or audit a result.
⎙ Print / PDF
Prints just the report — not the surrounding application — through the browser's own print dialogue. Choose "Save as PDF" there to file the report.
↻ Re-run
Runs the analysis again with the current filters and prompt, using the report language model configured in the admin Reporting tab.
Note Markdown support in the report is deliberately restricted. Headings, bold, italic, inline code, fenced code blocks, bullet and ordered lists, block quotes, horizontal rules and pipe tables all render. Links are limited to http, https, mailto and relative targets — any other scheme is neutralised — and raw HTML is sanitised, so scripts and event handlers in a model's answer are stripped before display. Images and nested lists are not rendered.

Configuring the prompt

The prompt template is the instruction the model receives alongside the transition table. It is edited from the sidebar under Configuration → LLM Prompt and is stored per project, so different processes can carry different documentation styles. The template is held server-side against your user account, which means it follows you to another browser or machine, and it is included in Backup & Restore alongside presets, happy paths, norms and node layouts.

  1. Select the project whose prompt you want to change.
  2. Open the sidebar and expand the Configuration section.
  3. Open the LLM Prompt editor and adjust the template.
  4. Switch to AI supported Documentation and tap ↻ Re-run — or the run button, on a first run — to apply it.
  5. Confirm with Show prompt that the text sent matches what you intended. The template is also reproduced in the report's Analysis Parameters chapter.

Notes

Notes are annotations attached to the process map. Click a step or a transition, add an observation, and it stays with that element — visible to you on every later visit, and to your colleagues when you share it. Each note is a thread: other users add comments underneath, and the note is closed by marking it resolved rather than deleted.

Notes are stored in a NOTES table in your Exasol database, created automatically on first use if the connecting database user holds CREATE TABLE rights. Because they live in the database rather than the browser, notes travel with the data and are visible to every user of that database — subject to the shared flag on each note — regardless of which machine wrote them.

Note A note always attaches to a node (a process step) or an edge (a transition between two steps). There is no free-standing note; the Notes view is the project-wide collection of every note recorded against that project's nodes and edges, and it is that collection which is appended to the AI report as the User Comments chapter.

Who a note belongs to

The author of a note is the signed-in application user — not the shared database login used by the connection. For directory (LDAP) accounts the author is shown by real name, taken from the directory's cn attribute. Every note also records who last contributed to the thread and, importantly, the complete filter context at the moment of creation — the date window, the included and excluded steps and the meta values then in force — so an observation such as "this loop is unusually heavy" remains interpretable months later when the map is filtered differently.

Creating a note on a node or a transition

  1. On any process map — A-Chart, B-Chart, either A/B panel, Individual Journey, Happy Path's left pane, Conformance Check or a simulation flow — click the node or the edge you want to annotate. Edge labels are clickable, and the edge line itself carries a wide invisible hit area, so you do not have to hit the stroke exactly.
  2. In the context popover choose ✎ Show Notes (N), where N is how many notes the element already carries.
  3. If N is zero, the note editor opens directly on a new note. If N is one or more, a list sheet titled Notes — <target> opens showing each existing note as a card, with ＋ New note and Close. One node or edge can carry several independent notes.
  4. Fill in Title (optional)… and Your note…. The title is optional; the body is not — Save stays disabled for a new note until the text is non-empty.
  5. Optionally set an Importance level and tick Share with other users of this database.
  6. Tap Save.
Note Simulation output is read-only, and its context popovers hide the ✓ Require in journeys and ⊖ Exclude from journeys actions — but Show Notes and Show description remain available, so you can still annotate a simulated map.

Threaded comments and resolving

Opening an existing note shows the full thread read-only at the top and an Add a comment box beneath it. Anyone who can see the note — the author, and every other user when the note is shared — may add a comment; it is placed at the top of the thread and recorded with that person's name and the time. Giving each comment a short title is worthwhile, because the most recent title becomes the note's heading wherever the note is displayed, separately from the body.

Resolving is deliberately open to everyone who can see a note rather than restricted to its author: the person who fixes an issue is often not the person who spotted it. Changing importance, changing sharing and deleting are restricted to the author, so a colleague cannot silently downgrade or remove someone else's observation.

Deleting a note

Requires: the note's author. No role grants deletion of another user's note — not even Administrator, from within this view.
  1. Open the note in the editor.
  2. Tap Delete in the footer.
  3. Confirm on the sheet "Delete this note?", which warns: "This removes the note and its whole comment thread from the database for everyone who can see it."
Warning Deletion removes the entire thread — every comment other people contributed — from the database, for everyone. If the point is that the issue is closed rather than that the record was a mistake, tick Mark this note / issue as resolved instead and leave the history in place.

The Notes overview

Choose Notes (🗒) from the ☰ Switch view menu to see every note on the project in one list, independent of the current chart filters. Switching into this view — as into the A-Chart, B-Chart, A/B Comparison or AI supported Documentation — also reloads the notes list from the database.

With no notes yet, the view shows 🗒 No Notes — "Click a node or an edge on the process map and choose "Show Notes" to add one."

A KPI strip runs across the top: Total Notes 🗒, then one coloured tile per importance level (Normal •, Info ℹ, Important ★, Urgent ⚠), then Resolved ✓ in green. The per-importance tiles respect every active filter except the importance filter itself, so selecting one level still lets you see how the remaining notes are distributed.

Tip Set Status to Unresolved and Sort to Oldest first to work a backlog from the bottom up, or filter Importance to Urgent before a review meeting. Combined with the User filter this gives you "everything <colleague> flagged and nobody has closed".

Note badges on the map

Annotated elements are marked directly on the process map so you can see at a glance where the commentary is:

Yellow ✎ badge on a node
The step carries at least one note. Tooltip: "This node has notes".
Yellow ✎ bubble beside an edge label
The transition carries at least one note. Tooltip: "This transition has notes".

Node badges are drawn as part of the node-annotation layer controlled by Show node notes in Configuration → Steps, which also governs the shortened step description under the node name. The badges scale with the flowchart font settings — graph.node.scale for nodes and graph.edge.scale for the bubbles on edges — so raising the node or edge font size in Configuration makes them easier to spot on a dense map.

Tip The two halves of this chapter are designed to work together. Notes recorded against nodes and edges are collected automatically into the User Comments chapter of every AI report, in chronological order and identified by author. Annotating as you analyse therefore builds the human commentary for the next report at no extra cost — and because notes carry the filter context in which they were written, that commentary stays readable even when the report is generated from a different window.
