Journey Sampling

When an event log is too big to explore comfortably, work on a representative subset instead — pick a sampling strategy, keep the process's shape, stay interactive. It is also where each A/B side (and every simulation) is chosen as a data source.

Sampling creates up to three named, representative subsets of a large event log so exploration stays fast. Choose the strategy that keeps what you care about (the average, the timeline, or the rare paths); samples are tagged in the database and shared on the connection. The Sampling menu is also the source picker for A/B Comparison — including stored simulations.
1

Why sample — too many events

A real event log can hold millions of events. Loading, laying out and re-querying the full graph on every filter change turns exploration sluggish. A representative subset keeps the app interactive while preserving the process’s shape — the same main paths, the same bottlenecks, far fewer rows to move.

2

Pick a strategy

How the subset is chosen shapes what you see. Three strategies trade speed against how faithfully rare behaviour survives:

🎲 Random
Uniform random journeys. The simplest, fastest baseline — unbiased, but rare variants may be under-represented.
📅 Temporal Stratified
Proportional across equal calendar-month buckets, so the sample keeps the original’s time distribution — for when volume varies seasonally.
🌿 Path Diversity
Coverage-maximising across distinct journey variants, so rare paths are more likely to appear — for when you care about the full variety of behaviour.
  • Random — a quick, faithful-to-the-average look.
  • Temporal Stratified — when when things happened matters.
  • Path Diversity — when the unusual routes are the point.
3

What sampling does to the numbers

A sample is a statistical estimate of the whole. The principal flow — the high-frequency paths that carry most journeys — comes through faithfully; in the best case the differences are minor. The uncertainty concentrates exactly where it matters least: the rarest variants, which may wobble or drop out.

Journey variantFull log50k sampleΔ
Login → Browse → Pay → Confirm (principal) 62.0 %61.6 %−0.4
… with a coupon8.0 %7.5 %−0.5
… rare browse-loop ×3 (long tail) 0.3 %0.1 %−0.2 · may vanish

Common routes land within a fraction of a percent; the long tail of one-off variants is where a sample blurs — which is exactly what Path Diversity protects.

  • For a path taken by a share p of journeys, a random sample of n estimates it with a standard error of about √(p·(1−p)/n) — so a common path is pinned down tightly, a rare one carries larger relative error.
  • The estimate improves with size: sampling error shrinks with √n, so a bigger sample tightens every number (doubling it cuts the wobble by roughly 30 %).
  • The overall shape — which steps connect, where the bottlenecks are — is driven by the dominant paths, so it stays recognisable even in a small sample.
Rule of thumb. For the overall shape and the dominant paths a modest sample is plenty; if a rare path is the subject, raise the count or use Path Diversity.
4

How samples are stored (and shared)

A sample isn’t a copy of your data — it’s a label. The app adds a SAMPLE_SET column to the JOURNEYS table (on first use) and tags the chosen journeys. The original rows are never modified, and deleting a sample removes only its rows.

The same JOURNEYS table serves Original and every sample; a filter just adds “SAMPLE_SET = …”. Because they live in the database, samples are shared by everyone on the connection — creating or deleting one changes it for all users.

6

Why it matters for simulation

This menu is the only place a simulation becomes comparable. You run a Simulation (stored as Sim-A or Sim-B), then select it here as an A/B source — that’s how a what-if is put side by side with reality. And on a huge log, sampling first keeps the whole loop fast: the simulation is built from the graph you have loaded, so a snappy sample means a snappy base to simulate from.

🎲 Sample (snappy base)→ Run Simulation → Sim-B→ Select Sim-B as B source

Sample → simulate → compare: reality on A, the what-if on B, a similarity score between them. Without the Sampling menu, a stored simulation can’t be shown.

See also. The Simulation and A/B Comparison guides cover running a what-if and reading the comparison.

Good to know

  • Up to three samples. Keep a Random, a Temporal and a Path-Diversity sample side by side and switch between them per A/B slot.
  • Non-destructive. Samples only tag rows via SAMPLE_SET; the Original data is untouched, and deleting a sample removes only its tagged rows.
  • Shared, not personal. Samples live in the connection’s database, so they’re shared by everyone using it — unlike filters and presets, which are per user.
  • Needs the right. Adding the SAMPLE_SET column and writing sample rows needs ALTER TABLE + INSERT on JOURNEYS — which is why sampling is a Power/Admin capability.
  • Further reading. The behaviour is standard sampling statistics applied to event data — W. G. Cochran, Sampling Techniques (Wiley) for the theory of representative samples and sampling error; W. van der Aalst, Process Mining: Data Science in Action (Springer) for event logs, variants and representativeness.

Sample to stay fast, choose the strategy to keep what matters, and use the same menu to put a sample, the original, or a simulation on each side of a comparison.
