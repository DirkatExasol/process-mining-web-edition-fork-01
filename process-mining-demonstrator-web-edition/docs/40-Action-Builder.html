Action Builder

Give users one-click actions in the node menu — "last log of this step", "this sub-process's transition table" — written in a few lines of a business-readable script that the app compiles into safe, filter-aware SQL. Write intent, not queries.

An action runs from a node's right-click menu and returns a table or a flowchart. You author it in a tiny script language that abstracts away raw SQL: it is node-relative (THIS, FOLLOWING…), filter-guided (it inherits the chart's date window and filters), and safe (escaped, id-hashed, row-capped). The example below shows a two-line script becoming a full SQL query.
1

What the Action Builder is

An action is a small, reusable command that a user runs straight from a node’s menu on the process map — “show me the last log entry for this step”, “open this sub-process’s transition table”. You author them in the Action Builder (a developer surface an admin switches on); they then appear in the right-click menu of the nodes you chose.

2

Why a script, not raw SQL

Every action ultimately becomes an Exasol query — but you don’t write SQL. You write a few lines of a business-readable script, and the app compiles it into correct, safe, filter-aware SQL for you. The script says what you want; the app handles the how.

  • Node-relative. THIS, PREVIOUS, FOLLOWING resolve to the node the action was run from — one script works from every node’s menu.
  • Filter-guided. The query automatically inherits the chart’s current date window and filters — you never re-type a WHERE clause.
  • Safe by construction. Values are escaped, the case id is MD5-hashed, results are capped — no SQL injection, no runaway queries.
  • Readable & reusable. An analyst can read, edit and share an action without knowing the table layout; the same script ports across projects and schemas.
3

Example — “last log of a node”

This is the whole point. The action “show the most recent event for the step I clicked” is two lines of script — and expands into a fully-filtered SQL query you’d otherwise write by hand every time:

The script you write
SHOW LAST LOG ENTRIES
FROM NODE(THIS)
The SQL it becomes
SELECT EVENT_ID, STEP, EVENT_TIME,
       META_1, META_2, META_3
FROM JOURNEYS
WHERE PROJECT_ID = 'BOOKSTORE'
  AND EVENT_TIME >= '2026-01-01 00:00:00'
  AND EVENT_TIME <  '2026-02-01 00:00:00'
  AND STEP IN ('Payment Processing')
ORDER BY EVENT_TIME DESC, STEP_ID DESC
LIMIT 1

The app filled in everything: 'Payment Processing' is whatever node you ran it from (THIS); the date range came from the chart’s current filter; the ordering, the LIMIT and the escaping are handled for you.

That is the abstraction. Change the date slider and the same two-line action returns the last entry for the new window — no SQL edit. Run it from a different node and THIS follows.
4

The building blocks

A script is a handful of clauses (keywords are case-insensitive). Most actions use just SHOW and FROM:

ClauseWhat it does
AVAILABILITYALL NODES or a list of steps — where the action appears in the menu.
SHOWLAST [N] LOG ENTRIES, or TRANSITION TABLE WITH "COUNT","%JOURNEY%" [FOR LAST N LOG ENTRIES], or a cross-project FLOWCHART.
FROMNODE(THIS | PREVIOUS | FOLLOWING | ALL FOLLOWING | ALL PREVIOUS) — the node set, relative to where it’s run.
SORTASCENDING / DESCENDING (optional).
WHEREEVENT_ID :: [id, …] — restrict to specific cases (optional).
More than log rows. SHOW TRANSITION TABLE WITH … returns a metric table for the selected nodes, and SHOW FLOWCHART FROM conn::project opens another project’s map in a panel — all from the same tiny grammar.
5

Run it, save it, share it

Set AVAILABILITY to the steps that should carry the action and save. It’s stored per (connection, project), so everyone using that project sees it in the node menu. Running it inherits the chart’s live filters and shows the result as a table (or a flowchart panel).

Author in Action Builder→ Saved on the project→ ⚡ Runs from the node menu

Write once, in business language; run anywhere the node appears, always scoped to what’s on screen.

Good to know

  • Who. Authoring actions is a developer/admin task (the Action Builder is on the admin port + 20 — :8110). Running a saved action is available to the users of the project.
  • Filter-guided, always. An action never captures a fixed date range — it re-reads the chart’s current window each run, so it stays in step with what you’re looking at.
  • Safe by design. The DSL compiles to escaped SQL with the case id MD5-hashed and the row count clamped; a script can’t inject SQL or dump an unbounded result.
  • Preview the SQL. The builder can show the exact SQL a script compiles to, so you can confirm what will run before saving it.

The script language exists so the person who knows the process question can answer it themselves — without writing, or maintaining, the SQL underneath.
