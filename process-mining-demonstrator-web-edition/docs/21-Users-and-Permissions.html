Users & Permissions — who can do what

Three cumulative roles — Regular, Power and Admin — plus a separate Developer grant decide what each account may do, from exploring maps to running the whole installation. Here is the complete picture, with the capability matrix.

Permissions come in two parts: a level (Regular ⊂ Power ⊂ Admin) that each account holds exactly one of, and an optional Developer grant that opens the authoring surfaces on top of any level. Everything is set in the admin Users tab, and every capability requires a signed-in identity.
1

Three roles that build on each other

Every signed-in account carries one of three permission levels. They are cumulative: a Power user can do everything a Regular user can, plus more; an Administrator can do everything a Power user can, plus run the whole installation. A new account is a Regular user by default.

RegularExplore: maps, charts, filters, presets, notes & personal settings — on the connections assigned to them.
Power = Regular +Own DB connections, schema provisioning, demo data, journey sampling and the advanced views.
Admin = Power +The admin interface: all users & roles, TLS, LDAP, licensing, logging, backups.

Each level contains the one below it.

Assigned connections. A Regular user only sees the database connections an administrator (or a Power user) has assigned to them.

3

The Developer grant — a separate add-on

Developer is an independent checkbox in the admin Users tab, not a level. It admits the account to the authoring surfaces regardless of whether it is Regular, Power or Admin: the Integration console (data sources), the Action Builder, and creating Σ aggregates for drill-down.

☑ Developer — grants the authoring surfaces
⚙ Integration console :8100 🔨 Action Builder :8110 Σ Create aggregates

A Regular user with only the Developer grant may enter these surfaces, but gains no other elevated power in the main app.

  • Integration console — configure the application’s data sources (developers, power users and admins).
  • Action Builder — author the business-readable node actions (developers and admins only; an admin must first enable Actions).
  • Aggregates — collapse connected steps into Σ super-steps for drill-down (see the Aggregates & Drill-Down guide).
4

Where roles are granted

All of this lives in the admin interface → Users tab: create local users, enable or disable access, and grant or revoke Power, Admin and Developer per account. Only enabled users can sign in.

alice is a Power user; bob is a Regular user with the Developer add-on; admin runs the installation.

Roles need a signed-in identity. If an admin turns off “Require sign-in for the main application”, the app runs with no user — so every Power/Admin feature is hidden and its API returns 403. Keep sign-in on to use them.

Good to know

  • Default is Regular. A brand-new account can explore, but nothing that changes shared data or the installation until it is granted Power, Admin or Developer.
  • Break-glass admin. The built-in Administrator account always works as a recovery route (and is exempt from auto-lockout), even if the LDAP directory is later misconfigured.
  • Directory (LDAP) users too. Both local and directory accounts can hold any role; the grants are applied in the same Users tab.
  • Power manages only its own connections. A Power user administers the connections it created; an Administrator sees and manages every connection.

Rule of thumb: Regular explores, Power prepares and analyses, Admin governs — and Developer builds the data sources, actions and aggregates.
