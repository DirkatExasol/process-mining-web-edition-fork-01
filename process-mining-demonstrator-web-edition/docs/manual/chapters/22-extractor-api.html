22 Reference: Writing an Extractor

The File extractor that the integration console ships with is not a special case: it is an ordinary plug-in written against a small, stable contract, and any other source — a CSV export, a message queue, a REST endpoint, a second log format — can be added the same way. This chapter is the reference for that contract. It documents the four types an extractor programs against (ExtractorInfo, Extractor, IngestSession, ExtractResult), the registry, the lifecycle of a run and how status and progress reach the console, the two ingest backends and the transaction bracket, how a destination is opened with stored credentials, the sandboxed file helpers, a complete worked skeleton in Python with its file layout and registration, and how to test the result without a database. It is written for developers with access to the product's source tree; nothing in this chapter is done from the browser.

Requires: write access to the deployment's backend/ source tree. Running the finished extractor through the integration console additionally requires the Developer or Administrator role.

Where the code lives

The whole abstraction layer is one Python package, backend/app/integration/. An extractor only ever imports from contract (the stable surface) and, if it reads files, from files. Everything else is machinery it is deliberately kept away from.

ModuleWhat it holdsAn extractor imports it?
contract.pyColumnType, ExtractorInfo, ExtractResult, IngestError, and the IngestSession / Extractor protocolsYes — this is the API
files.pyThe sandboxed path resolver and the line/delta readersYes, for file-shaped sources
layer.pyAbstractionLayer, the concrete session, and the process-wide layer singletonOnly to register
backends.pyInMemoryIngestBackend, SqlIngestBackend, identifier validation, bracket clampingNo — the caller wires these
destinations.pyopen_stored_connection() — opens a saved connection for a headless runNo

Note An extractor never opens a database connection, never builds SQL, never commits, and never decides where rows land. It is handed an IngestSession already bound to the target schema of the connection the user (or the watchdog) chose, and it pushes rows through that. This is what keeps extractors database-agnostic and what lets the same code be tested against an in-memory target.

The contract

ExtractorInfo — the identity

ExtractorInfo is a frozen dataclass carrying the plug-in's identity. It is what GET /api/integration/extractors returns and what the console displays.

FieldTypeMeaning
idstrThe registry key. Must be globally unique, stable across versions, and a slug: lower-case letters, digits and single hyphens (^[a-z0-9]+(-[a-z0-9]+)*$). Examples: file, csv-folder.
namestrThe display name, e.g. File.
versionstrA free-form version string, e.g. 1.0.
descriptionstrOne sentence shown next to the name. Defaults to the empty string.

Registration enforces both rules and reports them as ValueError:

Extractor id 'Not A Slug' must be a slug (a-z, 0-9, '-').
An extractor with id 'file' is already registered.

Extractor — the protocol

An extractor is any object with an info attribute and a run(session) method. There is no base class to inherit from; the protocol is structural.

class Extractor(Protocol):
    info: ExtractorInfo

    def run(self, session: IngestSession) -> ExtractResult:
        ...
run is synchronous
The layer executes it off the event loop in a worker thread (asyncio.to_thread). Do not make it a coroutine, and do not block the event loop by calling it directly.
Push incrementally
Read and push in batches rather than buffering the whole source. push accepts a generator and streams it, so a source of any size can be handed over without materialising it.
Raising means failure
Any exception marks the run failed, records the message as lastError in the user's status, rolls back the open transaction bracket, and propagates to the caller. Returning an ExtractResult marks the run completed.
Do not keep the session
The session is created per run and is invalid once run returns. Never store it on the instance for later use.

IngestSession — the only handle to the database

MemberSignatureBehaviour
schemaproperty → strThe target schema of the selected connection. Every table this session writes lives there. Validated as a SQL identifier when the session is created.
define_tabledefine_table(table, columns, *, keys=())Declares the table and creates it if absent (CREATE TABLE IF NOT EXISTS). Idempotent — call it on every run. columns maps column name → ColumnType and also fixes the column order used for inserts. keys names the business-key columns and is informational for now. Must be called for a table before any push to it. Also records the table in tablesTouched, in order of first touch.
pushpush(table, rows) -> intAppends rows (each a mapping of column name → value) and returns how many were written. Missing columns become NULL. Rows are flushed in internal batches of 1000. Every flush adds to the live recordsPushed counter and to the transaction bracket.
loglog(message)Appends a progress line to the status panel. Only the most recent 50 lines are kept; older ones are dropped.
progressprogress(done, total=None)Sets the progress-bar counters recordsDone / recordsTotal. Cheap — call it every few hundred items. A total of 0 means "unknown".
existing_keysexisting_keys(table, key_columns) -> set[tuple[str, ...]]The key tuples already present in the table, every value stringified and NULL rendered as the empty string. Use it for create-if-missing of small metadata tables (a project row, step definitions). It reads all keys of the table — never call it on a fact table.
Warning push rejects columns that were not declared. A row containing a key that is not in the define_table mapping raises IngestError with Unknown column(s) for JOURNEYS: GHOST, which fails the whole run. Pushing to a table you never declared raises Call define_table('JOURNEYS', ...) before push()., and declaring a table with an empty column mapping raises Table 'JOURNEYS' must declare at least one column.

ExtractResult — what the run reports

The result is purely informational: the layer has already counted every row that went through push. The result is where the extractor says what those rows meant.

FieldDefaultMeaning
records0Successful items — for the File extractor, journey events. Becomes eventsWritten in the status and the records field of the run response.
skipped0Source items that could not become a record. Becomes eventsSkipped. Report this honestly: it is the KPI that makes a silently misconfigured source visible as "lots skipped" rather than merely as a small record count.
tables()Tuple of table names the extractor touched.
detail""The human-readable summary shown to the user, e.g. 1 240 events written, 17 skipped, 3 new step(s).
Note recordsPushed in the status and records in the result are different numbers on purpose. recordsPushed counts every row that crossed the session, including the project, step and meta rows an extractor creates on the side; records counts only the domain objects the extractor set out to produce.

ColumnType and the portable type mapping

Extractors declare portable types; the backend maps them to the concrete database. This is the only reason an extractor written for the demonstrator does not contain a single line of Exasol-specific SQL.

ColumnTypeValueExasol typeAccepted Python values

DECIMALdecimalDECIMAL(36,6)int, float (non-finite values are rejected with Non-finite numeric value: …)
TIMESTAMPtimestampTIMESTAMPdatetime (rendered to millisecond precision), date
BOOLboolBOOLEANTrue / False

Identifier rules

Schema, table and column names must match a conservative grammar: a letter or underscore, then letters, digits or underscores, up to 128 characters. Anything else is rejected, never escaped, with Invalid SQL identifier: 'EVENTS; DROP TABLE X'. Names are therefore safe to interpolate into DDL and DML, and no source data can ever reach a statement as an identifier.

IngestError

IngestError is what the layer raises for an invalid ingest operation: unknown table, undeclared column, bad identifier, unknown extractor id, or a concurrent run. Extractors normally let it propagate — it is recorded as the run's failure exactly like any other exception. Extractors may also raise it themselves when they detect a condition the layer would consider fatal.

The registry

AbstractionLayer holds the registry and the per-user status. One process-wide instance exists, exported as layer from app.integration; that is the object the API and the watchdog share.

MethodEffect

layer.unregister(id)Removes it if present; silent when it is not.

Registration happens at import time, plug-in style. The package's __init__.py imports the built-ins and calls register_builtin_extractors(layer), so merely importing app.integration anywhere in the process is enough for the console to list them.

Tip Guard your registration with if layer.get(MY_ID) is None: as the built-in does. Module reloads during tests would otherwise trip the duplicate check and fail the import.

Descriptor entries versus configured instances

Some extractors cannot be run straight from the registry because a run needs configuration that only exists per source — a path, an encoding, a project id, a field list. The built-in File extractor solves this with a two-object pattern that is worth copying:

  1. A descriptor object is registered. It carries the real ExtractorInfo so the extractor appears in GET /api/integration/extractors, but its run raises immediately: The File extractor is run per source, not from the registry.
  2. The configured instance is built per run by the API or the watchdog, with everything it needs passed to its constructor, and handed to layer.run(extractor=instance, …) as an object rather than an id.

layer.run accepts either form: a string is looked up in the registry (No extractor registered with id 'nope'. if absent), and any object satisfying the protocol is used as-is.

The lifecycle of a run

Every run — a console Run, a watchdog poll, or a call from your own code — goes through the same coroutine. Its parameters are what the console's pipeline canvas is drawn from.

result = await layer.run(
    user=user,                         # status is per user; None/"" for no-sign-in
    extractor=instance_or_id,
    backend=backend,                   # SqlIngestBackend or InMemoryIngestBackend
    schema=schema,                     # target schema of the chosen connection
    connection_id=conn_id,
    connection_name=conn.name,
    source_name=source.name,
    source_type_name=st.name,
    trigger="manual",                  # or "watchdog"
    transaction_rows=transaction_rows,
)

What the layer does, in order:

  1. Resolves the extractor. A string id is looked up; a missing id raises IngestError.
  2. Takes the per-user run slot. If that user already has a run in flight it raises An extraction is already running for this user. Different users run concurrently; the same user cannot, which is precisely what stops a manual import and a watchdog poll from importing the same lines twice.
  3. Resets the user's status and sets state: running, the trigger, the extractor id and name, the source, source-type, connection and schema names, startedAt, and zeroes every counter (recordsPushed, eventsWritten, eventsSkipped, commits, recordsDone, recordsTotal), the table list, the error and the message log. The status therefore always describes the most recent or in-flight run only.
  4. Creates the session bound to the backend, the schema and the transaction bracket.
  5. Runs extractor.run(session) in a worker thread. While it runs, every push, log and progress call updates the same status object under a lock, so GET /api/integration/status shows live progress.
  6. Closes the final transaction bracket with a commit, also off the event loop.
  7. On success: sets state: completed and finishedAt, copies result.records into eventsWritten and result.skipped into eventsSkipped, writes the admin-log line extractor <id> pushed <n> rows to <schema> (usage level, operation integration), and returns the result.
  8. On failure: rolls the backend back (a failing rollback is swallowed so it cannot mask the real error), sets state: failed, finishedAt and lastError, logs extractor <id> failed: <error> as a warning, and re-raises.
  9. Always: releases the user's run slot.

The two backends and the transaction bracket

An IngestBackend is the seam between the portable ingest API and a concrete target. Extractors never see one; the code that starts the run picks it.

InMemoryIngestBackend
Keeps schemas, tables and rows in dictionaries. No database, no dependencies. It is the local development target and the reference implementation of the ingest semantics for tests; it additionally counts commits and rollbacks so a test can assert the bracketing. Inserting into a table that was never created raises Table <schema>.<table> was not defined.
SqlIngestBackend
The production target. It generates schema-qualified DDL and DML and runs it through a caller-supplied run_sql callable, plus optional commit and rollback callables that belong to whoever owns the connection. Identifiers are validated, values are rendered as defensively escaped literals, and each INSERT statement carries at most 1000 rows. Without the commit/rollback callables it is a no-op on both — the driver's autocommit then ends every statement, which is what the SQL-recording tests expect.

Transaction rows

The transaction_rows argument is the bracket size: the session counts rows written since the last commit and commits as soon as the bracket is full. This keeps the database's transaction small on a large import and makes rows durable as the run progresses.

Configured valueEffective valueMeaning
not set, or not a number5000The default bracket
0 or any value ≤ 00One transaction for the entire import — fully atomic, but the database holds all of it open
1 … 9991000Floored to one insert batch
1000 … 1 000 000as givenUsed unchanged
above 1 000 0001 000 000Clamped

Normalise user-supplied values with clamp_transaction_rows() from app.integration.backends rather than trusting the number. After run returns, the layer issues a final commit for the last, possibly partial bracket. That final commit is skipped only when nothing was written since the previous commit and at least one commit already happened; the very first commit always runs, even with zero rows, to close out the transaction any DDL or SELECT opened.

Warning On failure only the open bracket is rolled back. Brackets already committed stay committed — that is the point of bracketing. A failed run can therefore leave earlier rows in the database while the caller's read checkpoint does not advance, so a retry re-reads the same input and duplicates those rows. Nothing in the layer de-duplicates. If your extractor's source cannot tolerate that, run it with transaction_rows=0 for a single atomic transaction, and document the trade-off.

Opening a destination with stored credentials

A run's destination is always a stored connection, opened with the credentials an administrator saved — never with whatever the caller happens to have connected in their browser. That is what makes the trigger irrelevant: a console run, a watchdog poll and a headless push all name a connection by id and land in the same place.

from app.integration.destinations import open_stored_connection
from app.integration import SqlIngestBackend

opened, run_sql = open_stored_connection(conn)      # blocking — call via asyncio.to_thread
backend = SqlIngestBackend(
    run_sql=run_sql, commit=opened.commit, rollback=opened.rollback,
)
try:
    result = await layer.run(..., backend=backend, schema=conn.schema)
finally:
    opened.close()                                  # the caller owns the handle

open_stored_connection returns the raw handle and a synchronous SQL runner bound to it (a list of rows for a SELECT, an empty list otherwise), and it switches autocommit off so that the layer's bracket, not the driver, decides when work becomes durable. The caller owns the handle and must close it, on the failure path as well as the success path.

When the caller already has a live session pointing at exactly the same connection, the API reuses it instead of opening a second one — again turning autocommit off first, and routing commit and rollback through that live session. A connection that cannot be opened is reported to the user as Could not connect to “<name>”: <error>, and a connection whose stored target schema is blank as “<name>” has no target schema configured.

Note Whoever triggers a run must re-check that the connection is assigned to the acting user, on every run — the assignment, not the presence of a connection id, is the authorisation. The watchdog repeats this check on every poll for exactly this reason, so revoking an assignment stops it immediately.

Sandboxed file access

If your extractor reads files, use the helpers in app.integration.files. They are the only sanctioned path from a user-supplied string to an open file, and every one of them funnels through resolve_source_file. Do not call open() on a configured path yourself — that bypasses the sandbox.

HelperReturnsNotes
resolve_source_file(path)PathResolves and validates. Raises FileAccessError.
read_preview(path, limit=5){lines, truncated}First limit non-blank lines. limit is clamped to 1…50. Always decodes as UTF-8 with replacement, regardless of any configured encoding.
iter_lines(path, encoding)generator of strStreams non-blank lines for extraction. Safe to hand straight to a loop that pushes in batches.
count_lines(path, encoding)intA cheap pre-pass counting non-blank lines — the denominator for progress(done, total).
read_new_lines(path, encoding, offset){lines, new_offset, size, signature, rotated}Complete lines appended since offset. A partial trailing line is left for the next read.
read_delta(path, encoding, offset, signature)sameread_new_lines plus replacement detection: a changed head with an unchanged or grown size means the file was replaced, so it is re-read from byte 0.
seed_demo_files()—Copies the bundled example logs into the sandbox on startup. Never overwrites; best-effort.

The limits below apply to every one of these helpers, so they apply to any extractor built on them:

LimitValueConsequence
Line length2000 charactersEvery line is truncated first. A pattern targeting content beyond character 2000 never matches.
Blank linesalways skippedAlso excluded from the progress denominator.
Bytes per delta read8 MBA larger backlog is drained across successive reads; new_offset < size signals more is pending.
Single line longer than 8 MBskipped pastTreated as unparseable content rather than re-read forever.
Fingerprintfirst 64 bytesFiles shorter than that get an empty signature, so in-place replacement without shrinking goes undetected.
Decodingconfigured encoding, errors replacedUndecodable bytes never raise.

Path resolution raises FileAccessError with exactly one of these messages, which callers surface as HTTP 400: No file path given., That path is outside the allowed sources directory., File not found., Not a regular file. In the default sandboxed mode a relative path is taken relative to PMW_INTEGRATION_FILES_DIR, an absolute path is accepted only if it already lies inside that root, and the real path with symlinks resolved must still be inside it.

Warning Setting PMW_INTEGRATION_ALLOW_ANY_PATH to 1, true, yes or on disables the sandbox entirely: any absolute path the server process can read is then accepted. Use it only in a developer-trusted deployment.

The extractor

"""Example extractor: reads a comma-separated export and writes JOURNEYS events."""

from __future__ import annotations

import csv
import hashlib
from datetime import datetime

from .contract import (
    ColumnType, ExtractResult, ExtractorInfo, IngestError, IngestSession,
)
from .files import resolve_source_file

CSV_EXTRACTOR_ID = "csv-file"
_BATCH = 500

_JOURNEYS_COLUMNS = {
    "PROJECT_ID": ColumnType.STRING,
    "EVENT_ID": ColumnType.STRING,
    "STEP": ColumnType.STRING,
    "STEP_ID": ColumnType.INT,
    "EVENT_TIME": ColumnType.TIMESTAMP,
    "META_1": ColumnType.STRING,
    "META_2": ColumnType.STRING,
    "META_3": ColumnType.STRING,
    "SAMPLE_SET": ColumnType.STRING,
}
_PROJECTS_COLUMNS = {
    "PROJECT_ID": ColumnType.STRING,
    "TITLE": ColumnType.STRING,
    "DESCRIPTION": ColumnType.STRING,
}


def csv_extractor_info() -> ExtractorInfo:
    return ExtractorInfo(
        id=CSV_EXTRACTOR_ID,
        name="CSV file",
        version="1.0",
        description="Reads a comma-separated export and writes JOURNEYS events.",
    )


class CsvExtractor:
    """One configured run over one CSV file."""

    info = csv_extractor_info()

    def __init__(self, *, path: str, encoding: str, project_id: str) -> None:
        self._path = path
        self._encoding = encoding or "utf-8"
        self._project_id = project_id

    # ── the one method the layer calls ────────────────────────────────────
    def run(self, session: IngestSession) -> ExtractResult:
        session.define_table(
            "JOURNEYS", _JOURNEYS_COLUMNS, keys=["PROJECT_ID", "EVENT_ID", "STEP"],
        )
        real = resolve_source_file(self._path)   # sandboxed; may raise FileAccessError
        session.log(
            f"reading {self._path} → {session.schema}.JOURNEYS "
            f"(project {self._project_id})"
        )

        written = skipped = processed = 0
        batch: list[dict] = []
        with real.open("r", encoding=self._encoding,
                       errors="replace", newline="") as fh:
            for record in csv.DictReader(fh):
                processed += 1
                row = self._row(record)
                if row is None:
                    skipped += 1
                else:
                    batch.append(row)
                    if len(batch) >= _BATCH:
                        written += session.push("JOURNEYS", batch)
                        batch = []
                if processed % 200 == 0:
                    session.progress(processed)
        if batch:
            written += session.push("JOURNEYS", batch)
        session.progress(processed)

        session.log(f"pushed {written} events, skipped {skipped} unusable row(s)")
        created = self._ensure_project(session)

        detail = f"{written} events written, {skipped} skipped"
        if created:
            detail += ", project created"
        return ExtractResult(
            records=written, skipped=skipped,
            tables=("JOURNEYS", "PROJECTS"), detail=detail,
        )

    # ── one source item → one row, or None ────────────────────────────────
    def _row(self, record: dict) -> dict | None:
        case_id = (record.get("case") or "").strip()
        step = (record.get("activity") or "").strip()
        raw_time = (record.get("time") or "").strip()
        if not (case_id and step and raw_time):
            return None                       # counts as skipped, never as an error
        try:
            event_time = datetime.strptime(raw_time, "%Y-%m-%d %H:%M:%S")
        except ValueError:
            return None
        return {
            "PROJECT_ID": self._project_id,
            # Pseudonymise the case id — the raw value never reaches the database.
            "EVENT_ID": hashlib.md5(case_id.encode("utf-8")).hexdigest(),
            "STEP": step,
            "STEP_ID": None,
            "EVENT_TIME": event_time,
            "META_1": record.get("channel"),
            "META_2": None,
            "META_3": None,
            "SAMPLE_SET": "ORIGINAL",
        }

    # ── create-if-missing metadata ────────────────────────────────────────
    def _ensure_project(self, session: IngestSession) -> bool:
        session.define_table("PROJECTS", _PROJECTS_COLUMNS, keys=["PROJECT_ID"])
        if (self._project_id,) in session.existing_keys("PROJECTS", ["PROJECT_ID"]):
            return False
        session.push("PROJECTS", [{
            "PROJECT_ID": self._project_id,
            "TITLE": self._project_id,
            "DESCRIPTION": "",
        }])
        session.log(f"created project {self._project_id!r}")
        return True


class _CsvExtractorDescriptor:
    """Registry-only entry so the extractor is listed; runs use a configured instance."""

    info = csv_extractor_info()

    def run(self, session: IngestSession) -> ExtractResult:
        raise IngestError("The CSV extractor is run per source, not from the registry.")


def register_csv_extractor(layer) -> None:
    """Idempotent registration — safe under module reloads in tests."""
    if layer.get(CSV_EXTRACTOR_ID) is None:
        layer.register(_CsvExtractorDescriptor())

Driving it

To run the configured instance from your own endpoint or job, build the backend, run the layer, and close anything you opened:

from app.integration import SqlIngestBackend, layer
from app.integration.backends import clamp_transaction_rows
from app.integration.destinations import open_stored_connection

opened, run_sql = await asyncio.to_thread(open_stored_connection, conn)
backend = SqlIngestBackend(
    run_sql=run_sql, commit=opened.commit, rollback=opened.rollback,
)
try:
    result = await layer.run(
        user=user,
        extractor=CsvExtractor(path=path, encoding="utf-8", project_id="RETAIL"),
        backend=backend,
        schema=conn.schema,
        connection_id=conn.id,
        connection_name=conn.name,
        source_name=source.name,
        trigger="manual",
        transaction_rows=clamp_transaction_rows(cfg.get("transactionRows")),
    )
finally:
    await asyncio.to_thread(opened.close)
Tip If your source can be read incrementally, keep the read cursor outside the extractor and advance it only after the run succeeds, exactly as the file checkpoint does. A cursor advanced before or during a run silently loses data when the run fails.

Testing an extractor

Every extractor can be tested end to end with no database at all: register it on a private AbstractionLayer(), run it against an InMemoryIngestBackend, and assert on the rows that landed and on the status the console would have shown. Use a private layer instance rather than the shared layer singleton so tests cannot interfere with each other.

  1. Create backend/tests/test_csv_extractor.py alongside the existing test_integration_*.py files.
  2. Point the sandbox at a temporary directory before importing anything that reads it, then reload app.config and app.integration.files so the new value takes effect: 
    @pytest.fixture
def env(tmp_path, monkeypatch):
    monkeypatch.setenv("PMW_INTEGRATION_FILES_DIR", str(tmp_path / "files"))
    monkeypatch.delenv("PMW_INTEGRATION_ALLOW_ANY_PATH", raising=False)
    import app.config as config
    importlib.reload(config)
    import app.integration.files as files_mod
    importlib.reload(files_mod)
    return config
  3. Write a fixture file into config.INTEGRATION_FILES_DIR and run the extractor: 
    def test_csv_extractor_writes_rows(env):
    (env.INTEGRATION_FILES_DIR / "events.csv").write_text(
        "case,activity,time\nA1,login,2026-08-03 14:05:09\n"
    )
    mem = InMemoryIngestBackend()
    result = asyncio.run(AbstractionLayer().run(
        user="dev",
        extractor=CsvExtractor(path="events.csv", encoding="utf-8",
                               project_id="RETAIL"),
        backend=mem, schema="MINING", transaction_rows=1000,
    ))
    assert result.records == 1
    rows = mem.tables["MINING"]["JOURNEYS"]["rows"]
    assert rows[0]["STEP"] == "login"
    assert rows[0]["SAMPLE_SET"] == "ORIGINAL"
  4. Run the suite with ./test.sh backend, or a single file with cd backend && ../.venv/bin/python -m pytest tests/test_csv_extractor.py.

Rules to design against

A short checklist of the behaviours that most often surprise a first-time extractor author:

Nothing is de-duplicated
The layer appends. It never updates, never merges, never checks whether a row exists. Idempotence, if you need it, has to come from your read cursor — and from the caveat about committed brackets above.
One run per user
A second run for the same user fails immediately. Design any scheduler you build around that, and treat the error as "retry later", not as a data problem.
Declare before you push
define_table fixes the column set and the column order; unknown columns are a hard error, not a warning.
Count skipped items honestly
An item you cannot turn into a record should increment skipped, not raise. Failing the whole run over one malformed source item throws away everything already read.
existing_keys is for metadata only
It reads every key in the table. On a fact table with millions of rows that is a full scan on every run.
Report progress, then report it again
Without progress calls the console shows an indeterminate bar for the whole run. Call it every few hundred items and give a total as soon as you know one.
The id is permanent
The slug is the plug-in key stored and displayed everywhere. Changing it later orphans anything that referenced the old value.
