2 Architecture and the Four Surfaces

Process Mining Demonstrator — Web Edition is not one server but four independent processes: one compute backend and three browser surfaces. This chapter explains what each process does, which ports it listens on, how the browser surfaces pass your identity to the compute backend, where every piece of persistent state is written, and what happens between a click in the browser and a row coming back from Exasol. Read it before you install, before you put the product behind a proxy, and before you plan backups. It is written for administrators and for anyone who needs to reason about the product beyond a single machine.

The four processes at a glance

All four processes are started by the single launcher run.sh (or, in Docker, by the same script used as the image's CMD). They are separate operating-system processes, they can fail independently, and only one of them ever speaks to the database.

The compute backend (port 8000)

The compute backend is the only process that opens a connection to Exasol, the only one that calls a configured LLM server, and the only one that runs analytics. It listens on HTTPS only, on loopback by default (PMW_BACKEND_HOST is 127.0.0.1), and it is never published to the browser. On start it mints an internal self-signed certificate at data/certs/internal.crt and data/certs/internal.key; that certificate exists independently of the user-facing TLS mode, so the hop from the GUI server to the backend is encrypted even when the product is otherwise served over plain HTTP.

Because the browser never talks to the backend directly, the backend can run on a different host — ideally one close to the database. See Splitting the deployment.

Note The backend also hosts the integration API under /api/integration. The integration console has no analytics engine of its own; it proxies to the same backend that the main application uses.

The main application (ports 8080 / 8443)

The GUI server delivers the compiled SPA and acts as the authenticating reverse proxy for /api/*. It holds the session cookie, validates it on every request, and only then forwards the call to the compute backend. Any enabled user may sign in here. Sign-in can be switched off entirely for single-user demonstrations with the Require sign-in for the main application checkbox in the admin Users tab (default: on).

The admin interface (ports 8090 / 8453)

Requires: Administrator

The admin interface is a server-rendered application, not part of the SPA. It manages everything the other surfaces merely consume: users and roles, database connections and their assignments, TLS certificates and mode, the directory (LDAP) configuration, logging, backups, the runtime licence, sign-in page customisation, and the on/off switch for the integration console. It also owns the ↻ Restart app server button that rebinds all listeners after a TLS change.

Two properties make the admin interface the recovery surface of the whole product: it keeps running when the compute backend has stopped (so a licence can always be uploaded), and it falls back to HTTP if the configured TLS mode has no usable certificate (so a bad certificate can never lock you out).

The integration console (ports 8100 / 8463)

Requires: Developer or Administrator

The integration console configures data sources and source types and runs imports into a destination connection. Its ports are derived by convention as admin port + 10 (8090 + 10 and 8453 + 10) unless PMW_INTEGRATION_PORT / PMW_INTEGRATION_HTTPS_PORT override them, and its bind address defaults to whatever PMW_ADMIN_HOST is.

Power users are refused here. A valid password from an account without the Developer or Administrator role is answered with 403 and the message "You need the Developer role to use the integration console. Ask an administrator to grant it." The same gate is repeated inside the compute backend on every /api/integration endpoint, so the restriction cannot be side-stepped by calling through the main application's proxy.

An administrator can switch the console off completely (admin Integration tab, checkbox Enable the integration console). While it is off, browser navigations receive a 503 page titled Console unavailable with the text "The integration console has been turned off by the administrator.", and API calls receive the same text as JSON.

What changes in development mode

./run.sh --dev starts only the compute backend, the admin interface and the Vite dev server on http://localhost:5173. There is no GUI server and no integration console in this mode, and PMW_REQUIRE_PROXY_AUTH is set to 0 automatically because Vite proxies straight to the backend with no authenticating proxy in between. Everything is loopback in development; do not carry that setting into a real deployment.

How a request travels

The following walkthrough covers an ordinary data call in the main application — for example, loading a process map. The integration console follows exactly the same path with its own cookie and its own /api proxy.

  1. The browser requests a page from the GUI server on port 8080 (or 8443 when TLS is on). The SPA is served as static files; nothing about the database is involved yet.
  2. The SPA issues an API call, for example GET /api/graph…, to the same origin. It never addresses the compute backend directly and does not know its address.
  3. The GUI server validates the pmw_session cookie: signature, audience, session epoch, absolute lifetime, and the live user record (the account must still exist, still be enabled, and still hold any role the surface requires). If validation fails, the call is answered with 401 "Authentication required." and never reaches the backend.
  4. Having established who the caller is, the proxy injects the trusted header X-PMW-User with the signed-in username, adds the proxy-authentication secret, and forwards the request to PMW_BACKEND_URL over HTTPS, verifying the backend against the pinned internal certificate.
  5. The compute backend checks the proxy-auth secret first. Only then does it read X-PMW-User, look the user up, apply the endpoint's own role and ownership rules (for example, "You are not allowed to manage connections." for a plain user), and select that user's private database session.
  6. The backend runs the query against Exasol on the user's own pyexasol session, serialised through a per-user lock, and returns JSON. The GUI server passes the response back to the browser and re-mints the session cookie so the sliding idle window stays alive.

Two proxy-level failures are worth recognising on sight: 502 "The compute backend is not reachable. Start it with ./run.sh or check PMW_BACKEND_URL." means the GUI server is up but the backend is not, and 504 "The compute backend timed out." means the backend accepted the call but did not answer in time.

The trusted header and PMW_REQUIRE_PROXY_AUTH

Identity is carried between the surfaces and the compute backend in one plain header, X-PMW-User. That is only safe because the backend refuses every /api/* call that does not carry the proxy-authentication secret, which only the surface processes hold. Without that check, any local process able to reach port 8000 could claim to be any user simply by setting the header.

VariableDefaultMeaning
PMW_REQUIRE_PROXY_AUTH1 (on)The backend requires the proxy-auth secret on /api/*. 0, false, no and off disable it; run.sh --dev sets 0 automatically.
PMW_BACKEND_URLhttps://127.0.0.1:8000Where the surface proxies find the compute backend.
PMW_BACKEND_CA{data}/certs/internal.crtCA bundle the proxy verifies the backend against. Point it at a real CA if the backend is fronted by one, or set it empty to fall back to the system trust store.
Warning Never disable PMW_REQUIRE_PROXY_AUTH in a deployment where anything other than the surface processes can reach the backend port. With the check off, the backend trusts X-PMW-User unconditionally and any caller can impersonate an administrator.

When there is no identity at all

If sign-in is switched off for the main application, no X-PMW-User header is sent. The backend treats this as a single-user deployment: per-user settings and filter presets share one profile, notes have no author, and every power-user endpoint refuses the call because there is no identity to authorise. The integration console ignores the toggle — it always requires sign-in.

Sessions are per surface

Each surface issues its own cookie, and each cookie is bound to that surface's audience. A cookie minted by the main application is not accepted by the admin interface or the integration console, and vice versa. Signing in to one surface does not sign you in to the others.

SurfaceCookieAudienceDefault lifetime when no idle timeout is set
Main applicationpmw_sessionapp12 h (PMW_SESSION_TTL, 43200 s)
Integration consolepmw_integrationintegration12 h (same variable)
Admin interfacepmw_adminadmin8 h (PMW_ADMIN_SESSION_TTL, 28800 s)

All three cookies are HttpOnly, SameSite=Lax, path /, and marked Secure when served over HTTPS. They are stateless and Fernet-signed: the token carries the username, the user's session epoch, the audience, and the original sign-in time, and it is re-minted on every authenticated request. Regardless of activity, a sign-in dies 7 days after it began (PMW_SESSION_MAX_LIFETIME, 604800 s).

Note Separate cookies do not mean separate sign-outs. Signing out anywhere bumps the user's session epoch server-side, which invalidates every outstanding token of that user on all three surfaces. Any password change or admin password reset does the same; the single exception is an administrator changing their own password in the Profile overlay, whose current admin session is re-issued in the same response.

Where state lives

Everything the product must remember lives in one directory, PMW_DATA_DIR — <repo>/data by default, /app/data in the container, bind-mounted from ./data by the shipped compose file. The directory is created on start, is entirely git-ignored, and is the backup unit.

What lives in Exasol

No process-mining data is stored in the data/ directory. Projects, event logs and their annotations live in the Exasol schema named by each connection, in six tables:

PROJECTS
One row per project: PROJECT_ID, TITLE, DESCRIPTION.
JOURNEYS
The event log and the only large table: one row per event step, carrying PROJECT_ID, EVENT_ID (the case identifier), STEP, STEP_ID, EVENT_TIME, three free-form META_* columns and SAMPLE_SET.
STEPS
Per-step presentation and scoring — description, colours, shape, score, end-of-process flag and step group — edited through the app's Step editor.
METAS
The business titles shown for the three META columns.
NOTES
Annotations attached to a node or an edge, including a filter snapshot; created lazily the first time notes are used.
TRANSITIONS_RAW
Optional. A pre-materialised directly-follows pairing that turns the map query into a plain aggregate. It is a snapshot: it goes stale as soon as JOURNEYS changes, and any read failure falls back silently to the live query.

Because analysis data is in the database and configuration is in data/, the two are backed up and moved independently. Restoring data/ onto a fresh host restores users, roles, connections, certificates and settings, but not a single event.

Integration checkpoints

Each integration data source keeps one read checkpoint — byte offset, file size, a signature of the file's first 64 bytes, the cumulative record count and the last error — in security.sqlite3. That checkpoint is shared between manual imports and the file-source watchdog: both triggers advance the same offset, which is exactly what stops the two from importing the same line twice. It advances only after a successful run, so a failed import re-reads the same lines on the next attempt.

One TLS mode for three surfaces

TLS is configured once, in the admin interface's TLS / SSL tab, and applies to the GUI server, the admin interface and the integration console together. Exactly one stored certificate is marked active and is materialised to data/certs/active.crt and active.key so the listeners can read it; certificate private keys are encrypted at rest and written with mode 0600.

ModeMain applicationAdmin interfaceIntegration console
OffHTTP only (:8080)HTTP only (:8090)HTTP only (:8100)
Optional:8080 + :8443:8090 + :8453:8100 + :8463
RequiredHTTPS only (:8443)HTTPS only (:8453)HTTPS only (:8463)

Changes take effect on restart. The ↻ Restart app server button in App Control does this without a terminal: each TLS-aware launcher writes a PID file into data/, and the admin service sends SIGHUP so the listeners rebind with the current plan. If a mode needs a certificate but none is active, every server falls back to HTTP rather than becoming unreachable.

All surfaces send X-Frame-Options: DENY, a frame-ancestors 'none' content-security policy, X-Content-Type-Options: nosniff and Referrer-Policy: no-referrer, plus HSTS when TLS is on.

Warning The per-source-IP sign-in throttle keys on the socket peer address and deliberately ignores X-Forwarded-For. Behind a reverse proxy every client therefore shares one throttle bucket. Terminate TLS at the application itself, as run.sh does, unless you add trusted-proxy handling first.

Splitting the deployment

Because only the GUI server talks to the compute backend, and only the compute backend talks to Exasol, the backend can be moved next to the database while the surfaces stay near the users.

  1. On the database-side host, start the compute backend with PMW_BACKEND_HOST set to an address the surface host can reach, and keep PMW_BACKEND_PORT (default 8000).
  2. Copy the backend's data/certs/internal.crt to the surface host, or place a real certificate in front of the backend.
  3. On the surface host, set PMW_BACKEND_URL to https://<backend-host>:8000 and PMW_BACKEND_CA to the copied certificate (or to the real CA bundle; an empty value falls back to the system trust store).
  4. Leave PMW_REQUIRE_PROXY_AUTH at its default of 1, and firewall port 8000 so that only the surface host can reach it.
  5. Restart both sides and confirm the backend answers on /api/health.

Checking that all four processes are running

  1. Start the stack with ./run.sh (or docker compose up -d --build).
  2. Read the launcher's output. A healthy start prints one line per process: 
    → compute backend on https://127.0.0.1:8000 (TLS, internal cert)
→ admin interface (HTTP 8090 / HTTPS 8453, per TLS mode)
→ GUI server (HTTP 8080 / HTTPS 8443, per TLS mode)
→ integration console (HTTP 8100 / HTTPS 8463, per TLS mode)
  3. Open http://127.0.0.1:8080 (Docker: http://localhost:10080). If the page loads but every data call returns 502, the surfaces are up and the compute backend is not.
  4. Probe the backend directly on the host that runs it: 
    curl -k https://127.0.0.1:8000/api/health
    The -k is required because the backend serves its internal self-signed certificate. This is the same probe the container's HEALTHCHECK runs every 30 seconds.
  5. Open http://127.0.0.1:8090 for the admin interface and http://127.0.0.1:8100 for the integration console (Docker: ports 10090 and 10100). A 503 page titled Console unavailable on the latter means the console is switched off in the admin Integration tab, not that the process failed.
  6. Press Ctrl+C to stop everything: run.sh traps the signal and kills all child processes.
Tip In Docker the four processes share one container and one tini init process, so docker compose logs shows all four interleaved. The container is marked healthy only when the compute backend answers its health probe — the surfaces can be serving pages while the container is still reported unhealthy.
