13 Administration: Users and Permissions

This chapter describes the Users tab of the administration interface: how you create accounts, what each of the three roles (Administrator, Power user, Developer) actually grants, how you enable, disable, unlock and delete accounts, how you reset passwords, and how you allow passkeys and two-factor authentication for individual users or for everybody at once. It also sets out the three global access controls that live on the same tab — whether the main application requires a sign-in at all, when idle sessions are signed out, and after how many failed sign-ins an account is disabled. It is written for administrators. Every action described here requires an administrator account, because the administration interface admits nobody else.

Requires: Administrator

13.1 Opening the Users tab

The administration interface runs on its own port, separate from the main application: http://<host>:8090 or, when TLS is switched on, https://<host>:8453. Only administrators may sign in. Local administrator accounts always work — this is deliberate, so that a directory outage can never lock you out of your own server. Directory (LDAP) accounts reach this interface only when Also allow directory sign-in to this admin interface is ticked in the Directory (LDAP) tab and the account has been promoted to administrator here.

  1. Open the administration interface and sign in.
  2. Select the Users tab in the tab strip (the order is App Control · TLS / SSL · Users · Database Connections · Directory (LDAP) · Logging · Backup · Customize · Integration).
  3. The card header reads “Only enabled users will be allowed to sign in to the main application.”
Note On a fresh installation the built-in account Administrator exists with the password Administrator (the username can be changed with the environment variable PMW_DEFAULT_ADMIN_USER). Until that password is changed, every page of the administration dashboard carries the banner “⚠️ The Administrator account is still using its default password. Change it now in 👤 Profile (top right).” Changing the password clears the banner permanently.

13.2 The three global access controls

Three banners sit above the user list. They apply to the installation as a whole, not to a single account. Each takes effect as soon as it is applied — no restart is needed.

13.2.1 Require sign-in for the main application

A checkbox that applies instantly (toast “Access updated”). The hint under it reads “Users must sign in.” when on, and “The app is open — no sign-in required.” when off. The default is on.

With the box ticked, every visitor to the main application meets the sign-in panel and every /api/* call requires a session; without one the server answers 401 “Authentication required.” Only the health probe is open.

With the box cleared the application runs in open mode: it loads with no sign-in panel and, importantly, with no user identity at all. Per-user settings and filter presets then share a single profile, notes have no author, the sidebar footer (name, Two-factor, Passkeys, Sign out) disappears, the idle auto sign-out stops running, and every power-user and administrator feature is hidden in the browser and refused by the server, because there is no identity to check a role against.

Warning Open mode is a single-user convenience, not a permission level. Turning sign-in off does not make everyone a power user — it makes everyone anonymous, and anonymous callers get 403 from the power-user endpoints. The integration console and the administration interface ignore this toggle entirely; both always require a sign-in.

13.2.2 Auto sign-out after N minutes of inactivity

A number field (0–1440) with a Save button. This is the main application's idle timeout. The hint reads “Idle sessions are signed out after N min.” when N is greater than zero, and “Disabled — sessions never time out on inactivity.” at 0.

In the main application an invisible watcher observes mouse movement, mouse buttons, key presses, touches, scrolling and the wheel. After N idle minutes it signs the user out, and the sign-in panel shows the orange notice “You were signed out due to inactivity.” While the user is active the browser pings the session endpoint (at most every 15–60 seconds) so that the server-side sliding window stays open even when no other request is made.

Note The same value also governs the integration console's server-side session window, but that surface has no client-side watcher. An idle developer is not bounced to the login screen; their session simply expires, and they discover it when their next action fails. The administration interface has its own, separate setting in App Control → Admin session; the value here does not affect it.

13.2.3 Disable an account after N failed sign-in attempts

A number field (0–100) with Save (toast “Failed-sign-in lockout updated”). The hint reads “Accounts (incl. the Administrator) are disabled after N failed sign-ins.” or, at 0, “Disabled — accounts are never locked on failed sign-ins.” Fresh installations default to 3.

The counter records consecutive wrong-password attempts against a local account, pooled across all three surfaces — application, integration console and administration interface share one store. A successful sign-in resets it. The following never count towards it:

  • wrong two-factor codes (a mistyped or expired code can never disable an account),
  • failed passkey ceremonies,
  • directory (LDAP) accounts, which have no local password,
  • attempts against an account that is already disabled.

A locked account shows a red locked pill (tooltip “Disabled after too many failed sign-ins — Unlock to restore.”) and its action button reads Unlock. A lockout also lifts itself after 15 minutes; the expiry is applied lazily at the next sign-in attempt, so simply trying again after the window works. That 15-minute period is fixed — only the threshold is configurable in the interface.

Warning Despite the hint's wording, the built-in Administrator is counted but never automatically locked. It is the break-glass account; its protection is the per-IP throttle and slow password hashing, not a lockout. Other administrator accounts do lock normally. If your only non-built-in administrator locks itself out and you cannot wait out the window, restart the server with PMW_RESET_LOCKOUTS=1 to clear every lockout in the installation.

13.3 Finding and reading a user card

Above the list sit the filter chips All / Local / LDAP, each showing a live count, and a search box “Search users by name…” that matches the username or the display name. When nothing matches, the list shows “No matching users.”

Each user occupies a two-line card:

Line 1
The username (with the smaller display name beside it for directory users), a source pill reading local or LDAP, the role badge, the access pill (enabled in green, disabled or locked in red), and the two per-user checkboxes Passkey and 2FA.
Line 2
“Last sign-in: <date>” (or an em dash when the account has never signed in), followed by the action buttons described in the rest of this chapter.

The role badge condenses the additive role flags into one label. The base segment is admin if the user is an administrator, otherwise power, otherwise user; administrators always show a second segment (power or user) so that you can see whether they also hold power privileges; the dev segment is appended as an add-on. A user with more than one role gets a single animated gradient pill such as admin·power or admin·user·dev; a single role is a plain pill. The tooltip spells the roles out, for example “Roles: administrator, power user (manages own connections), developer (integration console)” or simply “Regular user”.

13.4 Creating a user

Requires: Administrator
  1. On the Users tab, expand the collapsed Add a user section at the foot of the list.
  2. Type the Username. It must be unique among local accounts.
  3. Type an initial Password. There is no confirmation field here, so type carefully; you can always reset it afterwards.
  4. Tick Administrator only if this account is to administer the server. Leave it clear for everybody else.
  5. Select Create user. The new account appears in the list as enabled, with no roles beyond the one you ticked.
  6. If the account also needs the power or developer privileges, grant them from the buttons on the new card (see 13.5). There is no checkbox for them at creation time.

Note You do not create directory users here. An LDAP account appears in the list automatically after its first successful sign-in, provisioned as a plain, enabled user. From that moment it behaves like any other row: you can grant it roles, allow passkeys and two-factor, assign database connections, disable it or delete it. Administrator rights are never granted by the directory — a local administrator must promote the account here.

13.5 Roles and what each one grants

Roles are independent, additive flags, not a ladder. A user can hold any combination of Administrator, Power and Developer; the implicit base is the plain user. In the main application's sidebar footer the identity is labelled with the highest role held (Admin > Power user > Developer > User), which is a display convenience only — the underlying flags are checked individually.

13.5.1 Administrator

Grants access to this administration interface and everything in it: users and permissions, TLS certificates, the directory configuration, logging, backups and restores, the licence, customisation, and switching the integration console on or off. An administrator also manages all database connections, not merely their own, and has the power-user analysis features in the main application.

Grant or revoke it with Make admin / Remove admin on the user's card.

13.5.2 Power user

A main-application privilege. Power users create and manage their own database connections from the application sidebar, and they get the advanced-analysis views — Conformance Check, Happy Path and Simulation — which are hidden from the view menu for plain users. They may also use journey sampling (creating and deleting representative subsets and A/B sources); the server refuses it for anyone else with “Journey sampling is available to power users and administrators only.”

Grant or revoke it with Make power / Remove power.

13.5.3 Developer

Purely an additional access grant to the integration console (the separate surface on :8100 / :8463). It does not include any power-user feature, although developers, like power users, may manage their own database connections. A user who holds only the Developer role sees the ordinary main application, plus the integration console.

Grant or revoke it with Make developer / Remove developer. Both actions are recorded in the shared log as “granted/revoked the Developer role for '<user>'”.

13.5.5 Role changes take effect immediately

Every request re-validates the session against the live user record, so a role change does not wait for the user to sign out. Revoking the Developer role from someone who is working in the integration console drops them, on their very next request, to a full-page Access denied screen reading “The integration console is available to developers and administrators only. Ask an administrator to grant you the Developer role.” with a ⏻ Sign out button. Anything they were driving from that console is no longer theirs to start, stop or monitor there. Revoking the administrator role ends their administration session the same way; revoking the power role removes the advanced views and refuses their sampling calls from that moment on.

Warning Revoke a role only when you are prepared for work in flight to be interrupted. There is no grace period and no warning shown to the user before the change lands.
Note The server refuses any change that would leave the installation without an administrator: “This would leave no enabled administrator. Promote or enable another admin first.” Promote or enable the replacement before demoting or disabling the incumbent.

13.6 Enabling, disabling and unlocking accounts

Requires: Administrator

Only enabled users may sign in to the main application. The card's first action button reads Disable for an enabled account, Enable for one you disabled, and Unlock when the account was disabled by the failed-sign-in lockout rather than by you.

  1. Find the account with the search box or the All / Local / LDAP chips.
  2. Select Disable to bar the account, or Enable / Unlock to restore it.
  3. Check the access pill afterwards: enabled (green), disabled or locked (red).

Disabling is immediate and retroactive: the account's live sessions are re-validated on their next request and die, on all three surfaces at once. A user whose password is correct but whose account you disabled is told exactly that — “This account has been disabled. Contact an administrator.” — while someone typing a wrong password only ever sees the generic “Invalid username or password.” The specific reason is revealed only after the password has been proved, so that the messages cannot be used to discover which accounts exist.

Tip Disabling and re-enabling an account clears its failed-sign-in counter, so it doubles as a manual reset when someone has been fumbling their password but is not yet locked out.

13.7 Resetting a password

Requires: Administrator
  1. Find the user's card. The Reset password button is shown for local users only — it is hidden on LDAP rows, because those accounts have no local password.
  2. Select Reset password. The browser prompts “New password for <user>:”.
  3. Type the new password and confirm the prompt. An empty value is refused with “Password is required.”
  4. Communicate the password to the user by a channel other than the one you are administering.
Warning Any password change bumps the user's session epoch, which invalidates every outstanding session token for that user on all three surfaces. Someone whose password you reset while they are working is silently signed out at their next request and must sign in again with the new password. This is the intended behaviour for a compromised account; it is a surprise if you meant it as a courtesy.
Note Administrators change their own password in the 👤 Profile overlay (top right), not here. That path is the one exception to the rule above: the current session is re-issued in the same response, so the administrator making the change stays signed in while all of their other sessions are invalidated. The log records “changed their password — other sessions invalidated”.

13.8 Allowing passkeys

A passkey (Touch ID, Windows Hello, a security key) is an alternative to the password, never a replacement: the password always remains a fallback. Users cannot enrol one until you allow it. The master row above the list carries the caption “Passkey and two-factor are optional alternatives/additions to the password (which always works).”

13.8.1 Allowing a passkey for one user

  1. Find the user's card.
  2. Tick the Passkey checkbox on line 1 (tooltip “Allow this user to enrol and sign in with a passkey”). The change applies at once.
  3. Tell the user to open 🔑 Passkeys in the application sidebar footer — or, for an administrator, 👤 Profile → Passkeys — name the device and select Add a passkey.

13.8.2 The all-users master toggle

The All users: row offers a Passkey checkbox (tooltip “Allow every user to enrol and sign in with a passkey”). It is shown as ticked only when every user currently holds the permission, and toggling it writes the flag for all existing users at once (toast “Passkeys allowed/disabled for all users”).

Note The master toggle is a bulk edit, not a default. It changes the users who exist at the moment you click it; accounts created afterwards start without the permission and need their own tick.

13.8.3 Consequences and prerequisites

  • Revoking the permission blocks passkey sign-in immediately. It is checked at every step of the ceremony, and the management controls disappear from the user's interface. The registered credentials are not what is checked at sign-in time — the permission is — so revocation is an effective, instant kill switch.
  • A passkey registered on a host works on all surfaces of that host: application, integration console and administration interface share the relying-party identifier (the hostname without the port).
  • Passkeys require a WebAuthn-capable browser, a secure context (HTTPS, or localhost) and a real hostname. WebAuthn rejects bare IP addresses and single-label hosts. Reached by IP, the sign-in button and the management controls hide themselves and the user sees “Passkeys need a hostname, not an IP address. Reach the server by its name over HTTPS — e.g. its ‘.local’ name — instead of its IP, then try again.”
  • Sign-in is username-first: the user types their username, then selects 🔑 Sign with Passkey. There is no one-click, usernameless flow.
  • If the application and the administration interface live on different sub-domains, set PMW_PASSKEY_RP_ID to the shared parent domain and list the expected origins in PMW_PASSKEY_ORIGINS.
Warning A passkey sign-in satisfies two-factor by itself and skips the code step, even for users who are enrolled in TOTP. If your policy is “always a one-time code”, do not allow passkeys.

13.9 Allowing two-factor authentication

Two-factor authentication is a time-based one-time code (TOTP) layered on top of the password. Two independent facts govern it per user: whether you have allowed it, and whether the user has enrolled (confirmed a code from their authenticator app). One secret protects all three surfaces.

13.9.1 Allowing 2FA for one user or for everybody

  1. Find the user's card and tick the 2FA checkbox on line 1 (tooltip “Allow this user to set up two-factor (TOTP)”), or
  2. tick the 2FA checkbox in the All users: master row to write the flag for every existing user at once (toast “Two-factor allowed/disabled for all users”).
  3. Tell the user what will happen at their next sign-in (see below). No further administrator action is needed.
Warning Allowing 2FA is the same thing as requiring it. A user who is allowed but not yet enrolled cannot decline: their next sign-in — on the application, the integration console or the administration interface — halts after the password and forces enrolment. The caption changes to “Set up two-factor to continue”, a QR code appears with the text “Two-factor is required for your account. Scan this with an authenticator app (Google Authenticator, 1Password…), then enter the 6-digit code.”, and no session is issued until a correct code confirms the authenticator. Nothing is stored server-side until then, so there are no half-enrolled accounts.

Immediately after a successful enrolment the user is shown 10 recovery codes, once, under the heading “Save your recovery codes” with the text “Each works once if you lose your authenticator. They won't be shown again.” Each code works exactly once, anywhere a TOTP code is accepted. They are stored only as salted hashes: you cannot view or recover them for a user, and regenerating a set invalidates the previous one entirely.

13.9.2 Resetting 2FA for a user who lost their authenticator

There is no administrator command that resets an enrolment while preserving it. The supported recovery path is to withdraw the permission, let the user back in with their password alone, then restore the permission so that they enrol afresh.

  1. Ask the user first whether they still have an unused recovery code — entering one at the code step signs them in without any administrator involvement.
  2. If not, find their card and untick the 2FA checkbox. Password-only sign-in works again from that moment.
  3. Have the user sign in and, from the sidebar, open 🔒 Two-factor and select Turn off, entering a current code if they can — this deletes the stale secret and its recovery codes. If they cannot produce a code, leave the enrolment in place and continue.
  4. Re-tick the 2FA checkbox on their card when they are ready to enrol the new device.
Warning Un-ticking 2FA does not delete the enrolment — it only relaxes the login gate. Re-ticking the box re-arms the same authenticator instantly, with no new enrolment step. If the old authenticator is in the wrong hands, have the user turn two-factor off from their own sheet (which does delete the secret and the recovery codes) before you re-allow it, or reset their password as well.
Note A user cannot silently strip their own two-factor: turning it off requires a current code or a recovery code, so a hijacked session cannot remove the second factor. Wrong codes are throttled per source IP but never count towards the account lockout — a mistyped code can never disable an account.

13.10 Deleting a user

Requires: Administrator
  1. Find the user's card.
  2. Select the danger button Delete.
  3. Confirm the dialogue Delete user "<name>"?.

Deleting an account also deletes its passkeys and its recovery codes, and any live session it holds fails on its next request. Deleting a directory user removes the local row only; the account still exists in the directory and will be re-created as a plain, enabled user the next time it signs in successfully — with every role, permission and connection assignment gone. Prefer Disable when you want the account kept but barred.

Warning Deletion is not offered as reversible anywhere in the interface, and the deletion is recorded in the shared log at WARN severity so that it stands out during an audit.

13.11 The built-in Administrator

The bootstrap account is protected in the interface and again on the server, so the protection holds even for a hand-crafted request:

Attempted actionServer response
Disable itThe built-in Administrator account cannot be disabled.
Remove its administrator roleThe built-in Administrator account must remain an administrator.
Delete itThe built-in Administrator account cannot be deleted.

Its card therefore shows only the Passkey and 2FA checkboxes, Reset password, an Unlock button if it is ever flagged as locked, and the note built-in admin (tooltip “The built-in administrator cannot be disabled, demoted or deleted.”).

Tip Treat the built-in Administrator as a break-glass credential: give it a long, unique password, store that password where your organisation stores emergency credentials, and do the day-to-day administration from a named personal administrator account so that the log attributes every change to a person.

13.12 Working to least privilege

The role flags are independent precisely so that you can grant the narrowest useful set. The following practices follow from the behaviour described above.

Start every account as a plain user
Creating a user without the Administrator tick and adding Make power or Make developer only when a concrete task requires it costs one extra click and avoids the far more common mistake of a whole team holding administrator rights.
Do not use Administrator as a synonym for “experienced”
The advanced-analysis views and journey sampling come from the power flag, not from the administrator flag. An analyst who needs Conformance Check, Happy Path and Simulation needs Make power — nothing more.
Grant Developer only for the integration console
It confers no power features. If a data engineer also needs sampling or the advanced views, grant both flags explicitly rather than reaching for the administrator role.
Keep at least two administrators
The server refuses to leave you with none (“This would leave no enabled administrator. Promote or enable another admin first.”), but a single administrator who forgets their password and is not the built-in account is an avoidable outage: other administrator accounts do lock after the configured number of failed attempts.
Prefer Disable to Delete
Disabling bars the account and kills its sessions at once while preserving its roles, connection assignments and history. Delete when the person has left for good.
Decide the second factor as a policy, not per person
Because a passkey sign-in skips the code step, allowing both passkeys and 2FA for the same population means the effective second factor is whichever the user chooses. If a code is mandatory in your organisation, allow 2FA and leave passkeys off.
Review the list periodically
Use the LDAP chip to see which directory accounts have signed in at least once and now hold local roles, and the “Last sign-in” line to spot dormant accounts. Directory users keep their locally granted roles until you remove them, even if the directory entry changes.
