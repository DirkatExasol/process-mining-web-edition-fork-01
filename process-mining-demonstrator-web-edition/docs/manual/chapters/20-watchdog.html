20 The Watchdog: Automatic Imports

A manual run imports a file when you press a button. The watchdog imports it whenever it grows — unattended, without a browser, without anybody being signed in. This chapter explains what the watchdog does and how it differs from a manual run, how to switch it on for a file source and which destination it writes into, why that destination has to be stored with the source, how the authorisation is re-checked on every single poll, how to read and reset the checkpoint, where failures are recorded, and which deployment-wide switches an operator has over the whole loop. It is written for developers who configure sources in the integration console, and for the administrator or operator who runs the server they sit on.

Requires: Developer or Administrator — the watchdog is configured in the integration console (HTTP :8100, HTTPS :8463), which only these two roles may sign in to. The deployment-wide switches in section 20.10 are environment variables and require access to the server, not to any screen.

20.1 What the watchdog does

The watchdog is a single background loop inside the compute backend. It starts with the backend process and is cancelled when the backend shuts down. On every tick it lists all file sources of all owners, decides which of them are due, and polls each due source in turn: it opens the source's file, reads the complete lines that have been appended since that source's checkpoint, runs them through the linked source type exactly as a manual import does, writes the resulting events into the configured destination, and advances the checkpoint.

Everything the extractor does is identical to a manual run — the same regexes, the same compound step rules, the same timestamp normalisation, the same MD5 pseudonymisation of the case id, the same automatic creation of missing PROJECTS, STEPS and METAS rows, and the same transaction bracket (rows per transaction, default 5000). What differs is who triggers it, what it is allowed to read, and where the result is reported.

Manual run (Run dialog)Watchdog poll

Both triggers share one checkpoint per source. That is deliberate: it is exactly what stops a manual top-up and the watchdog from importing the same line twice between them.

20.2 Switching the watchdog on for a source

The watchdog is configured inside the source itself, on step 2 of the source wizard, in the panel headed 👁 Watchdog — auto-import new lines when the file grows. The panel explains itself on screen: “A background job watches this file and imports only the newly-appended lines into the destination below. A checkpoint is kept per file, so nothing is imported twice — even across restarts.”

  1. In the sidebar, open the Sources section and click the source you want to automate. (To create one first, use the ＋ button; see the previous chapter.) The wizard opens at step 2, Configuration.
  2. Check that File path or glob points at the file that grows, and that a Source type is selected. A source with no source type linked can never be imported, by hand or by watchdog.
  3. Tick the checkbox in the 👁 Watchdog panel. Three further fields appear.
  4. Choose the Destination connection. The dropdown lists the connections assigned to you and starts on “— pick a connection —”. If it is empty you will see “No connections are assigned to you — ask an administrator, or create one in the main app.”
  5. Type the Project id the events are written into, for example LIVE-LOG. The PROJECTS row is created for you on the first import if it does not exist.
  6. Set Every (seconds) — the poll interval. The default is 30 and the minimum is 5.
  7. Click Next, review step 3, then Save changes (or Create source for a new source).

Destination connectionyesnoneMust be a connection assigned to you, both now and at every later poll (20.5).

If you enable the watchdog but leave the destination or the project id blank, saving is refused and the wizard returns you to step 2 with “The watchdog needs a destination connection and a project id.” If the connection you picked is not assigned to you, the backend refuses the save with “The watchdog's destination connection is not assigned to you.”

Tip Once the watchdog is on, the source badge in the sidebar gains a 👁 eye after its name (tooltip “Watchdog on — auto-imports new lines”), and its ▷ Run button turns green with the tooltip “Watchdog active — run an import now as well”. You can still run a watched source by hand at any time; because both share the checkpoint, the manual run simply takes whatever the watchdog has not yet picked up.

20.3 Why the destination is stored with the source

A manual run can ask you where to write, because you are standing in front of it. The watchdog cannot: it runs headless, with no signed-in user, no browser and no active database session. There is nothing to ask and nobody to ask. The destination therefore has to be part of the source's own configuration — the connection id and the project id are stored in the source's watchdog block, and the loop uses the connection's stored credentials (the username and password an administrator saved on the connection) to open the database for the duration of the poll and close it again afterwards.

This is the same mechanism the manual run uses when you name a connection you are not currently connected to, and the same one the administrative rebuild job uses. It is what makes an import possible with no session at all.

Note Because the watchdog acts as the source's owner, its run updates that owner's status, KPIs and pipeline in the console — not the administrator's. If a developer's watchdog is importing, that developer sees it live in their own console; nobody else does.

20.4 The authorisation model

Storing credentials with a source raises an obvious question: what stops a developer from pointing a watchdog at a connection they were never given? The answer is that the assignment is the gate, and it is checked twice.

  • At save time — enabling the watchdog on a connection that is not assigned to you is rejected outright with “The watchdog's destination connection is not assigned to you.” This is a fail-fast convenience, not the real protection.
  • On every poll — before it opens anything, the loop re-checks that the source's owner is still assigned to the destination connection. This check is repeated for the lifetime of the watchdog, on every single poll.

The consequence is the one administrators care about: revoking a connection assignment stops that user's watchdogs immediately. The very next poll fails with The destination connection is not assigned to you., the checkpoint does not advance, and nothing further is written. There is no window in which a stored connection id keeps writing with credentials the user no longer has rights to.

Warning Revoking access stops future imports; it does not remove what has already been imported. Rows written by earlier polls stay in the destination schema and must be removed there (for example from the Projects tab of the connection editor) if they should not remain.

20.5 When a poll happens

Two intervals combine.

The loop tick
The background loop wakes every PMW_INTEGRATION_WATCHDOG_TICK seconds — default 10, hard minimum 5. On each tick it lists every file source of every owner and decides which are due. This is deployment-wide.
The per-source interval
Every (seconds) in the source's watchdog panel — default 30, minimum 5. A source is due when it has never run, when its checkpoint has no usable timestamp, or when at least this many seconds have elapsed since the checkpoint was last touched.

Because the tick is the loop's own heartbeat, a source is never polled more often than the tick: setting an interval of 5 seconds on a deployment ticking every 10 gives you a poll roughly every 10 seconds, not every 5.

Note “Since the checkpoint was last touched” means exactly that: every checkpoint write updates the timestamp, including a poll that found nothing new and including a manual run. The interval therefore measures the time since the last import activity of any kind on that source, not since the last import that actually wrote rows.

20.6 What one poll reads

A poll reads only complete lines beyond the stored byte offset; a partial trailing line that the writing application has not finished is left for the next poll. Blank lines are skipped and each line is truncated to its first 2000 characters, exactly as in a manual run.

A single poll reads at most 8 MB of new bytes. A larger backlog — typically the first poll on a file that already existed — is drained across successive polls, 8 MB at a time, until the file is caught up. This is normal and needs no intervention; it simply means the first few polls after enabling a watchdog on a large file import a slice each.

Rotation and replacement are detected automatically. If the file has shrunk below the stored offset (truncation, or a fresh file at the same name), reading restarts from byte 0. If the file's head has changed — the watchdog fingerprints the first 64 bytes — while the size did not shrink, the stored offset is assumed to point into unrelated content and the file is likewise re-read from byte 0.

Warning Events are appended and never de-duplicated. Anything that makes the watchdog re-read from byte 0 — a detected rotation, a checkpoint reset, a change of file path — imports that file's events into the project a second time. The database has no idea it has seen them before.

20.7 The checkpoint status display and Reset

The checkpoint is the watchdog's memory: how far into the file it has read, how large the file was, the fingerprint of its head, how many events it has imported in total, when it was last touched, and the last error if there was one. It is shown in two places.

In the source wizard, directly under the watchdog fields (for a source that already exists), you see one of:

In the Run dialog the same checkpoint appears in more detail: “✓ <n> records imported · read to <bytes> of <bytes> bytes · last <date and time>”, or the red error, or “No checkpoint yet — this is the first import of this file.” The two byte figures tell you whether a backlog is still draining: while “read to” is smaller than the file size, more is pending.

20.7.1 Resetting the checkpoint

Both places carry a ↺ Reset checkpoint button (in the Run dialog it is disabled while a run is in flight or when no checkpoint exists; its tooltip reads “Forget how far the file has been read, so the next import starts from the top”).

  1. Open the source in the wizard, or open the Run dialog from the ▷ button on the source badge.
  2. Click ↺ Reset checkpoint. The stored offset, size, fingerprint, record count and last error are discarded.
  3. The next import — whether the next watchdog poll or a manual run — starts at byte 0 of the file.
Warning A reset forgets a position; it deletes nothing from the database. Re-importing after a reset writes the file's events into the project a second time. If you want a clean reload, delete the project in the destination schema first (connection editor, Projects tab), then reset.
Note Changing a source's File path or glob deletes its checkpoint automatically — the old offset means nothing in a different file — so the next poll reads the new file from the beginning. Renaming the source, or editing any other field, keeps the checkpoint.

20.8 When a poll fails

A watchdog runs unattended, so a silent failure would go unnoticed. Every failure is therefore recorded in two places at once: on the source's checkpoint, as the last error you see in the wizard and the Run dialog, and in the admin log as a warning under the tag DATA, operation import, attributed to the source's owner. The log line reads:

watchdog import failed: '<source name>' — <message>

The offset does not advance on failure, so the next poll retries exactly the same lines. One misconfigured source never stops the other sources and never stops the loop.

Successful polls are logged too. When new lines were imported, the admin log records, at usage level under tag DATA:

watchdog imported <n> new event(s) from '<source>' into <connection>/<schema> (project <id>)

Problems with the loop itself, rather than with one source, appear as watchdog: could not list sources: <error> and watchdog: source '<name>' poll failed: <error>.

Warning If rows per transaction is greater than 0 and a poll fails part-way through, the brackets already committed stay committed, but the checkpoint does not advance. The next poll therefore re-reads those lines and can write them a second time. Set the transaction bracket to 0 (“one transaction for the whole import”) if a failed import must be all-or-nothing; the cost is that the database holds the entire import open.

20.9 Watching the watchdog from the console

A watchdog import is a normal run of the abstraction layer, tagged with the trigger watchdog, so it shows up everywhere a manual run does.

  • The Abstraction layer card switches to Running while a poll imports, then Completed or Failed, and its Run log carries lines such as “watchdog: 14 new line(s) from /var/log/app/access.log → …” and “pushed 500 events, skipped 2 unparseable line(s)”. A failed run is repeated as the banner “Last run failed: <error>”.
  • The KPI strip separates the two triggers: Manual imports (▷) and Watchdog imports (👁) count the recorded runs of each kind, while Watchdogs active (🐕) shows a live “<active> / <total>” — your file sources with the watchdog switched on out of all of them — and turns green when at least one is active.
  • The pipeline flowchart adds an edge for each combination that has actually run, so a watchdog's source type, source and destination appear on the canvas alongside your manual imports, with the cumulative row counts on the source and connection nodes.
Note Only one extraction runs per user at a time. If you press ▷ Run extraction while your own watchdog is mid-import (or the other way round), the second one is refused with An extraction is already running for this user. For a manual run this appears as an error in the Run dialog; for the watchdog it is recorded on the checkpoint as Import failed: An extraction is already running for this user. and retried automatically on the next poll. Different users are unaffected by each other.

Requires: Administrator / server operator — these are environment variables read at backend start, not settings in any interface.
VariableDefaultEffect
PMW_INTEGRATION_WATCHDOGon (1)The global on/off switch for the whole loop. Truthy values are 1, true, yes, on. When it is off, the loop exits immediately at start-up and no source is ever polled, whatever its own watchdog setting says.

# disable all automatic imports on this backend
PMW_INTEGRATION_WATCHDOG=0

# or keep them, but only look every 30 seconds
PMW_INTEGRATION_WATCHDOG_TICK=30

The console does not hide the fact that the loop is off. The status endpoint reports it, and the Watchdogs active KPI tile relabels itself to Watchdogs (off) and turns orange — so a source whose watchdog is “on” but that never actually polls is visible at a glance instead of quietly doing nothing.

Tip Switching the loop off is the cleanest way to freeze all automatic ingestion during a database migration or a maintenance window. Per-source settings and checkpoints are untouched; when you switch it back on, each due source resumes from exactly where it stopped.

20.11 Operational guidance: log rotation

The watchdog is normally pointed at a file that a live application keeps appending to, which in practice means a file that some rotation scheme keeps renaming, compressing or truncating. The detection described in 20.6 handles the common cases, but a few operational rules keep it reliable.

  • Poll considerably faster than you rotate. The watchdog only ever looks at the configured path. Lines that are written to the active file and then rotated away before the next poll are never read, because the file at that path is a different file by the time the watchdog gets there. An interval of 30 seconds against an hourly rotation is safe; an interval of ten minutes against a rotation every five is not.
  • Point the source at the stable name. Configure the path of the live file (access.log), not of a rotated generation (access.log.1). The label on the field says “File path or glob”, but the path is resolved to one regular file — wildcards are not expanded, so a pattern intended to match rotated generations simply fails with File not found.
  • Copy-truncate and create-new are both detected. Truncation is caught by the size dropping below the stored offset; a brand-new file at the same name is caught by the changed fingerprint of its first 64 bytes. Either way the watchdog restarts at byte 0 of the new file.
  • Beware very small files. A file shorter than 64 bytes cannot be fingerprinted. If such a file is replaced in place by another one of the same or greater size, the replacement goes undetected and the watchdog carries on reading from the old offset. Files of that size are rarely worth watching in the first place.
  • Expect a burst after every rotation. Because a detected rotation re-reads from byte 0, the poll after a rotation imports the whole of the new file so far. That is correct for a genuinely fresh file — but if your rotation scheme seeds the new file with content that was already imported, those events are appended again.
  • Keep the sandbox in mind. Source paths are confined to the integration files directory unless the deployment has explicitly opted out. If your log lives elsewhere, arrange for the rotation scheme to write or link into that directory rather than loosening the sandbox.
  • Watch the skipped counter. A rotation that changes the log format (a new application version, a different formatter) produces lines that the linked source type's regexes no longer match. The import will not fail; it will succeed with everything skipped. The orange Events skipped KPI is your early warning.
Note Nothing about the watchdog depends on the console being open. It lives in the compute backend, polls on its own timetable and writes with stored credentials. Closing the browser, signing out, or never signing in at all changes nothing — only the two environment switches in 20.10, the per-source checkbox, and the connection assignment do.
