19 Sources and Running an Import

A source tells the integration console where the raw data is; a source type (Chapter 18) tells it how to read each line. This chapter covers the remaining half of the job: creating a File source, pointing it at a file inside the sandboxed sources directory, previewing the lines, linking a source type, choosing how often the import commits, and then running the import into a destination connection and project. It closes with the two things that surprise people most — how the read checkpoint decides what a delta import picks up, and the fact that events are always appended and are never de-duplicated. Read it before you import into a schema anyone else relies on.

Requires: Developer or Administrator. Sources, source types and checkpoints are owned per user — you only ever see and run your own.

19.2 Where source files must live

Every file read by the console — the preview, a manual import, a watchdog poll — goes through one path resolver. By default that resolver confines you to a single directory, the sources directory, so that a developer account cannot use the console to read arbitrary files from the server.

SettingDefaultEffect
PMW_INTEGRATION_FILES_DIR<data dir>/integration_files, where the data directory is PMW_DATA_DIR or <project root>/dataThe sandbox root. Created automatically at start-up, parents included. In Docker it is a mounted volume, so you can drop log files into it from the host.
PMW_INTEGRATION_ALLOW_ANY_PATHoffWhen set to 1, true, yes or on (case-insensitive), the sandbox is switched off entirely and any absolute path the server process can read is accepted; ~ is expanded.

In the default, sandboxed mode the rules are:

  • A relative path is taken relative to the sources directory — so access.log means <files dir>/access.log.
  • An absolute path is accepted only if it already lies inside the sources directory.
  • The real path is resolved with symlinks followed, and the result must still be inside the (likewise resolved) root. Traversal with ../ and symlinks pointing outside are rejected.
Error textCause
No file path given.The path is empty or only whitespace.

Tip On start-up the backend copies every *.log file from the installation's examples/ directory into the sources directory, unless a file of that name is already there. Existing files are never overwritten, so you can experiment with the bundled demo log immediately, and your own edits to it survive a restart.

19.3 Creating a File source

Sources are created and edited in the same three-step wizard. The footer always shows Step N of 3 together with Cancel, Back and Next, and on the last step Create source or Save changes. Opening an existing source from the sidebar takes you straight to step 2, since its kind is already fixed.

  1. In the sidebar, open the Sources section and click ＋ (Add a source). The New source sheet opens at step 1.
  2. On Choose a source kind, select the File card — “A log or data file the extractor reads at run time.” A green dot marks the selected kind. Click Next.
  3. Enter a Name (required; for example File — access log). Next stays disabled until the name is filled in.
  4. Fill in File path or glob, the required field marked with *. Type a path relative to the sources directory, or an absolute path inside it.
  5. Choose the Encoding that matches the file: utf-8 (default), latin-1 or utf-16.
  6. Check the Preview box underneath (see §19.3.2) to confirm the console is reading the file you meant.
  7. Pick the Source type that parses these lines. The first entry is — none —, which is also the default.
  8. Set the ⇄ Transaction bracket if the default of 5000 rows per commit does not suit the import (see §19.4).
  9. Optionally switch on 👁 Watchdog — auto-import new lines when the file grows and complete its destination fields (Chapter 20).
  10. Click Next, check the review page — kind icon, name, and every configured field as label → value — and click Create source.

19.3.2 The line preview

Below the path field, the row Preview first [N] lines shows the beginning of the file exactly as the extractor will see it. N defaults to 5 and is clamped to 1–50; an invalid entry falls back to 5. The preview refreshes roughly 350 ms after you stop typing in the path or changing N.

What you seeMeaning
Monospace linesThe first N non-blank lines. Blank lines are skipped everywhere — preview, import and progress counting.
A trailing …Further non-blank content follows the lines shown.

“No lines.”The file exists but has no non-blank content.
Red textA sandbox or file error, verbatim — for example File not found.
Note Two limits apply to the preview and to the import alike. Every line is truncated to its first 2000 characters, so a regex aimed at content beyond that never matches. And the preview always decodes as UTF-8, whatever Encoding you selected — a latin-1 file may therefore look slightly wrong in the preview yet import correctly.

19.3.3 Linking a source type

The linked source type is what turns a line into an event: its timestamp, id, step, meta and helper regexes plus any compound step rules are applied to each line at run time. Two consequences are worth remembering:

  • A source with — none — selected cannot be run. The Run dialog shows the banner “This source has no source type linked — edit it and pick one so the lines can be parsed.” and ▷ Run extraction stays disabled.
  • Deleting a source type does not cascade. Sources that referenced it keep a dangling link and behave exactly as if none were selected until you pick a new one.
Warning Changing the File path of an existing source deletes that source's read checkpoint. The next import — manual or watchdog — therefore reads the new file from the very beginning. That is usually what you want, but if the new path points at the same content under a different name, everything is imported again.

19.4 The transaction bracket

The ⇄ Transaction bracket panel holds a single number input labelled rows per transaction. Rows are written inside a transaction and committed as soon as that many rows have been written; when you set it to 0 the label gains the suffix (one transaction for the whole import).

Value enteredValue usedBehaviour
(blank or non-numeric)5000The default.
0 or negative0One single transaction for the whole import — all rows become durable together, or none do.
1–9991000Raised to the minimum bracket.
1000–1000000as enteredCommits every n rows.
above 10000001000000Clamped to the maximum.

A larger bracket means fewer, bigger transactions — more atomic, but the database holds more work open at once. A smaller one commits steadily, so a failure part-way through leaves the already-committed rows in place and makes progress durable as the run proceeds. The number of brackets committed so far is reported in the status panel as commits. Autocommit on the destination driver is switched off for the duration of every run, so the bracket — not the driver — decides when work becomes durable. The setting applies to manual runs and to watchdog imports alike.

Warning With a bracket greater than 0, a run that fails half-way leaves the brackets it already committed in the database, while the checkpoint stays where it was (§19.6). Retrying therefore re-reads those lines and writes them a second time. If a mid-run failure must never duplicate rows, set rows per transaction to 0 and accept one long-open transaction instead.

19.5 Running an import

Click the ▷ button on a source badge (tooltip Run extraction) to open the Run “<source name>” sheet.

  1. Choose the Destination connection. The dropdown offers — pick a connection — plus every connection assigned to you. Under it, the target summary reads <host>:<port> — writes into schema <schema>, or “(none set)” when the connection has no schema.
  2. Choose the Project. The first entry is ＋ New project…; below it are the projects already present in that schema, shown as <projectId> — <title>.
  3. If you picked ＋ New project…, type the identifier into New project id (for example RETAIL-DEMO). It is written into JOURNEYS.PROJECT_ID for every event, and the PROJECTS row is created for you.
  4. Decide whether ⏩ Delta upload — import only what was appended since the last import stays ticked. It is on by default.
  5. Check the checkpoint panel underneath so you know what the run will read (§19.6).
  6. Click ▷ Run extraction. The button reads “Running…” while the import is in flight; Cancel becomes Close once a result is shown.

19.5.1 The destination connection

You do not need to connect to the database in the main app first. The backend opens the chosen destination itself, using the connection's stored credentials, and closes it again when the run ends — including when it fails. The exception is a connection you happen to be actively connected to in the main app: that live session is reused instead, with autocommit turned off for the run.

The dropdown pre-selects, in this order: the connection this source last imported into (remembered on the server per source, and dropped if the assignment has since been revoked), then the main app's currently active connection, then the first connection assigned to you.

Note The dropdown is a convenience, not the authorisation. The server re-checks that the connection is assigned to you on every run. An unassigned — or simply non-existent — connection id both return the same message, Connection not found., so that knowing an id reveals nothing about whether it exists.

If nothing is assigned to you the sheet shows the banner “No connections are assigned to you — ask an administrator, or create one in the main app.” If the connection cannot be opened, the run fails with Could not connect to “<name>”: <error>; if it has no target schema, with “<name>” has no target schema configured.

19.5.2 Choosing the project

Filling the project list opens the destination database on demand; while that happens the sheet shows “Reading the projects in that schema…”. The outcomes are:

Projects found
They are listed with their identifier and, when different, their title. The project you last imported into is pre-selected — but only when the same connection is selected; on a different connection nothing is pre-selected.
None found
“That schema has no projects yet — this import creates the first one.” A reachable schema that has no PROJECTS table at all counts as an empty list, not an error.
Listing failed
An orange line, “Could not list existing projects (<error>) — you can still type a new project id below.” The import itself is unaffected.

If the remembered project no longer exists in that schema, its identifier is kept in the New project id field rather than being silently discarded, so a re-created project keeps its name.

Warning — events are appended and never de-duplicated Selecting an existing project shows the banner “Events are appended to “<id>” (<n> already stored)”. There is no de-duplication anywhere in the pipeline: nothing compares a new row against what is already in JOURNEYS. With Delta upload on, only newly-appended lines are read, so nothing is stored twice. With it off, the whole file is read again and every event already imported is written a second time. To reload a project from scratch, delete the project first (the connection editor's Projects tab does this) and then import with delta upload switched off.

19.5.3 Delta upload

⏩ Delta upload is ticked by default. With it on, a checkpoint records how far the file has been read and the run picks up only the lines appended since — the help text reads “no duplicates”. With it off, the file is read from the top, ignoring the stored offset, and the run restarts the checkpoint's imported-records counter rather than adding to it.

Note One read consumes at most 8 MB of new bytes. The first delta run on a large existing file therefore imports only the first ~8 MB; run it again (or let the watchdog poll again) to continue draining the backlog, cap by cap.

While the import runs, a progress bar shows Importing <done> / <total> log records…, or Reading the file… and an indeterminate animation before the totals are known. The same progress appears on the Abstraction layer node of the pipeline canvas, since both read the same live status, polled every 350 ms.

Note Only one extraction per user may run at a time. Starting a second — including a manual run while your own watchdog is importing — fails with An extraction is already running for this user. Different users are unaffected and may import concurrently.

Unparseable lines are skipped and counted rather than aborting the run; the count appears both in the result detail and in the Events skipped KPI tile, which turns orange as soon as it is greater than zero. Regexes are executed with a 0.25-second timeout per match where the optional regex module is installed, so a catastrophically backtracking pattern costs you skipped lines rather than a frozen backend.

19.6 Checkpoints

Each source has exactly one checkpoint, stored on the server. It is what makes “import only what is new” possible, and it is shared between the manual delta run and the watchdog — both advance the same offset, which is precisely what stops the two triggers importing a line twice between them.

Note — a manual run imports the whole file at once A manual Run extraction reads everything from the checkpoint to the end of the file in a single run, however large the file is (it is streamed in bounded chunks internally, so it is never loaded into memory whole). The watchdog is different: to keep each unattended poll cheap it reads at most one ~8 MB chunk per poll and lets a large backlog drain over several polls. So if you point the watchdog at a huge pre-existing file it will catch up over a few polls, whereas a manual run finishes it in one.

19.6.1 What is stored

FieldMeaning
byteOffsetWhere the next read resumes. Only complete lines — up to the last newline — are ever consumed, so the offset always stops on a line boundary and a partial trailing line is left for next time.
sizeThe file's size at the last read, used to detect truncation.
signatureThe MD5 of the file's first 64 bytes — a fingerprint that does not change as the file grows by appends, used to detect replacement.
recordsThe cumulative number of events imported from this file.
updatedAtWhen the checkpoint was last written, shown in your local time.
lastErrorThe last failure message, or empty. Cleared by the next successful read.

The checkpoint panel in the Run dialog renders this as one of three lines: red ⚠ <last error>; ✓ <n> records imported · read to <bytes> of <bytes> bytes · last <date and time>; or “No checkpoint yet — this is the first import of this file.”

19.6.2 Delta versus full re-read

Every manual run is checkpointed, whether or not delta upload is ticked.

  • Delta run — reads from byteOffset to the end of the file and adds to the records counter.
  • Full run (delta unticked) — reads from byte 0, ignoring the stored offset and signature, and restarts the records counter.
  • Empty file, or nothing appended — a normal outcome, not an error. The run still executes, so it appears in the pipeline and the KPIs, and simply writes no rows.

19.6.3 Rotation, truncation and replacement

Log files are rotated, and the console detects the two common shapes of that without you doing anything:

Truncation or rotation in place
The file is now smaller than the stored offset. Reading restarts at byte 0.
Replacement under the same name
The size did not shrink, the offset is greater than zero, but the stored signature no longer matches the file's first 64 bytes. The offset must therefore point into unrelated content, so the file is re-read from byte 0.
Warning A file shorter than 64 bytes gets an empty signature and cannot be fingerprinted. Replacement of such a file without a size decrease goes undetected, and the import silently resumes at an offset that now means something else.
Note A single “line” longer than the whole 8 MB read cap is treated as unparseable log content: the offset jumps past it rather than retrying it forever.

19.6.4 Failed runs leave the checkpoint alone

The checkpoint advances only after the run's rows are safely written — offset, size, signature and record count are updated, and lastError is cleared, only on success. A failed run leaves all of it exactly where it was, so the next attempt re-reads the same lines instead of skipping them. Combine this with §19.4: a failure part-way through a bracketed import means some rows are already committed and will be read again on the retry.

19.6.5 Resetting the checkpoint

↺ Reset checkpoint appears in the Run dialog's checkpoint panel (and, for watchdog sources, in the source wizard). Its tooltip reads Forget how far the file has been read, so the next import starts from the top. It is disabled while a run is in progress and when there is no checkpoint to forget.

  1. Open the Run dialog for the source (▷ on its badge), or edit the source and scroll to the watchdog panel.
  2. Read the current checkpoint line so that you know how many records have been counted so far.
  3. Click ↺ Reset checkpoint. The next import — manual or watchdog — starts at byte 0.
Warning Resetting a checkpoint is not a database cleanup. Nothing is removed from JOURNEYS. Unless you delete the destination project first, the next import appends the file's events all over again.

The checkpoint is also discarded automatically when you change the source's file path (§19.3.3).

19.7 What the import writes

The File extractor reads the file line by line, applies the linked source type's regexes, and writes one JOURNEYS row per line that yields a complete event. A line produces an event only if a case id, a step and a timestamp were all captured and the timestamp normalises successfully; anything else counts as one skipped line. Events are pushed in batches of 500 rows, and progress is reported every 200 processed lines.

JOURNEYS columnWritten value
PROJECT_IDThe project id chosen in the Run dialog (or configured on the watchdog).
EVENT_IDThe hex MD5 digest of the raw captured id — never the raw value.
STEPThe captured step value, replaced by a compound rule's step when one matches.
STEP_IDAlways NULL; it is filled in at load time by the main app.
EVENT_TIMEA real TIMESTAMP, normalised to YYYY-MM-DD HH:MM:SS.
META_1, META_2, META_3The first three meta fields of the source type, in field order; NULL where the regex did not match. A fourth meta field is silently unused, and helper fields are never written at all.
SAMPLE_SETAlways the literal string ORIGINAL.
Warning The EVENT_ID hashing is unconditional and cannot be switched off. Because the same raw id always produces the same digest, journeys still correlate correctly across events — but the original identifier (which is often a login or customer number) cannot be recovered from the database afterwards. Treat this as the pseudonymisation it is: if you need the raw id for business reporting, capture it additionally as a meta field, with all the data-protection consequences that carries.

After the events are written, the extractor creates the companion rows that the main app needs, always create-if-missing and never update-if-present:

PROJECTS
If the project id has no row, one is created with TITLE set to the project id and an empty description. The run log line is created project '<id>'.
METAS
Only when at least one meta field carries a business title. A row with META_1_TITLE…META_3_TITLE is created if the project has none. Existing rows are never rewritten, so editing meta titles later does not change a METAS row that already exists.
STEPS
Every step name seen in the run that has no row for this project gets one: empty description, a background colour chosen deterministically from a fixed ten-colour palette (the same step name always gets the same colour), white foreground, SCORE 0 so auto-created steps do not skew scoring, a deterministically chosen shape, END_OF_PROCESS false and no parent. The run log line is created <n> new step(s): <names>.

19.8 Where a run is recorded

Every import writes to three places you can consult afterwards:

  • The Abstraction layer status card — state pill, target line, KPI tiles and the expandable Run log with lines such as reading <path> → <schema>.JOURNEYS (project <id>), pushed 500 events, skipped 2 unparseable line(s) and created project 'X'. At most the 50 most recent messages are kept.
  • The ingestion pipeline canvas and the KPI tiles, which accumulate every run that has actually started — manual or watchdog.
  • The admin log under tag DATA: import started: …, import finished: … — <detail>, and on failure import failed: … — <error> at error level.
Tip On success the destination connection and project are remembered on the source, so the Run dialog reopens on the same target next time. Renaming or otherwise editing the source in the wizard carries that memory forward — it is only lost when the connection assignment itself is revoked.
