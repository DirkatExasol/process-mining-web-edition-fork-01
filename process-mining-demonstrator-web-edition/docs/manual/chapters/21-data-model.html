21 Reference: The Exasol Data Model

Everything the application shows you comes out of one Exasol schema. This chapter is the complete reference for that schema: the six tables, every column with its type and default, what the SAMPLE_SET column means and how samples and simulations live alongside the original data, how EVENT_ID is formed in the demo datasets and what that means when you want to trace a journey back to a source record, how the process map is derived from the event log, and what changes when the optional TRANSITIONS_RAW table is in play. It closes with a summary of the provisioning DDL, guidance on sizing, and the list of database privileges the application needs. It is written for database administrators, ETL developers and anyone who has to load, size or govern the data — not for everyday chart users.

The schema at a glance

The application reads and writes six tables inside a single Exasol schema. The schema name is part of each connection definition, so different connections may point at different schemas on the same or different servers. Five tables are the canonical set; the sixth, TRANSITIONS_RAW, is an optional performance table that the application builds for itself.

The source tables normally arrive with your own data — you load them from your ETL and the application only reads them. The application can also create them itself; see Schema provisioning. All provisioning DDL uses IF NOT EXISTS, so re-running it never disturbs existing data and never alters an existing table.

PROJECTS

One row per process-mining project. A project is the top-level unit of separation: every other table carries PROJECT_ID and every query the application issues is scoped to one project.

ColumnTypeConstraint / default
PROJECT_IDVARCHAR(100)NOT NULL, PRIMARY KEY
TITLEVARCHAR(500)default ''

The project picker lists projects ordered by TITLE. A project with an empty title is displayed under its PROJECT_ID instead.

Note A PROJECTS row is not strictly required for data to be visible. The project listing in the connection editor reports a project if it exists in either PROJECTS or JOURNEYS, so an orphan on either side is visible rather than silently invisible. This is deliberate: it lets you spot a load that wrote events without registering the project, and a project registration whose events never arrived.

JOURNEYS — the event log

One row per (event, step). This is the only large table in the schema, and the only one your ETL normally writes.

ColumnTypeConstraint / defaultMeaning
PROJECT_IDVARCHAR(100)NOT NULLOwning project
EVENT_IDVARCHAR(200)NOT NULLThe journey (case) identifier
STEPVARCHAR(500)NOT NULLThe activity name
STEP_IDDECIMAL(18,0)—Orders steps that share the same EVENT_TIME
EVENT_TIMETIMESTAMPNOT NULLWhen the step happened
META_1VARCHAR(1000)—Free-form attribute 1
META_2VARCHAR(1000)—Free-form attribute 2
META_3VARCHAR(1000)—Free-form attribute 3
SAMPLE_SETVARCHAR(20)default 'ORIGINAL'Which data set the row belongs to

A journey is the set of all rows sharing one EVENT_ID within one project and one sample set. Steps are ordered by EVENT_TIME, and where two steps carry the same timestamp — common when a source system stamps a whole batch at once — by STEP_ID. If your source has no natural sub-second ordering, populate STEP_ID with an increasing counter per journey; otherwise the order of same-second steps is arbitrary and the derived process map will show pairs that never occurred in that order.

Physical layout

When the application creates JOURNEYS itself, the DDL declares a physical layout tuned for the queries the map issues:

DISTRIBUTE BY EVENT_ID
Co-locates all events of one journey on one cluster node, so the transition query's LEAD() window and every GROUP BY EVENT_ID filter run node-local instead of shuffling rows across the cluster. EVENT_ID is high-cardinality, so the rows still spread evenly.
PARTITION BY EVENT_TIME
Lets Exasol prune by date range. It helps the selection of event IDs that are active in the filter window more than it helps the final scan. Exasol requires the partition column to differ from the distribution column, which is why the two are split this way.
Warning Provisioning never alters an existing table. Because all DDL is written with IF NOT EXISTS, a JOURNEYS table that already exists keeps whatever layout it has — you get no error and no warning, only slower queries. A DBA must apply the layout by hand: 
ALTER TABLE JOURNEYS DISTRIBUTE BY EVENT_ID;
ALTER TABLE JOURNEYS PARTITION BY EVENT_TIME;

EVENT_ID: type tolerance and hashing

The declared type of EVENT_ID is VARCHAR(200), but in real deployments it varies — sites use VARCHAR, HASHTYPE or DECIMAL depending on what their source systems produce. The application tolerates all of them. This is also why TRANSITIONS_RAW is deliberately built with CREATE TABLE AS SELECT rather than an explicit column list: its EVENT_ID then inherits the exact type of the JOURNEYS column. Hard-coding a type there would make the semi-join against JOURNEYS raise Exasol's Incomparable Types error on any site whose column is not a VARCHAR.

The three built-in demo datasets do not use readable order numbers as journey identifiers. Each demo EVENT_ID is the MD5 hex hash of a synthetic key:

DatasetProjectSynthetic key hashed into EVENT_ID
Retail — Online BookstoreBOOKSTOREORD-000001, ORD-000002, …
Finance — Online Credit ApplicationCREDITCRA-000001, CRA-000002, …
Transportation — Flight Booking & ManagementFLIGHTSFLT-000001, FLT-000002, …

In each case the key is the three-letter prefix plus a six-digit sequence number, and the value stored in EVENT_ID is the MD5 hash of that string in hexadecimal.

Note The consequence for tracing back to a source record: an EVENT_ID you read off the Individual Journey view or copy out of a variant listing is a one-way hash, not an order number. You cannot invert it. To find the underlying case you must hash forward — compute the MD5 of the candidate key and compare — or keep your own mapping table. The same reasoning applies to production loads: if your ETL hashes or pseudonymises the case key on the way in (a common requirement when the event log leaves the source system's access controls behind), plan for the lookup direction you will actually need before you load, because the application only ever shows you the stored identifier.
Tip If you need operators to be able to identify a case from the chart, carry a human-readable reference in one of the three META columns. Meta values are displayed and filterable; EVENT_ID is only ever matched exactly.

SAMPLE_SET: originals, samples and simulations

SAMPLE_SET is what lets one JOURNEYS table hold your real data and several derived working sets side by side. It takes four values.

ValueMeaning
ORIGINALThe source data as loaded. This is the default for new rows and cannot be deleted from the application.
SAMPLE_1First derived working set.
SAMPLE_2Second derived working set.
SAMPLE_3Third derived working set.

Everywhere the application filters by sample set, NULL is treated as ORIGINAL. The generated predicate is SAMPLE_SET = 'ORIGINAL' OR SAMPLE_SET IS NULL, so a legacy table whose rows were loaded before the column existed continues to work unchanged and its rows count as original data.

Warning Whenever a count differs from what you expect, check for NULL values in SAMPLE_SET. They are invisible in the sample picker but they are counted as ORIGINAL everywhere else.

The quiet migration

If the column is missing, the application adds it on demand rather than failing. It issues, ignoring failures (for instance because the column already exists):

ALTER TABLE JOURNEYS ADD COLUMN SAMPLE_SET VARCHAR(20) DEFAULT 'ORIGINAL';
UPDATE JOURNEYS SET SAMPLE_SET = 'ORIGINAL' WHERE SAMPLE_SET IS NULL;

Because the failures are ignored, an account without ALTER rights simply leaves the table as it is — the application then keeps working through the IS NULL branch of the filter, but no samples can be created.

Samples are physical copies

Creating a sample does not create a view, a flag or a reference. It INSERTs the chosen journeys' rows back into JOURNEYS with the new SAMPLE_SET value, in batches of 200 event IDs per INSERT. Every row of every selected journey is duplicated. Three sample sets covering a quarter of the log each therefore add roughly 75 % to the size of the table.

Three sampling strategies are offered: random, temporal and pathDiverse. Whichever you choose, the storage behaviour is the same.

Deleting a sample deletes only the rows carrying that SAMPLE_SET value. Deleting ORIGINAL is not possible through the application — the call is a no-op — so a mis-click can never destroy your source data through the sampling controls.

Warning Sample deletion is irreversible. There is no recycle bin and no undo. The rows are removed with a DELETE and can only be recovered by re-running the sampling — which, for the random strategy, will not produce the same selection.

STEPS

Presentation and scoring for each step, edited through the application's Step editor. This table is what makes the map look like your process rather than a set of grey boxes.

ColumnTypeConstraint / default

Where a value is missing or is not a string, the reader falls back to: the step name for the description, blue for the background colour, white for the foreground colour and stadium for the shape. A step that appears in the transitions but has no STEPS row at all is synthesised on the fly in grey (gray background, white foreground, stadium shape). Grey nodes on the map are therefore a reliable signal that your event log contains an activity nobody has described yet.

Warning STEPS must hold exactly one row per (PROJECT_ID, STEP). The application caches the table per user and per project and joins it to the event log to attach scores; duplicate rows would multiply journey rows in that join and inflate every score-derived figure. If you load STEPS from an ETL rather than through the Step editor, enforce uniqueness there.

The cache is refreshed when a step is edited in the Step editor, when the user disconnects or connects to another connection (it is never carried across connections), when a manager deletes a project from the connection editor, and when demo content is generated. A STEPS row changed behind the application's back — by a direct SQL update, for example — is picked up only after one of those events.

How the process map is derived from the event log

Nothing in the schema stores a process model. The directly-follows graph you see on the canvas is computed from JOURNEYS every time you load or filter a map.

The live query

The derivation is a self-join expressed as a window function. Conceptually the application does this:

  1. Select the rows of the chosen project and sample set that survive the current filters.
  2. Within each journey, order the rows by EVENT_TIME and then by STEP_ID, and use LEAD() to pair every row with its immediate successor. Each pair is one observed transition, and the difference between the two timestamps is its duration.
  3. Aggregate the pairs by (from-step, to-step), producing COUNT and the AVG, MIN, MAX and STDDEV of the gap. Those five figures are what the edge labels, the metric colouring and the duration statistics display.
-- conceptually equivalent to
SELECT FROM_STEP, TO_STEP,
       COUNT(*), AVG(DUR), MIN(DUR), MAX(DUR), STDDEV(DUR)
FROM (
  SELECT STEP AS FROM_STEP,
         LEAD(STEP)       OVER (PARTITION BY EVENT_ID ORDER BY EVENT_TIME, STEP_ID) AS TO_STEP,
         LEAD(EVENT_TIME) OVER (PARTITION BY EVENT_ID ORDER BY EVENT_TIME, STEP_ID) - EVENT_TIME AS DUR
  FROM JOURNEYS
  WHERE PROJECT_ID = ? AND (SAMPLE_SET = ? OR ...)
)
WHERE TO_STEP IS NOT NULL
GROUP BY FROM_STEP, TO_STEP;

The last row of every journey pairs with nothing and drops out; that is why a journey of n steps contributes n − 1 transitions. On large logs the window function dominates the cost of the query, and it is paid again on every filter change.

TRANSITIONS_RAW: what the materialised table changes

TRANSITIONS_RAW performs the pairing once and stores the result, so that the map query at request time is a pure GROUP BY aggregate with no window function at all. The admin interface describes it as "much faster for interactive filtering on large logs".

ColumnMeaning
PROJECT_IDOwning project
EVENT_IDThe journey — type inherited from JOURNEYS
FROM_STEPThe predecessor activity
TO_STEPThe successor activity
FROM_TIMETimestamp of the predecessor
TO_TIMETimestamp of the successor
DUR_SECSPrecomputed gap in seconds
SAMPLE_SETWhich data set the pair belongs to

The table carries PROJECT_ID, SAMPLE_SET and EVENT_ID, which is exactly what the filter clauses need, so the same filters apply unchanged. Build mechanics worth knowing:

  • It is built with CREATE OR REPLACE TABLE … AS SELECT into a staging table TRANSITIONS_RAW_STAGE, so every column type — critically EVENT_ID — inherits from JOURNEYS exactly.
  • The pairing covers every project and every sample set in one pass. The window partitions by (PROJECT_ID, SAMPLE_SET, EVENT_ID), because an EVENT_ID is only unique within one project and one sample set.
  • After the build the job attempts ALTER TABLE … DISTRIBUTE BY EVENT_ID on a best-effort basis — a failure there never aborts the rebuild, since distribution is only an optimisation — then counts the rows, then swaps the table in with DROP TABLE IF EXISTS TRANSITIONS_RAW followed by a RENAME TABLE.
  • Readers are never blocked by the build. The swap leaves a sub-millisecond window in which no live table exists, during which reads simply fall back to the live query.
  • The operation is idempotent and safe to re-run. It requires a schema name and returns {ok, error, rows, built_at}, where rows is the pair count and built_at an ISO-8601 UTC timestamp.

Reading is equally forgiving. With the per-connection flag Use pre-materialized transitions switched on, any read failure — table missing, never built, mid-swap — is non-fatal: the application falls back to the live query so that the map never breaks, and logs a warning under the operation materialize. The detail-pane pill tells you which path served the map: "⚡ Pre-materialized", "⚠ Live (not built)" or "↻ Live query".

Warning TRANSITIONS_RAW is a snapshot and goes stale the moment JOURNEYS changes. Loading data, generating demo content and creating or deleting a sample do not rebuild it automatically. If the table still exists you will see pairs computed from the old log; if it does not, you get the live fallback. Make the token-authenticated rebuild call the last step of every ETL run that touches JOURNEYS.

Schema provisioning DDL summary

Requires: Administrator, Power user or Developer in the application — and a database account permitted to CREATE SCHEMA and CREATE TABLE

Create schema & tables is available in the admin panel (Connections tab → connection editor → Database inner tab) and in the main application's connection editor sheet (Database / LLM Details tab). Both surfaces run the same backend routine:

  1. Connect without opening a schema, because the target schema may not exist yet.
  2. CREATE SCHEMA IF NOT EXISTS for the schema named in the form.
  3. OPEN SCHEMA.
  4. Run each table's CREATE TABLE IF NOT EXISTS in the order PROJECTS, JOURNEYS, STEPS, METAS, NOTES.

The routine returns {ok, error, created}. On failure, created lists what was made before the failure, so partial progress is reported honestly — schema created but a table refused, for example. On success the banner reads "Created: schema <name>, PROJECTS, JOURNEYS, STEPS, METAS, NOTES". A blank schema name is refused with "A schema name is required.", and the admin panel pre-checks with the toast "Enter a schema name first."

The schema identifier is safely double-quoted, with embedded quotes doubled, so mixed-case and special-character names work. Remember that a quoted identifier is case-sensitive in Exasol: a schema created as "Demo" is not the same object as DEMO.

The effective shape of the DDL is:

CREATE SCHEMA IF NOT EXISTS "DEMO";
OPEN SCHEMA "DEMO";

CREATE TABLE IF NOT EXISTS PROJECTS (
  PROJECT_ID   VARCHAR(100)  NOT NULL PRIMARY KEY,
  TITLE        VARCHAR(500)  DEFAULT '',
  DESCRIPTION  VARCHAR(2000) DEFAULT ''
);

CREATE TABLE IF NOT EXISTS JOURNEYS (
  PROJECT_ID  VARCHAR(100)  NOT NULL,
  EVENT_ID    VARCHAR(200)  NOT NULL,
  STEP        VARCHAR(500)  NOT NULL,
  STEP_ID     DECIMAL(18,0),
  EVENT_TIME  TIMESTAMP     NOT NULL,
  META_1      VARCHAR(1000),
  META_2      VARCHAR(1000),
  META_3      VARCHAR(1000),
  SAMPLE_SET  VARCHAR(20)   DEFAULT 'ORIGINAL'
)
DISTRIBUTE BY EVENT_ID
PARTITION BY EVENT_TIME;

CREATE TABLE IF NOT EXISTS STEPS (
  PROJECT_ID      VARCHAR(100)  NOT NULL,
  STEP            VARCHAR(500)  NOT NULL,
  DESCRIPTION     VARCHAR(2000) DEFAULT '',
  BG_COLOR        VARCHAR(30)   DEFAULT '',
  FG_COLOR        VARCHAR(30)   DEFAULT '',
  SCORE           DECIMAL(18,2),
  SHAPE           VARCHAR(50)   DEFAULT '',
  END_OF_PROCESS  BOOLEAN       DEFAULT FALSE,
  BELONGS_TO      VARCHAR(500),
  PRIMARY KEY (PROJECT_ID, STEP)
);

CREATE TABLE IF NOT EXISTS METAS (
  PROJECT_ID    VARCHAR(100) NOT NULL PRIMARY KEY,
  META_1_TITLE  VARCHAR(500) DEFAULT '',
  META_2_TITLE  VARCHAR(500) DEFAULT '',
  META_3_TITLE  VARCHAR(500) DEFAULT ''
);

NOTES follows with the columns listed in the NOTES section. TRANSITIONS_RAW has no provisioning DDL at all — it only ever comes into existence through a rebuild.

Tip In the admin panel only, the checkbox Also build pre-materialized transitions after provisioning (default unchecked) runs a rebuild immediately after a successful provision. The resulting table is empty until JOURNEYS is loaded, but the structure exists and the per-connection flag can be switched on straight away. The result line gains the suffix " · transitions built (N pairs)" or " · transitions build failed: <error>".
Warning Provisioning, testing and demo generation all use the password typed into the form, not the stored one. On a saved connection whose password field shows the "unchanged" placeholder, the operation runs with an empty password and normally reports an authentication failure even though the connection itself works. Retype the password before using any of these three buttons.

Privileges the application needs

The provisioning banner states the boundary plainly: "This requires a database account permitted to CREATE SCHEMA and CREATE TABLE — only your database administrator can grant those rights; this application cannot." The application never attempts to grant anything to itself. Decide which of the following capabilities the connection's database account should have, according to what you want that connection to be able to do.

CapabilityNeeded forStatements issued
SELECT on the schemaEverything. A read-only connection can browse maps, statistics and journeys.SELECT on all six tables
INSERT, UPDATE, DELETEThe Step editor, project metadata, notes, samplingINSERT / UPDATE / DELETE on STEPS, METAS, NOTES, JOURNEYS
CREATE TABLE in the schemaCreating NOTES lazily on first use; building TRANSITIONS_RAW_STAGECREATE TABLE IF NOT EXISTS, CREATE OR REPLACE TABLE … AS SELECT
ALTER TABLEThe SAMPLE_SET migration, the NOTES column migrations, the distribution hint on TRANSITIONS_RAWALTER TABLE … ADD COLUMN, ALTER TABLE … DISTRIBUTE BY
DROP TABLE and RENAME TABLEThe TRANSITIONS_RAW staging swapDROP TABLE IF EXISTS, RENAME TABLE
CREATE SCHEMACreate schema & tables and demo generation onlyCREATE SCHEMA IF NOT EXISTS

Demo generation additionally requires INSERT, and its replacement step requires DELETE on PROJECTS, METAS and JOURNEYS for the dataset's own project. Project deletion from the connection editor issues DELETE … WHERE PROJECT_ID = '<id>' against JOURNEYS, STEPS, METAS, NOTES, TRANSITIONS_RAW and PROJECTS, in that order — children before PROJECTS. Absent tables are skipped rather than treated as errors, and the response's tables array lists what was actually cleared.

Tip A practical split for production: give analysts' connections SELECT plus INSERT/UPDATE/DELETE so notes, steps and samples work, and keep CREATE SCHEMA, DROP and RENAME for a separate maintenance connection used by the administrator and by the scheduled rebuild. Because the rebuild endpoint uses the stored credentials of the connection it names, a scheduler can drive the maintenance connection without ever handling a database password.
Warning Project deletion is permanent. There is no undo and no application-level backup, and it erases every note attached to the project along with the events. The confirmation dialog spells out the six tables it clears; read it before confirming.

Sizing the schema

Only JOURNEYS and TRANSITIONS_RAW grow with your data. PROJECTS, METAS and STEPS are configuration-sized — tens to hundreds of rows — and NOTES grows with human activity, not with the log, although a single note row can hold up to 100,000 characters of thread text.

Work with row counts rather than bytes:

JOURNEYS, original data
journeys × average steps per journey rows. This is the base figure for every other estimate.
JOURNEYS, with samples
Add the full row count of every sampled journey again, per sample set. Samples are physical copies, so a project with three 25 % samples occupies about 1.75 times the base. Budget for the worst case — three sample sets at 100 % would quadruple the table.
TRANSITIONS_RAW
Roughly base rows − journeys pairs per project and sample set, because the final step of each journey has no successor. Its rows are narrower than JOURNEYS rows (no META columns) but it covers all projects and all sample sets in one table, so size it against the whole schema, not one project.

Points that affect load and query time rather than storage:

  • Inserts from the sampling and demo-generation paths are batched at 200 journeys' rows per INSERT. Your own ETL should batch at least as coarsely.
  • Demo generation is hard-capped at 20,000 journeys server-side. A larger request is silently clamped to exactly 20,000; the field's own maximum is the same figure and its default is 500. Use a real load, not the demo generator, to build a volume-test data set beyond that size.
  • Demo event times are spread randomly over 2024-01-01 08:00 to 2024-12-31 22:00, so date filters on demo data always operate within that single year.
  • Heavy statistics queries — variants, routes and the goodness metric — are subject to a query timeout of 30 s by default. On a log large enough to hit it you will see "Statistics query timed out (30 s). Narrow your date range or filters and try again." Variant and route listings are additionally capped at 10,000 rows.
  • Every statement runs under a 300 s socket timeout. Rebuilds, provisioning and demo generation have no application-level timeout of their own and are bounded only by that per-statement limit.
Note One user's queries are serialised. The database driver is synchronous and a single connection cannot safely run concurrent statements, so each user's queries queue behind one another on that user's own session. Different users run in parallel on their own sessions. When you size the cluster, size it for concurrent users, and remember that a long rebuild launched from a scheduler runs on its own stored-credential session and does not block anybody's map.

Loading checklist

A summary of the operational rules that follow from the model above.

  1. Create or verify the schema and the five canonical tables, either from your own DDL or with Create schema & tables.
  2. If JOURNEYS pre-existed, apply DISTRIBUTE BY EVENT_ID and PARTITION BY EVENT_TIME by hand — provisioning will not do it for you.
  3. Register the project in PROJECTS and fill its METAS row so the meta filters are labelled.
  4. Load JOURNEYS. Populate STEP_ID wherever timestamps can collide, and set SAMPLE_SET to ORIGINAL (or leave it null — it is read as original).
  5. Populate STEPS with one row per activity, unique on (PROJECT_ID, STEP), or let operators build it up in the Step editor and watch for grey nodes as the to-do list.
  6. If the connection has Use pre-materialized transitions enabled, call the rebuild endpoint as the final step of the load. Confirm afterwards that the map's pill reads "⚡ Pre-materialized" and not "⚠ Live (not built)".
